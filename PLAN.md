Несколько номеров (например, №45.1/77.1) допустимы только для **одного связанного сценария**: в реестре указывается одна и та же поставка, а не два независимых завершения.

**Архитектурный gate каждого PR (28.10.2026):** перед реализацией — C0-A (существующие writer/reader/источник истины/ACL/CAS/backup, дубли и риски); после фактического diff — C3-B (та же карта, актуальные регрессии, новое дублирование и план-конформность). [Обязательные правила](docs/DEVELOPMENT_GATES.md), [ретроспективный аудит памяти #166–185](docs/architecture/MEMORY_PR_RETROSPECTIVE_2026-10-28.md). Новую конкурирующую очередь/граф/поиск не создавать; C3 большой — только шаг 6.5, после M1–M4.

**Учёт результатов:** код в PR ≠ код в main ≠ зелёный CI точного SHA ≠ проверенный Android ≠ функциональность целиком. ### M0 — единая архитектура долговременной памяти (PR #131, проектный контракт)

**Проверка типов сохраняемых материалов:** [матрица покрытия](Plans/MEMORY_CONTENT_COVERAGE.md) уточняет, как одна память хранит медицинские анализы и обследования, врачебные и кулинарные рецепты, веб-статьи, Telegram/MAX, ссылки на видео, документы и другие материалы. **Ссылку без скачанного контента можно сохранить и найти**; это не даёт права говорить, что её содержимое прочитано. Специализированные медицинские поля и views не требуют отдельной памяти или облачного сервера; DICOM/клинические решения/задачи с уведомлениями не входят в базовый движок. Интегрировать в уже имеющуюся очередь, не добавлять второй план.



**Решение владельца:** память PersAI должна быть памятью интеллектуального агента, а не только заметками с поиском. [Memory Engine M0–M6](Plans/MEMORY_ENGINE_ARCHITECTURE.md) проектирует локальный временной граф: идентичность людей/объектов, типизированные утверждения, отдельные эпизоды, два времени (действительности и знания), точное происхождение, пользовательское подтверждение связей/изменений, доступ по всему пути связей и восстанавливаемые FTS/векторы. SQLCipher, AppLock, отсутствие сервера и сохранение оригиналов обязательны.

**Порядок:** этот документ, §2, остаётся единственной очередью; M0–M6 — архитектурные этапы, реализуемые согласованно с пакетами №66.1/63а.1/66.2/45.1/66.3/72/66.4/83, а не вторая параллельная очередь. Уже слитая в main реализация №66.1 со схемой v6 не подменяет будущий канонический движок и сохраняется при переходе. [Исполнительный подплан надёжности](Plans/MEMORY_RELIABILITY.md), [временные факты](Plans/TEMPORAL_MEMORY.md) и [связи](Plans/RELATIONAL_MEMORY.md) содержат конкретные требования и тесты; архитектура M0 объединяет их в целевую модель, не отменяя ни одной проверки. Новые SQL DDL, repository, переход и backup — отдельные PR после проектного контракта; текущий PR #131 не меняет runtime.

**Интерфейс обязательно доработать**, когда будут готовы стабильные API фактов/связей/источников: [M4-UX](Plans/MEMORY_ENGINE_UI.md) — карточки людей/объектов, время и история, источники/таймкоды, подтверждение новых связей и разрешение конфликтов. UX-спецификацию готовить раньше; сохранять Nebula, визуальную библиотеку, Home и существующий Share. Относится к №65/87–90; не запускает новый глобальный редизайн.

**Интеллектуальная групповая очистка №79:** [MEMORY_HYGIENE.md](Plans/MEMORY_HYGIENE.md) — гибридный анализ дублей, старых статей, видео «посмотреть позже», архивов проектов и неиспользуемых производных индексов. Предложения группируются, объясняются и показывают последствия для графа; перед подтверждением пользователь может **исключить любые элементы**, закрепить/отложить их или сменить действие. **AIRequest:** [оценён выборочно](Plans/MEMORY_ENGINE_AIREQUEST_REVIEW.md), код и зависимости не переносить. ## 4. Что упрощено и что добавлено

- **Убраны преждевременные обязательства:** полная Figma как условие разработки; новый набор иконок после утверждения; жёсткая schema v6 для геозон; требование всех шести ползунков в первом выпуске; прогнозы «через 1–3 года» как сроки; внедрение самокритики/автоадаптации без измеренной пользы.
- **Добавлены недостающие результаты:** согласованность backup/write/restore, versioned evidence и source locations, пагинация/list/count, состояния очереди/покрытия индекса, отмена и восстановление фоновой работы, оценка на больших корпусах, раздельное хранение истории чатов и личных фактов, repair/экспорт и честные границы удаления. ## 5. Неизменяемые решения и границы

1. Локальная память в SQLCipher, fail-closed, общее AppLock, package ID **`com.persai.app`**, существующие ключи/данные/миграции сохраняются. Обычные разрешённые заметки могут обрабатываться выбранной внешней моделью для индексных слов по прежнему решению владельца; private/secret/«Документы» не уходят внешнему агенту. [Фактическая политика](docs/MEMORY_AND_SECURITY.md).
2. Сохранение в память, вложение в чат, отправка модели — разные действия. Ответ модели и самооценка не доказывают изменение данных; результат подтверждает приложение.
3. MSG-0/1/2/6 — середина, без n8n/бота/сервера; теги необязательны, без тега «Входящие», сохранение после предпросмотра. MSG-3/4/5 — позднее; relay только отдельным решением. Не обещать доступ к закрытым постам.
4. «Текущее» выводится из модели времени и подтверждений; старое событие не исчезает при повторении. Новое утверждение вызывает адресный поиск связей/конфликтов, а не LLM-перебор всей памяти. Явное однозначное утверждение не требует повторного одинакового вопроса; гипотезы можно отклонить/отложить.
5. Собственный сервер, синхронизация нескольких устройств, графовая СУБД и облачный vector store не являются предпосылками. Вынос оригиналов из SQLCipher/ANN — только после профиля и проверяемого дизайна. Серверные инициативы не разворачиваются этой ревизией.
6. Подтверждение новой художественной концепции, полномочий внешнего действия или инфраструктуры не равно ручной приёмке каждого PR. В уже порученной работе не добавлять новые стоп-условия. PR публикуются; слияние — по явному поручению владельца.

## 6. Как проверять и завершать пункты

**Обязательное правило процесса (26.10):** [DEVELOPMENT_GATES.md](docs/DEVELOPMENT_GATES.md) + корневой [AGENTS.md](AGENTS.md) и всегда применяемое правило Cursor. Перед **каждым** этапом перепроверять актуальность PLAN, реестра, относящихся подпланов/OpenSpec и референсов/лучших практик; по обоснованной необходимости уточнять планы и реализацию. **После каждого промежуточного этапа** проверять только реализованное и затронутые регрессии, а **отдельным обязательным шагом** — сравнивать фактические результаты с относящимися к этому этапу требованиями **общего плана и каждого профильного подплана**. Необоснованные отклонения исправлять; обоснованные изменения документировать и синхронизировать. Невыполненное будущее помечать `NOT IMPLEMENTED`, непроверенное — `NOT RUN`. [Шаблон отчёта](.github/pull_request_template.md). Это правило не создаёт новый пункт очереди и не заставляет проходить тесты ещё не существующих функций.

Для каждого технического PR: контракт и применимые регрессии → проверки конечного SHA → обновлённый статус. На гонки/жизненный цикл нужны поведенческие тесты. Docs-only изменение не запускает заново весь UI/модельный benchmark и не превращает запланированные сценарии в PASS.

- **Память:** существующий синтетический eval — лишь baseline; реальные embeddings отдельно. Для изменений добавлять длинные вопросы/заметки, отрицания, даты, тёзок, повторные события, удаление/merge/undo, lock/restart и ACL. Цели и непроведённые измерения — [аудит/evidence](docs/architecture/MEMORY_AUDIT_EVIDENCE_2026-10-26.md).
- **Масштаб:** 1k/10k/100k записей — ступени синтетического профиля, не обещание поддержки; 100k после безопасного генератора и ранних измерений. Фиксировать RAM, latency, объём, время восстановления и rebuild; предельные размеры тестировать граничными fixtures, не создавать гигабайты в каждом CI.
- **Android:** обязательный minimal Maestro сохраняется; функциональные проверки расширяются по затрагиваемому сценарию. U5 ведётся по фактам; нет просьбы повторять всё вручную для продолжения. [DEVICE_QA](docs/DEVICE_QA.md), [UI testing](docs/ANDROID_UI_TESTING.md), [performance gate](docs/design/NEBULA_PERFORMANCE_GATE.md).
- **UI:** утверждённый B+C, три вкладки, 320–430 dp/крупный шрифт, Gboard, Back/IME/insets, доступность. [UI delivery](Plans/UI_DELIVERY.md), [production rollout](docs/design/NEBULA_PRODUCTION_ROLLOUT.md). Непроверенный физический телефон не объявлять проверенным по browser.
- **Внешние вызовы:** нужны права/лимиты/отмена/классификация ошибок; произвольная повторная отправка или команда после таймаута запрещена. Журнал показывает реально выполненное, не текст обещания модели.

## 7. Ведение плана и продолжение диалога

1. Читать разделы 1–2 и строку задачи в реестре; проверить актуальные main/PR, затем конкретный подплан/аудит. Не возобновлять работу из исторического «текущий PR».
2. Находки записывать сразу в соответствующий аудит с ID, доказательством и следующим действием. Перед длинным переходом контекста сохранять git-checkpoint/PR. Чат не единственное хранилище решения.
3. Обновлять **активную очередь и строку реестра**, затем подплан/OpenSpec. Для реализуемого контракта — `openspec/changes/...`; принятые требования синхронизировать с `openspec/specs`, без массового архивирования неподтверждённых задач.
4. В завершении различать: код в ветке / main / тесты на SHA / APK / native / физический телефон. У каждой частичной задачи должен быть конкретный остаток, у эксперимента — условие возврата/остановки.
5. Длинную историю держать вне рабочей очереди. [Снимок плана до ред. 75](PLAN_HISTORY_2026-10-26.md), [прежний реестр](Plans/ROADMAP_STATUS_HISTORY_2026-10-26.md) сохраняют старые ссылки и приёмки. Номера не удалять: объединённые, отклонённые и отложенные требования тоже имеют строку.
