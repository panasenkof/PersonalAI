## Обязательное правило реализации КАЖДОГО этапа и пакета (решение владельца 06.11.2026)

Это **обязательный повторяемый цикл** для каждого этапа, подпакета и функционального PR; применяется и к дальнейшим шагам 9–15. Принцип [«диалог прежде экранов»](Plans/DIALOG_FIRST_UX.md) действует внутри пункта 2, а [архив завершённых планов](Plans/history/README.md) не является источником новых задач.

1. **Сверка существующего.** Проверить, что уже реализовано в актуальном `main`, действующем плане и коде; переиспользовать существующие authoritative storage, reader/search и executor. Не создавать второй механизм хранения, поиска или исполнения.
2. **Исполнимая спецификация.** До реализации зафиксировать конкретные действия и естественные реплики пользователя, интерфейс (сначала чат, отдельный экран — с обоснованием), API/контракты, состояния успеха/ошибки/отмены, права/версии и измеримые критерии приёмки.
3. **Последовательные небольшие PR.** Разделить работу на малые функционально законченные PR с собственными регрессионными тестами и явно описанными зависимостями. Не считать частичный PR завершением родительского пункта.
4. **Архитектура до и после.** До каждого PR — C0-A, после фактического diff — C3-B: единый источник истины, writer/reader, ACL/CAS/undo, source/provenance, backup/restore, индексы и отсутствие дублирования механизмов.
5. **CI и слияние.** Устранить ошибки обязательного CI до `SUCCESS` на актуальном SHA, проверить реальный merge target, затем слить PR в `main` и проверить наличие изменений в `main`. Один успешный тест, зелёный локальный запуск или открытый PR не равны DONE.
6. **APK и телефон на функциональных рубежах.** На завершении пользовательского сценария/этапа собрать подписанную APK, проверить соответствующие сценарии на целевом телефоне или честно пометить `NOT_RUN_PHYSICAL` и остаток. Раздельно фиксировать автоматические тесты, конкретные SHA/CI, выпуск APK и фактически выполненную физическую проверку. Проверять затронутые маршруты, а не всё приложение после каждого небольшого PR.

**Выход каждого пакета:** ссылка на PR/merge SHA, C0-A/C3-B, список проверенных требований, подтверждение CI/сборки/Android (или честные `NOT RUN`), остаток и точный следующий пакет по §2. Никаких новых задач из исторических подпланов без явного переноса в действующий PLAN/ROADMAP_STATUS.

## 5. Неизменяемые решения и границы


1. Локальная память в SQLCipher, fail-closed, общее AppLock, package ID **`com.persai.app`**, существующие ключи/данные/миграции сохраняются. Обычные разрешённые заметки могут обрабатываться выбранной внешней моделью для индексных слов по прежнему решению владельца; private/secret/«Документы» не уходят внешнему агенту. [Фактическая политика](docs/MEMORY_AND_SECURITY.md).
2. Сохранение в память, вложение в чат, отправка модели — разные действия. Ответ модели и самооценка не доказывают изменение данных; результат подтверждает приложение.
3. MSG-0/1/2/6 — середина, без n8n/бота/сервера; теги необязательны, без тега «Входящие», сохранение после предпросмотра. MSG-3/4/5 — позднее; relay только отдельным решением. Не обещать доступ к закрытым постам.
4. «Текущее» выводится из модели времени и подтверждений; старое событие не исчезает при повторении. Новое утверждение вызывает адресный поиск связей/конфликтов, а не LLM-перебор всей памяти. Явное однозначное утверждение не требует повторного одинакового вопроса; гипотезы можно отклонить/отложить.
5. Собственный сервер, синхронизация нескольких устройств, графовая СУБД и облачный vector store не являются предпосылками. Вынос оригиналов из SQLCipher/ANN — только после профиля и проверяемого дизайна. Серверные инициативы не разворачиваются этой ревизией.
6. Подтверждение новой художественной концепции, полномочий внешнего действия или инфраструктуры не равно ручной приёмке каждого PR. В уже порученной работе не добавлять новые стоп-условия. PR публикуются; слияние — по явному поручению владельца.

7. Telegram (решение владельца 10.11.2026): основной канал — личный аккаунт через официальную TDLib, резервный — личный бот без сервера. Автосинхронизация по умолчанию выключена и возможна только после разблокировки приложения и подтверждённой авторизации. Произвольные чаты не читаются: только «Избранное» и его подборки.
8. Импорт из Telegram (решение владельца 12.11.2026): пользователь выбирает раздел для аккаунта и для бота отдельно; по умолчанию — закрытые «Входящие». Запись в обычный раздел сразу доступна помощнику и может передаваться выбранной модели. Пакет TG-6.
9. Настройки Telegram входят в зашифрованную резервную копию (решение 12.11.2026): API ID/hash, режим синхронизации, бот с подтверждённым чатом и курсором, выбор разделов. Ключ базы TDLib, флаг входа и отметки автосинхронизации не переносятся: на новом телефоне вход в аккаунт выполняется заново. Пакет TG-10. Учёт расхода LLM в копию не входит (решение 11.11.2026, ARCH-9).

Блок Telegram до приёмки включает ссылки (TG-5) и медиа — фото, документы, аудио, видео, альбомы (TG-9; основное сделано в #475–#482: до 80 МБ для «Избранного», до 20 МБ для бота; автосинхронизация остаётся текстовой); импорт всей истории одной кнопкой (TG-7) реализован по повторному поручению владельца 12.11.2026 (#496).

## 7. Как вести план

1. `PLAN.md` меняется только когда меняется очередь (§1–§2) или решение владельца (§3, §5). Отчёты о PR сюда не дописывать. Предел: 250 строк.
2. Каждый слитый PR: одна строка сверху в `Plans/CHANGELOG.md`; если изменилось состояние пункта — одна ячейка в `Plans/ROADMAP_STATUS.md`; если закрыта проверка — отметка в `Plans/PHYSICAL_ACCEPTANCE_DEBT.md`.
3. Новая непроверенная на телефоне или живой модели функция добавляет строку в `Plans/PHYSICAL_ACCEPTANCE_DEBT.md` тем же PR.
4. Подплан описывает требования и шаги пакета; порядок исполнения он не задаёт. Пакет становится исполнимым только после появления в таблице 2.1.
5. В отчёте о работе раздельно указывать: код в ветке, `main`, CI на точном SHA, APK, физический телефон, живая модель.
6. Постоянные номера №1–91 не удалять и не перенумеровывать.
