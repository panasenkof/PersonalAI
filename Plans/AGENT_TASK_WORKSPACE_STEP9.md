# Этап 9B — временная рабочая область агента (task workspace)

**Контракт 06.11.2026.** Узкий инструмент для длительных задач №73/9T1, **не** новая постоянная задача/этап или отдельный движок памяти. Реализация — [PR #395](https://github.com/panasenkof/PersonalAI/pull/395) поверх [#393](https://github.com/panasenkof/PersonalAI/pull/393) и [#394](https://github.com/panasenkof/PersonalAI/pull/394). Полный CI/merge #395 проверять по его фактическому head SHA; подтверждение на Vivo — **NOT_RUN_PHYSICAL**. Это не означает полного завершения 9B/9C.

## Мотивация и решение

Запрос «найди 20 статей, прочитай, сравни и составь выжимку» не должен заставлять модель заново читать десятки тысяч символов при каждом уточнении. Нужны **два разных типа состояния**:
- **Проверенное исходное состояние** — только канонические заметки/вложения/версии/ACL и фактически исполненные read tools с координатами/coverage; показываются как источники ответа. Первая подборка #393 сохраняет ID+version только в SQLCipher-истории текущего диалога; #394 читает эти handles пакетами. Ссылка/метаданные не считаются прочитанным оригиналом.
- **Рабочие черновики модели** — прогресс, открытые вопросы, промежуточные сравнения и гипотезы. Они **не являются личными фактами, не имеют статуса verified evidence, не изменяют исходные заметки** и не подменяют обязательное чтение оригиналов перед итоговым выводом.

**C0-A/C3-B:** переиспользуется **существующий** `direct-agent/task-state.ts::TaskState` внутри зашифрованного `SavedConversation` (SQLCipher через `chat-store.ts::persist`). Никаких вторых таблиц, произвольных директорий, векторных индексов, отдельного task-runner или нового note writer. Личный раздел «Память» не изменяется автоматически.

## Инструментальный контракт

| Инструмент | Разрешённое поведение | Не разрешено |
| --- | --- | --- |
| `workspace_put(key,kind,content)` | Обновить один короткий рабочий блок текущей задачи только после подтверждённой записи через сериализованный SQLCipher conversation writer. | Сохранять пользовательскую заметку, якобы подтверждать исходный факт/receipt; пути файлов и произвольные поля. |
| `workspace_list()` | Показать ключи, типы, длину блоков; без полного содержимого. | Смешивать чужие диалоги, аккаунты и темы. |
| `workspace_get(key)` | Дочитать один блок модели по ключу; ответ помечен `verifiedSource=false`. | Приводить его как доказательную цитату вместо `read_local_note`/source reader. |
| `workspace_clear()` | Очистить **только** рабочие черновики текущего диалога (при смене цели или по просьбе); постоянные записи, оригиналы и историю ответов оставить. | Удалять пользовательскую память, вложения, другие диалоги, доказательства действий. |

**Пределы MVP:** 16 именованных блоков; каждый до 1200 символов (до ~19,2 тыс. символов данных на задачу), допустимые типы `finding/todo/question/comparison`; ключи — короткие безопасные идентификаторы, строгая JSON-схема. Числа — бюджет состояния, **не** лимит поиска или полноты исходников. При заполнении можно заменить существующий ключ, но нельзя незаметно удалить оригинал или выдавать короткую подборку за «все».

**Изоляция:** один профиль/зашифрованный диалог и одна сохранённая цель `TaskState.goal`; при изменении цели прежняя рабочая область не читается до явной очистки. AppLock/отмена/удаление диалога блокируют инструмент; повреждённое состояние пропускается без потери остальных сообщений. Зафиксированные в workspace тексты **не** отправляются модели автоматически в каждом запросе: общий контекст содержит только ключи/размеры, чтение — по запросу инструмента.

**Долговечность и очистка:** временная означает «не пользовательская долговременная память»; небольшие черновики переживают новое сообщение и восстановление зашифрованного диалога, но не считаются автономной фоновой задачей. Автоматический TTL/очистка завершённых задач **не входит в MVP**: преждевременное удаление может потерять незаконченный анализ. Первый способ очистки — `workspace_clear` либо удаление самого диалога; позднее можно добавить срок хранения с согласованным UX. Каждый `workspace_put/clear` должен дождаться результата *фактической* записи в существующий SQLCipher writer до объявления успеха.

## Пример реального сценария 9B

1. Пользователь выбирает статьи на тему ИИ за календарную неделю через текущую 9A / `select_local_articles`. В истории хранятся конкретные ID/version; `count` и `hasMore` не равны числу прочитанных материалов.
2. Запрос «сделай из них выжимку» вызывает `read_selected_local_articles` на группах по 1–6 записей; при частичных чтениях — `read_local_note` по offset/version, при наличии вложений — `read_local_source_segment`. Версии/ACL проверяются при каждом read.
3. Модель записывает `workspace_put` промежуточную структуру без полных текстов: `paper_1` — краткие наблюдения, `differences` — несовпадения, `pending` — ещё не прочитано. Это **черновики**, не факты из original.
4. В следующем сообщении или после восстановления вызывается `workspace_list/get`, затем при необходимости источник дочитывается/перепроверяется. Итог содержит ссылки на **действительно прочитанные** документы, охват, неизвестные даты, link_only, отсутствующие источники, и предупреждение при незавершённом обходе.

## Отдельные критерии до закрытия 9B/9C

- CI: 16×1200, обновление ключа, неподдерживаемый формат, сериализация и восстановление после перезапуска, 0 записей, новая задача, AppLock, отмена, ошибка сохранения, отсутствие инструмента без host-capability, очищение без изменения обычных заметок.
- E2E c реальной LLM: 6+ материалов с разногласиями и одним link_only, доказать реальный вызов tools, отсутствие выдуманных цитат, проверяемые `read_evidence`, понятный неполный результат при недостаточном бюджете.
- Масштаб: 20/21/100+ материалов с постраничной обработкой без «первые 24 = всё»; проверить чтение 24+ handles и следующий диалоговый turn.
- Физическое Vivo X200 Pro: время/память, отключение приложения, AppLock, смена профиля, продолжение задачи с зашифрованным восстановлением. **Автотест/эмулятор не равны physical PASS.**

## Обязательное правило на будущее

В последующих этапах **переиспользовать этот task workspace только для структурированных промежуточных выводов/плана**, а данные пользователя и доказательства — брать из канонических readers/versions. Любой инструмент отправки почты, изменения памяти, календаря, массового удаления и т. п. обязан иметь свой отдельный preview/confirm/receipt. Наличие рабочего черновика **не даёт модели право выполнить внешнее действие**.
