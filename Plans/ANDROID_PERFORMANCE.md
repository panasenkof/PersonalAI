# Android: отложенный контроль производительности

Статус: **PLANNED / P3**, не реализовано. Детализация №90; основной порядок — [PLAN.md](../PLAN.md).
Начинать после стабилизации интерфейса U0–U5 и основных функций. Не блокирует текущий редизайн.
Функциональный smoke работает отдельно: [ANDROID_UI_TESTING.md](../docs/ANDROID_UI_TESTING.md).

## Цель

На одинаковых сценариях обнаруживать ухудшение CPU, памяти, времени запуска, плавности,
энергопотребления и нагрева относительно подтверждённого baseline. Нельзя сравнивать
температуру виртуального эмулятора с телефоном или объявлять температуру батареи температурой CPU.

## Этапы

1. **PF-1 · контракт измерений.** Фиксировать SHA исходников, SHA-256 APK, ABI, release/profileable
   вариант, модель телефона, Android, частоту экрана, заряд, подключение питания, яркость,
   исходную температуру и температуру помещения. Раздельные cold/warm start и live/static Nebula.
2. **PF-2 · сценарии.** Запуск; 5 минут idle Home; длинный диалог и прокрутка; переходы
   Home/Memory/Settings; импорт файла; локальный поиск; отдельный прогон Whisper.
   Сетевые ответы воспроизводимы, задержки внешнего LLM не включать в стоимость UI.
3. **PF-3 · память/CPU/кадры.** Macrobenchmark/Perfetto, dumpsys meminfo и gfxinfo;
   PSS/RSS/Java/native heap, CPU приложения (не всего хоста), frame timing/jank, cold/warm startup.
   Замеры до нагрузки, в ходе и после восстановления; искать рост памяти на повторных циклах.
4. **PF-4 · физический телефон.** Android Thermal API (статус throttling), доступные температурные
   сенсоры с именем/единицами, температура батареи как отдельная величина. При недоступном
   сенсоре — N/A, не ноль. Сравнивать рост температуры и время до throttling при одинаковой
   нагрузке; батарея/энергия по поддерживаемым устройством средствам, погрешность указывать.
5. **PF-5 · baseline.** Несколько повторов после охлаждения, медиана и разброс, p95 для кадров.
   Хранить JSON + trace + отчёт с ссылками на оба SHA. Baseline — принятая стабильная версия,
   а не любой последний запуск; сравнение с предыдущим валидным запуском дополнительно.
   Калибровать абсолютный и относительный пороги по шуму; не блокировать PR по единичному выбросу.
6. **PF-6 · CI.** Сначала ручной/nightly job на выделенном телефоне, затем предупреждения.
   Блокирующие пороги вводить только после подтверждения повторяемости. Не запускать весь
   performance-набор на каждом UI PR. Эмулятор — для функциональности, телефон — для энергии/нагрева.

## Критерии приёмки

- Контрольная искусственная регрессия обнаруживается, неизменённая сборка не даёт систематических тревог.
- Сравнения несовместимых устройств/условий отвергаются с объяснением.
- При падении или неполном прогоне baseline не обновляется; полный provenance доступен в отчёте.
- Проверены A/B Nebula и восстановление памяти после нагрузки.
- Связанные документы: [Nebula performance gate](../docs/design/NEBULA_PERFORMANCE_GATE.md),
  [UI delivery](UI_DELIVERY.md). Настоящий подплан задаёт поздний срок автоматизации,
  не отменяя исправление уже замеченных зависаний/утечек.
