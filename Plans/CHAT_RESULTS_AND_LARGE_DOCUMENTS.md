## H-DOC1. Большие TXT + PDF и пересказ в одном чате

**Факт теста №5:** в обычном чате файл «СУБД УЗ.txt» отклонён при подготовленном PDF: «Превышен общий лимит текста 24 000 символов или размер вложений». В исходниках mobile/src/direct-agent/chat-attachments.ts установлены MAX_CHAT_TEXT_CHARS = 24000, MAX_CHAT_FILES = 3, MAX_CHAT_FILE_BYTES = 6 МБ для вложений чата. Этот лимит не является универсальным контекстным окном модели. Совместный пересказ **не проверен: BLOCKED**.

**H-DOC1a — отдельный маленький PR.** Точная причина отказа каждого вложения, сохранение других успешно прикреплённых файлов и текста запроса; варианты «Обработать по частям»/«Заменить»/«Убрать». Не писать, что файл доступен модели, если его не удалось принять.

**H-DOC1b — отдельный PR.** Большие TXT/PDF читать ограниченными порциями через существующие extractor/source/segment пути; отдельно обобщать части каждого источника и лишь затем делать общий пересказ. Не вводить вторую очередь, новый writer, индекс или дубликаты оригиналов; не скрывать обрезку до первых N символов. Показать реальные страницы PDF, текстовый слой/OCR coverage и фактически прочитанные либо пропущенные части. У PDF-скана без распознанного текста не выдумывать содержание.

Перед платной обработкой показать выбранную модель/провайдера, примерный объём, бюджет и наличие внешней передачи, получить явное согласие; ограничивать по контексту и токенам фактического провайдера, а не одной константе символов. Существующие ACL/private/secret и запрет облачного fallback обязательны. Прогресс по фактическим частям, отмена, защита при double send, AppLock/смене беседы/профиля, очистка временных данных и ограниченная RAM.

**Приёмка:** большой UTF-8 TXT + текстовый PDF в одном сообщении: «Перескажи каждый отдельно, затем сделай общий вывод». Итог действительно учитывает оба файла и честно обозначает предел чтения. Проверить 24 001 символ, частичный/скан PDF, ошибку одного файла, лимит бюджета, отмену, offline, смену модели, приватность и физический APK.

## H-SAVE1. «Сохранить в заметки» результаты работы диалога

**H-SAVE1a — ответ ИИ.** Через долгое нажатие/контекстное меню у **завершённого** сообщения ассистента — компактное действие **«Сохранить в заметки»**. Сохранить ровно его текст, списки, разметку и действительные ссылки **без нового LLM-вызова**, без огромной дублирующей кнопки под каждым ответом. Незавершённый ответ не объявлять полным.

**H-SAVE1b — итог беседы.** В меню диалога — **«Сохранить итог диалога»**: пользователь явно запускает создание единого конспекта, подтверждает диапазон истории, модель/внешнюю отправку и возможную стоимость; перед сохранением видит полный предпросмотр и фактический охват. Длинную беседу обрабатывать по частям или честно сообщать о пропусках, не сохранять и не тратить токены автоматически. Допускается отдельный небольшой PR поверх H-SAVE1a.

**Единый UX:** оба действия открывают **существующий сценарий создания заметки** с предложенным заголовком, редактируемым текстом, необязательными разделом/тегами («Входящие» по умолчанию), «Сохранить»/«Отмена». Использовать существующий SQLCipher memory writer, ACL/AppLock, backup/restore и автоматическую индексацию/поиск. Никакого нового редактора, таблицы ответов, второго механизма заметок. При Back/отмене запись не создаётся, при ошибке черновик не теряется; «Сохранено» только после настоящего commit, double tap не создаёт дубль. Простое сохранение готового ответа работает без интернета.

**Provenance:** пометка «Ответ ИИ»/«Итог диалога» и дата; ссылка на исходное сообщение/чат, источники PDF/заметки — только при реально устойчивых идентификаторах, разрешённом доступе и рабочей навигации. Не считать LLM-вывод подтверждённым личным фактом, не придумывать ссылки на evidence, не копировать оригиналы автоматически. Смена профиля, lock, удаление исходного чата и устаревшие ссылки не должны раскрывать защищённые материалы или сохранять в неверную память.

**Приёмка:** ответ с Markdown → долгое нажатие → «Сохранить в заметки» → отредактировать → сохранить → открыть и найти; отдельно переписка → «Сохранить итог» → согласие/конспект → предпросмотр → сохранить. Проверить офлайн для готового ответа, длинный текст, отмену, double tap, lock, профиль, приватность, потерю сети для отдельной генерации, Back/IME/320–430 dp, backup/restore. При обобщении нескольких источников шага 9 используется **этот же Save и writer**.

**Порядок:** H-ASR1/2 → H-DOC1a → H-DOC1b → H-SAVE1a → H-SAVE1b (если LLM-часть отделяется) → **H-UX1/2, общая интерфейсная полировка** → финальная APK → **единое итоговое пользовательское тестирование на Vivo** → I. Промежуточные PR проходят targeted CI и security checks; они не требуют отдельной полной пользовательской приёмки, кроме обоснованного native-probe. Каждый пакет требует C0-A, C3-B, targeted regression и CI exact SHA; незавершённое не помечать DONE.
