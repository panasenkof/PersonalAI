# Какие материалы человек хранит в PersAI — покрытие Memory Engine
Дата: 26.10.2026. Статус: M0, проектный контракт и критерии. Архитектурная основа: [MEMORY_ENGINE_ARCHITECTURE.md](MEMORY_ENGINE_ARCHITECTURE.md), очередь реализации: [PLAN.md](../PLAN.md) §2, UX: [MEMORY_ENGINE_UI.md](MEMORY_ENGINE_UI.md).

## Решение: память — не только база личных фактов
Каждый сохранённый материал представляет сочетание **(1) источника/ссылки/оригинала**, **(2) пользовательского назначения/комментария/статуса**, **(3) необязательных типизированных объектов/утверждений**, **(4) связей с людьми, темами и эпизодами**, **(5) индексов, восстанавливаемых по источникам**. Не все пять обязательны: запись «Сохранить ссылку и ничего не анализировать» полноценна.

Сохранять отдельно:
- `source.kind`: web_article, messenger_post, video_bookmark, health_document, lab_report, examination, prescription, cooking_recipe, pdf, photo, audio, document, note, chat_message и другие **категории представления**, не отдельная таблица на каждый kind.
- `source.acquisition_status`: link_only, fetched, extracted, partial, inaccessible, removed; `content_hash` **nullable** при link-only; исходный URL, финальный URL, когда пользователь сохранил, когда проверяли ссылку, когда опубликовано и когда импортировано — независимые поля/атрибуты. Недоступный источник не выдавать за сохранённую офлайн-копию.
- `saved_item/user_mark` как логический слой: saved_at, user_note, favorite/read_later/archived/read/seen, необязательный collection/tag. Реализовать в M1 через `objects+claims` либо лёгкую projection/таблицу, если для 1k–10k ссылок это эффективнее; **не кодировать всё в одном непрозрачном JSON**, когда нужны быстрые запросы/фильтры.
- `extraction_run` и `source_segment` по версии: какой инструмент, когда, какие фрагменты доступны, полнота OCR/ASR/HTML, human edits и локатор страницы/времени. Производные тексты могут быть пустыми, но источник остаётся видимым.
- Приватность и доступ: для health/prescription по умолчанию защищённый режим; локальное индексирование не разрешает внешнюю LLM; никаких автоматических пересылок новых категорий данных. Для собственных чувствительных документов выбор явный и заметный.

## Что ядро НЕ обещает
1. **Любая ссылка ≠ доступный контент:** сохранённый URL виден/находится по известным метаданным и пользовательскому описанию; невозможность получить страницу/ролик фиксируется, «полного конспекта» нет.
2. **Медицинская карточка ≠ клиническая информационная система:** медицинская интерпретация, лекарственные взаимодействия, DICOM-серии, синхронизация с медицинскими учреждениями и нормативный обмен FHIR — самостоятельные интеграции со строгой проверкой; клинического качества LLM не обещать.
3. **Напоминание ≠ память:** факт «назначен препарат» и активное задание «уведомлять о приёме» — разные сущности с разными разрешениями.
4. **Пароли, TOTP, ключи доступа:** защищённый password manager/secret vault требует отдельной модели угроз, защиты отображения и политик извлечения; обычный memory index **не использовать как менеджер паролей**.
5. **Постоянно меняющиеся данные:** банковский остаток, курс, погода, наличие товара, цены/расписания требуют актуального внешнего источника или timestamp/staleness; память хранит известный на время снимок, не «сегодняшнюю правду».
6. **Большие медиа/серии/backup:** полноразмерные фильмы, DICOM, бесконечные журналы и потоковые ленты могут превысить телефонное хранилище; нужно ограничение объёма, выбор «ссылка / оригинал / только извлечённый текст», потоковая обработка и честный backup/restore; не обещать unlimited storage.
7. **Совместное редактирование и синхронизация:** многопользовательские права, межустройственная синхронизация, conflict-free collaborative merge и двусторонняя почта — отдельная распределённая система. Локальный SQLCipher сам их не обеспечивает.
8. **Автоматический импорт приватного чужого контента:** не обходить DRM, авторизацию, защиту мессенджера или разрешения на доступ. User-supplied Share и публичная ссылка имеют разные возможности.
9. **Автономные действия:** запись в календарь, отправка сообщения, подписка, покупка или перевод денег не возникают от сохранённой заметки и требуют отдельного инструмента, бюджета и подтверждения.

## Архитектурные решения, которые добавить перед реализацией
- **M1, источники:** `content_hash` допускает NULL для link_only; статус получения, origin/canonical URL, save intent, user note, source version, дата публикации и актуальности, контроль дубликатов одной ссылки (same URL ≠ same snapshot) и принадлежность коллекциям.
- **M1/M2, typed values:** `claims.value_json` должен иметь ограниченные валидируемые типы (text/number+unit/boolean/date+precision/enum/range/object reference). Для лабораторных измерений источнику и пациенту нужны stable IDs, дата образца, единица, референсный интервал конкретного бланка и precision; выбирать отдельную type-safe measurement projection только по необходимым числовым запросам/индексам, а не создавать таблицу на каждую медицинскую дисциплину.
- **M1/M2, сохраняемая аннотация:** `user_note` / `favorite` / `read_later` / `read` / `seen` принадлежат сохранённому элементу пользователя, не автору публикации; краткая пометка пользователя участвует в поиске отдельно от копии чужого текста.
- **M2/M3, извлечение по требованию:** если источника/транскрипта нет, ответ «сохранена ссылка, содержание неизвестно»; дословная цитата привязана к конкретной версии и локации, а не создана из LLM-резюме.
- **M4-UX, библиотека:** карточка «ссылка / файл / рецепт / анализ / видео» с одинаковыми основными действиями «Открыть / Найти связанное / Исправить / Удалить» и небольшими специфичными действиями только где применимо. При отсутствии подключения тип не исчезает из библиотеки.
- **M5+, плагины:** медицинский ряд/график, медицинское изображение (DICOM), рецепт с масштабированием, видео-таймкоды — специализированные domain view/parsers поверх **одного ядра**, не разные «памяти».
- **QA:** для каждой категории минимум тест link_only→metadata search, successful extraction→source citation, failed extraction→original preserved, duplicate import→no data loss, privacy cloud blocked, backup+restore and stale content status.

## Приоритет доставки, без нового блока в очереди
Самый простой и полезный кейс — **сохранённая ссылка с пользовательской пометкой без обязательного скачивания/анализа**. Затем статьи и рецепты (в том числе кулинарные), как варианты общего импорта №85/MSG-0–2. Лабораторные показатели и медицинские временные ряды — поверх того же M1/M2 с отдельной type validation и строгим доступом; DICOM и лечебные рекомендации вне MVP. Видео-ссылка работает до появления M5, полноценный поиск сцены/таймкода — после доступного транскрипта/индекса. Доставка согласуется с существующим PLAN.md §2 и не требует переносить целый этап раньше исправлений надёжности.
