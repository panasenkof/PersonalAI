# PersAI Memory Engine — M0: целевая архитектура долговременной памяти
Дата: 26.10.2026. Статус: M0 — проектный контракт и план; **не реализация**. Решение владельца: заменить заметко-центричное хранилище на долговременную память агента, сохранение текущих тестовых данных не обязательно.

> **Согласование с актуальным main (PR #129, редакция плана 76):** [MEMORY_RELIABILITY.md](MEMORY_RELIABILITY.md), [TEMPORAL_MEMORY.md](TEMPORAL_MEMORY.md), [RELATIONAL_MEMORY.md](RELATIONAL_MEMORY.md) и [аудит M01–M19](../docs/architecture/MEMORY_RETRIEVAL_AUDIT_2026-10-26.md) задают конкретные промежуточные исправления и сценарии, не отменяемые этим проектом. Этапы M1–M6 — **архитектурные пакеты**, вписываются в единственную очередь PLAN.md §2, а не новая независимая очередь. Уже созданная техническая ветка №66.1/schema v6 остаётся самостоятельным незавершённым пакетом, и до объединения её изменений с новой схемой требуется сверка. В этой ветке PR #131 работа только с документацией.

## 0. Цель, границы, источники решений
Одна локальная SQLCipher-база на профиль, без обязательного сервера и специальной графовой СУБД. Объекты, факты и их история должны переживать отдельные беседы и смену модели. Полные оригиналы не заменяются выводами LLM. Агент не «вспоминает» несуществующее, умеет отвечать «не знаю», указывать источник, хранить неопределённость и корректировать знания со временем.
- Существующее: mobile/src/local-memory/{storage,repository,types,search-index,vectors,backup}.ts; mobile/src/direct-agent/{memory,conversations,chat-store}.ts; media/attachments.ts.
- Продуктовые обязательства: PLAN.md №15–20, 45, 51, 54–56, 60–66, 72–73, 75, 77, 79, 81, 83–85, 87–90; Plans/ASSISTANT_FEATURES.md; Plans/LOCAL_MULTIMODAL_AI.md; openspec/changes/personal-assistant-capabilities/{design,memory-management,media}.md; docs/design/MEMORY_VISUAL_LIBRARY_2026-10-24.md.
- Сохраняем SQLCipher/AppLock, единую авторизацию, доступность словесного поиска offline, подтверждения изменений, черновики и импорт, резервное шифрование, возможность выбрать LLM. Одобрённую сферу Nebula, иконку и чатовый UX не пересоздаём.

## 1. Выбор архитектуры и альтернативы
**Выбрана архитектурная цель:** локальный temporal knowledge graph + журнал эпизодов и доказательств + гибридный индекс. SQLite/SQLCipher с обычными FK, индексами, FTS5; запросы по графу — с ограниченной глубиной, не отдельный GraphDB. Изменения выполняет детерминированный код после валидации; модель возвращает кандидаты.
Альтернатива А (только заметки + поля JSON) не обеспечивает идентичность людей, историю отношений и верифицируемые факты. Альтернатива В (полный event sourcing) излишне усложняет мобильные проекции, сброс и восстановление; выбираем простой неизменяемый журнал действий вместе с материализованным состоянием. Graphiti/Mem0/Letta — концептуальные ориентиры, **не зависимости**.
Персистентное ядро описано ниже; таблицы задач/напоминаний/геозон и процедур вводятся **отдельно по своим этапам**, не нужны для M1.

## 2. Инварианты системы
1. **Источник истины:** оригинальный источник (сообщение, документ, аудио, файл) + утверждение со ссылкой на свидетельство. Индекс/эмбеддинг — производные, переиздаваемые данные.
2. **Личность и стабильные ID:** объект имеет UUID независимо от заголовка/коллекции; слияние сохраняет redirect через merged_into_id и происхождение утверждений. Одинаковое имя не означает один и тот же объект.
3. **Факт ≠ упоминание:** найденное «Лиза» в аудио — source mention, но не утверждение, что Лиза участвовала в разговоре. Подозрения не выдавать за подтверждённые знания.
4. **Два времени:** valid_from/valid_to = когда верно в мире; known_from/known_to = когда это было известно системе. Хранить точность, интервал неопределённости, исходное относительное выражение («год назад»), его дату-основание и часовой пояс. **NULL-окончание не доказывает продолжающееся состояние**: сохранять continuity=ongoing/ended/unknown и last_confirmed_at; не подменять unknown открытым бесконечным периодом.
5. **Повторение vs замещение:** каждое обслуживание автомобиля — отдельное событие; смена единственного текущего места работы может закрыть прежнее состояние. Нельзя выводить уникальность любого предиката из названия: правила задаются словарём предикатов.
6. **Подтверждение:** модель предлагает запись/связь/изменение/слияние; предложение не становится принятым фактом само. Возможна пакетная приёмка после предпросмотра; отклонения учитываются, не задаются снова без новой информации.
7. **Приватность:** политика доступа применяется к факту, исходному сегменту и всему пути обхода графа. Производный факт не может быть доступнее источников, из которых он получен, без явной переклассификации; закрытые данные не уходят облачной модели по умолчанию.
8. **Удаление:** архив/корзина обратимы, уничтожение очищает оригиналы, производные, граф, индексы и персональные копии в журналах. Для экспортированных архивов показывать невозможность удалённого ретроактивного удаления.
9. **Воспроизводимость:** индекс хранит модель, fingerprint весов/токенизатора/нормализации/версии алгоритма и хеш входа. Позднее вычисление не должно воскресить старые данные.
10. **Никакого выполнения инструкций из источника:** материал из веба, документов и транскриптов — данные. Процедура исполнения может появиться только после отдельного подтверждения и проверки прав.

## 3. Канонические таблицы vNext: модель M1
Типы указаны для SQLCipher SQLite: TEXT (UUID/ISO-8601 UTC), INTEGER (epoch миллисекунды/счётчик), REAL, BLOB. Не полагаться на случайную SQLite FK-навигацию; PRAGMA foreign_keys=ON; явные транзакции. Колонки *_id имеют FK, ON DELETE выбирается по политике «удалить/перенаправить/запретить», не по удобству схемы.

Правила: (object_id IS NOT NULL) XOR (value_json IS NOT NULL) для значимого объектного/literal-предиката; exception для unary-предикатов только явно в каталоге. claim_type: state/event/observation/enduring/preference (и при необходимости отдельные виды эпизода); modality: asserted/planned/hypothetical, negated отдельно; status: accepted/disputed/retracted. Предположения LLM живут в proposals, не в accepted claims; явное заявление пользователя сохраняется по стандартному действию «Сохранить», без повторных вопросов о том же факте. На M1 определить допустимые predicate и payload-схемы: relation cardinality (functional/multi-valued), типы субъектов/объектов, допустимые единицы, направленность/обратный предикат. Предикат не задаётся произвольным SQL от модели. Проверки конфликта/пересечения временных интервалов выполняет транзакционный слой.

Важный нюанс: файлу, обнаруженному в чужом источнике, нельзя приписывать произвольного автора/участника; извлечённое моделью описание — отдельное доказательство с методом и уверенностью. «Фото похожей машины» не равно «моя машина».
Дедуп отпечатков Share: на M1 привязать fingerprint (из источника/контента) к уникальному ключу импортирования и источнику; не путать совпадение содержимого с совпадением контекста/подписи/места импорта. При необходимости создать компактный import_receipts, но не дублировать bytes.

Это не финальная DDL; M1 должен утвердить физическую схему, CHECK, FK, индексы, back-up manifest и удалить ненужные атрибуты, если не требуются тестами. SQLite внутренние таблицы FTS в счёт не входят. Индекс вектора версии 2026 нельзя использовать с другим fingerprint. При необходимости вспомогательная таблица модельных метаданных — лишь по доказанной пользе.

### 3.5. Согласование с планами №72 и №66.4 (критично до M1)

Это **одна общая модель**, а не параллельные таблицы для каждого подплана:
- [TEMPORAL_MEMORY.md](TEMPORAL_MEMORY.md) различает occurrence (событие, в том числе с длительностью), observation/measurement (снимок на дату), state (состояние), enduring (устойчивое знание), а также asserted/planned/hypothetical и отрицание. Все эти измерения должны иметь сериализуемый контракт; событие с длительностью не обязано быть точкой `occurred_at`. Конкретный формат интервальной неопределённости и anchor согласовать до финальной DDL.
- `valid_to IS NULL` означает «конец не указан», а не обязательно ongoing. Для вопроса «где сейчас работаю» нужно учитывать подтверждённую непрерывность и дату последнего подтверждения; план/гипотеза о переезде не становится фактом при наступлении даты. Условия predicate учитывают контекст и роль: `primary_employer` ≠ `secondary_employer`, адрес регистрации ≠ место проживания.
- [RELATIONAL_MEMORY.md](RELATIONAL_MEMORY.md) временно предлагает `memory_relation_candidates` + `memory_relation_decisions` поверх legacy `memory_relations`, **если расширять старую v5/v6**. В новой канонической схеме эта функциональность реализуется общими `claims`, `claim_evidence`, `source_mentions`, `memory_proposals` и `memory_operations`. Не строить два одновременно существующих графа и две очереди подтверждений.
- Разговор/обслуживание/поездка могут требовать идентичности **самого эпизода**: разрешить объект типа `event/episode` с ролями `participant`, `about`, `performed_on`, когда бинарного claim недостаточно. Отдельно хранить упоминание имени, доказанное участие и вычисленный поисковый путь, не подменяя одно другим.
- При изменении оригинала/расшифровки связанная `claim_evidence` переходит в `stale`/ `withdrawn`, а утверждение пересматривается на основании **всех независимых подтверждений**; копии одного источника не равны независимым свидетельствам. Ручное подтверждение явного факта пользователя не должно заново запрашиваться после обычной индексации.
- `memory_proposals` обязана хранить точные исходные версии, объектные/смысловые ключи и результаты выбора, чтобы адресные обновления и отказы переживали смену модели, рестарт и переиндексацию без повторного спама; `deferred` не означает `rejected`.
- Техническая ветка №66.1/schema v6 чинит реальную гонку enrichment, но **не является реализацией vNext**. Перед M1 сделать таблицу соответствия её CAS/source-version решениям, чтобы не реализовать одно и то же повторно; текущая очередь PLAN.md §2 и уже подготовленные исправления сохраняются.
- Параллельно проверить гарантии SQLite `FOREIGN KEY`/CAS/ACL, обратимость изменения, устойчивость backup/restore; новые требования не оправдывают удаление работоспособных возможностей интерфейса.

## 4. Как работает ingestion — обязательный контракт M2
1. Сначала безопасно принять оригинал/сообщение и зафиксировать source_id. При сбое распознавания источник не теряется.
2. В пределах приватности и бюджета извлечь типизированные кандидаты (JSON-schema; ни одного произвольного SQL/инструмента из ответа модели). Неизвестное оставить неизвестным.
3. Найти кандидатов objects по ID/имени/алиасам/смыслу. Не объединять по совпадению имени; при неоднозначности запросить уточнение.
4. Найти подходящие claims по subject+predicate+времени+значению. Классифицировать: duplicate, corroboration, additive event, state transition, contradiction, uncertain.
5. Сохранить предложения с доказательствами; показать пакетное подтверждение для существенных изменений, отличать отказ/пропуск. Отклонённый proposal fingerprint препятствует одинаковым повторным вопросам до изменения источника.
6. Атомарно записать утверждения, ссылку на source_segments и memory_operations, проверить связь с текущим объектом и границы доступа. Поставить обновление поискового индекса; индекс никогда не публикует неподтверждённые утверждения.
7. Асинхронная консолидация эпизодов предложением, а не молчаливая правка; при lock/budget/offline очередь возобновляется без повторных дорогостоящих вызовов.

## 5. Временная семантика
- state: «работаю в компании Б с сентября 2025» может предложить закончить старое primary_employer, **только** если правило предиката functional с тем же контекстом, и источник действительно свидетельствует о переходе. Вторую занятость не закрывать; если дата/факт завершения прежней работы неизвестны — сохранить uncertainty и предложить уточнение, не выдумывать срок.
- event: замена свечей в 2023 и 2025 — два отдельных claims с одним predicate и разными occurred_at/интервалами; месячная/годовая точность и длительность не подставляются произвольно. Второе не supersede первое.
- timeless: «Лиза моя сестра» не устаревает без свидетельства смены/ошибки; отрицание относится к тому же периоду и тоже нуждается в источнике.
- valid time != observation/ingestion time: «сегодня узнал, что переехал в июне» сохраняет valid_from в июне, known_from сегодня. Для неопределённых дат required valid_precision.
- Исправление ошибочного утверждения и завершение периода действия — разные операции. Сохранение предшествующей версии и доказательства обязательно.
- Разрешение явного вопроса «что было известно на дату X» по known_*, «что было верно на дату X» по valid_*; не путать их.

## 6. Чтение, контекст и приватность — M3
Режимы: lexical FTS5 (включая русский и алиасы), vector (при доступной локальной модели), entity linking, ограниченный traversal, временной фильтр, сортировка по доказательствам и актуальности. RRF и пороги — параметры eval, не константы «из статьи». Возвращать typed-hit: object/claim/source/segment, snippet, confidence/status, valid interval, evidence locators, privacy decision and missing-index flag. Пользователь видит больше, чем автоматическая облачная LLM. Любой путь через секретный источник закрывается согласно конечной политике; запретить вытекание названия/факта через счетчик, alias или summary.
LLM получает короткое ядро только подтверждённых разрешённых сведений и по требованию выборку с источниками. Не индексировано/не разрешено/не найдено/ошибка поиска — разные состояния. Источник и содержимое транскрипта обрабатываются как недоверенные инструкции.

## 7. Нужен ли новый UI?
**Да, функционально нужен; не полная смена визуального стиля.** Существующая визуальная библиотека, цвета/типографика и Nebula остаются. После стабилизации M1–M3 переработать информационную архитектуру «Памяти», карточки объекта, ленту фактов и событий, просмотр источника/таймкода, предложения связей и разрешение противоречий. Удалить технические поля из обычного редактора, разделы сделать удобной навигацией. Подготовить UX-контракт и референсы/дизайн-систему **перед** UI-кодом. Подробный сценарный план: Plans/MEMORY_ENGINE_UI.md. Старая U2-библиотека — совместимый референс, но не гарантия готовности будущих графовых сценариев. Home composer, сфера и существующие потоки Share не меняются без отдельной причины.

## 8. Backup/restore, reset, удаление
- Шифрованное полное SQLCipher backup с независимым ключом включает все источники, chunks, историю, медиа и связи; индекс можно rebuild. Восстанавливать только после проверки схемы, foreign_key_check, content hashes и отсутствия исходных orphan объектов.
- Старая база v5 содержит лишь тестовые данные; сохранение **не является продуктовым требованием** этой перестройки. Однако новый APK не стирает локальные данные без предупреждения и явного выбора (сброс тестовой памяти / отмена); не затрагивает старые файлы до успешной новой инициализации. Для не-тестового профиля — безопасный отказ от необратимого обновления.
- До смены хранилища сохранить рабочий чат/ключи/вложения на этапе PR; выполнить offline unit integration, restore, на Android реальное шифрование, MIME и lifecycle; отключение старого schema-layer после проверки всех вызовов.
- Удаление данных снимает индексы и связанные доказательства; пользователь видит, что экспортированные ранее бэкапы не очищаются.

## 10. Эталонные тесты для M1–M3 (обязательные, без онлайн-зависимости)
- ID01: «моя сестра Лиза» + аудиофайл с упоминанием Лизы + вопрос «найди разговор с моей сестрой»: подтверждённое участие не выводится из простого mention; подходящий сегмент обнаруживается, неопределённость видна.
- ID02: «Лиза» и другая «Елизавета» с совпадающим именем: не сливать без независимого evidence.
- TIME01: нынешний работодатель Б с сентября, прежний А до сентября, вопрос «где работал в июле» => А; вопрос «что ты знал в августе» использует known-time.
- TIME02: замена свечей в 2023 и 2025 => оба события, ни одно не закрыто.
- CONF01: два противоречащих документа о двигателе 1,6 / 1,8 => disputed, ни один не перезаписан тихо; обе цитаты доступны.
- SOURCE01: поиск цитаты из аудио/видео с таймкодом, после ошибок ASR оригинал сохранён.
- PRIV01: секретный документ порождает факт/alias/индекс; облачный assistant его не видит даже через связанную открытую заметку.
- DELETE01: удаление объекта/отзыв согласия => ссылки, кэш и векторы убраны; из старого backup явно предупреждается о восстановлении.
- INDEX01: изменение факта во время вычисления embedding => устаревший вектор отклонён; другая модель/fingerprint => rebuild.
- FAIL01: crash на записи связей/вложений и почти заполненный диск => транзакционный rollback; restore реальной зашифрованной копии.
- UX01: редактор и «показать источник» доступны из карточки; длинное название, 320dp, крупный шрифт, TalkBack, отмена диалога без потери сохранённого.

Метрики: recall@5/@10, MRR/nDCG, false positive on no-answer, точность entity-resolution/temporal interval, source attribution, p50/p95 latency, RAM/нагрев/батарея на 100/1000/10000 элементов. Зафиксировать версию fixture и движков; «неизвестно» не считать провалом автоматически и не считать успехом без нужного evidence.
