## CHAT-CONTEXT · утверждённая модель организации тем и диалогов (07.11.2026)

**Решение владельца:** тема беседы и её раздел определяются **самой LLM в основном инструментальном ходе**, в том числе после прикрепления файла в чат, а не отдельным regex/хэштег-роутером. При первом определении и реальной смене темы приложение показывает короткую строку **под ответом**; если раздел изменился, явно показывает «Раздел изменён: старый → новый». При обычном уточнении не создаётся новый сегмент. Пользователь может исправить классификацию свободным текстом (тот же LLM tool) или закрепить/открепить раздел через компактную кнопку. Заголовок диалога соответствует актуальной теме; поисковый индекс истории учитывает **все** прежние темы/разделы, а не только последнюю. Перейти к исторической ветке можно из результатов поиска; точный переход к исходному сообщению — отдельный UI gate, нельзя объявлять реализованным лишь наличием текстового поиска.

**Контракт данных:** `ConversationContext` = `{topic, sectionSlug|null, pinned}`; `ContextChange` — запись на ответе с прежней и новой темой/разделом, именами разделов, краткой причиной и временем. Содержатся только в прежнем `direct_conversations.snapshot_json` через `conversations.ts` / `chat-store.ts`; сохранение единым шифрованным snapshot. Старые `ChatRow` без полей читаются неизменными, malformed context отбрасывается без потери сообщений, при повреждении поля нельзя переписывать источник. Никакой миграции SQLCipher, второй таблицы тегов, отдельной статистики или background classification.

**Контракт модели:** один `set_conversation_context` в уже существующем `tool-catalog.ts`, только при обычной отправке/продолжении диалога. Строгие поля `topic` (2–80 символов), `sectionSlug` (только существующий, не `documents`, либо null), `reason` (2–180). Ответ инструмента — **не утверждение, что уже сохранено**. Приложение повторно проверяет раздел и pinned-состояние, сохраняет метаданные вместе с ответом, после успешного commit показывает статус; при отказе/Stop/неполном ответе не объявляет смену раздела. Ни один раздел диалога **не является** правами заметки и не даёт автоматического перемещения, экспорта или передачи файла внешнему провайдеру. Публичный текст/вложение остаётся недоверенным содержимым; системная инструкция классификации выше текста источника. Фоновые/изолированные служебные LLM-вызовы, подготовка многосегментного документа и разовые преобразования текста не могут незаметно менять текущую тему или тратить дополнительное обращение.

**Граница импортов:** загрузка **в чат** классифицируется тем же LLM-ходом только по реально доступному/прочитанному содержимому и собственному тексту пользователя. Автоклассификация **отдельного** Android Share → «В память» не должна раскрывать защищённое содержимое `Входящих` удалённой модели ради тега. При отсутствии разрешённой локальной/провайдерской обработки оставить «Входящие», доступен прямой ручной выбор и ограниченная read-only подсказка #413; полноценный отдельный проверяемый LLM-импорт — следующий узкий пакет с explicit consent/ACL и тестом реальной сети. Сохранять ту же `saveMediaNote`, не создавать второй импортёр/писатель. Если класс определить нельзя — не угадывать.

**C0-A / C3-B:** REUSE старого `direct-agent` runtime/tool loop, `memory_collections` (только идентичность раздела), `direct_conversations` и сохранённого поиска истории. Запрещены параллельный регистратор тем, массовое переназначение прошлых заметок, неотменяемые фоновые операции и копия поиска. **Приёмка:** 0/1/3 темы в одном диалоге, первые ответ/загрузка фото или PDF/уточнение/коррекция/закрепление/смена/открепление, поиск старых тем и фильтр всех прежних разделов, lock/retry, конфликт прав и исчезнувший раздел, ошибка/отказ LLM, чтение старых snapshot, export/restore, быстрый UI на малом экране, OpenAI/Anthropic-compatible, реальные настройки лимита вызовов; физический Vivo отдельно. **Текущая реализация:** PR #415, required CI/physical проверять по итоговому SHA, не объявлять DONE до доказательств.

## 9T2 · Первая проверяемая операция (PR #404, CI SUCCESS, СЛИТО В MAIN)

**Вертикаль:** пользователь пишет в обычном чате «Перенеси заметку про лазанью в Рецепты». LLM сама вызывает `search_local_notes` или `list_local_notes`, затем `propose_move_local_note({noteId,expectedVersion,targetSectionSlug,reason})`. Каталог отказывает для выдуманных ID/версий, требует текущий разрешённый handle, не даёт модели ни `changeNotes`, ни `undoNotes` как tool. Проверенный preview берётся в одной SQLCipher-транзакции только для активной `domain='notes'` записи обычной приватности, при существующем стандартном целевом разделе. Новые разделы, Документы, приватные/секретные записи, архив/корзина и повторный перенос не входят в этот первый slice. Источник и цель отображаются вместе с названием, причиной, количеством вложений и объяснением того, что копии/слияния/удаления не происходит.

В чате рядом с ответом появляется карточка «Подтвердить перенос» / «Отмена» — сохраняется **только** внутри существующей SQLCipher истории `ChatRow.moveProposal`, а не в новой таблице фактов. Нажатие «Подтвердить» вызывает `changeNotes('move')` с CAS expected record_version и дополнительными source/target collection ACL/status guards **внутри его исходной BEGIN IMMEDIATE-транзакции**. Реальный batch из `memory_revisions` сохраняется в `ChatRow.moveReceipt`; кнопка «Отменить перенос» использует `undoNotes` и повторно проверяет версии и обе коллекции. Отмена предложения — лишь изменение истории чата. При lock/смене прав/версии модель не может протащить запись через ограничение или заявить успешный перенос. Фоновое автоизменение отсутствует.

**Приёмка:** 0 результатов не даёт предложения; один найденный и версионированный — preview; выдуманный ID, другая версия, неверная цель, приватная/архивная запись — отказ без SQL UPDATE; подтверждение → одна ревизия + индексация, payload и attachments сохраняются; undo → вторая ревизия, исходный раздел восстановлен; конфликт перед подтверждением и undo — fail-closed; AppLock — отказ; перезапуск чата — предложение/receipt валидируются; реальный Vivo `NOT_RUN_PHYSICAL`, live paid LLM `NOT_RUN`. **C0-A**: canonical reader и writer, одна SQLCipher история; **C3-B**: нет второго LLM runtime, новой таблицы, shadow writer, автоматического переноса или обхода ACL.

**Оставлено на более поздний пакет O2/O3:** пакетный перенос, выбор нового раздела, изменение раздела прямо на карточке, необязательные теги, дубликаты/merge, специализированный UX для приватных записей. Для первого безопасного действия выбран только перенос одной активной обычной заметки между двумя уже существующими стандартными разделами.

## 1. Пользовательский результат

Из **обычного чата** человек просит: «Разложи эти заметки по темам», «Предложи разделы для новых статей», «Найди дубликаты сохранённых ссылок», «Объедини два одинаковых сохранения, не потеряв комментарии». Ассистент показывает **обоснованные предложения и предварительный результат**, а изменения выполняет только после явного подтверждения. Отмена ничего не меняет. Дополнительная экранная форма не требуется; при необходимости используется существующий выбор записей и компактный просмотр последствий.

- **№18 — распределение:** на основе названия, источника, типа материала, содержимого и необязательных пользовательских тегов *предложить* существующую коллекцию. По умолчанию — действующий раздел заметок, для будущего импорта MSG — «Входящие», если он существует; не создавать второй механизм маршрутизации.
- **№56 — организация:** предложить существующий или новый раздел, необязательные теги, пакетное применение к выбранным записям; не навязывать дерево папок/шаблоны, не перемещать записи скрыто и не переводить чувствительный объект в менее защищённый раздел.
- **№20 — повторы и конфликтующие сведения:** отличать exact duplicate одного URL/вложения от похожей статьи, другой редакции, нового события, иной пользовательской заметки или конкурирующего факта. Для возможного дубля показать причины совпадения и все затронутые записи. «Оставить обе» всегда доступно; автоматического слияния нет.

## 2. Единый контракт proposal → preview → confirm/undo

1. **Сбор (read-only).** Из чата/выделения запросить кандидатов через уже действующие search/reader SQLCipher, с теми же lock, profile, sensitivity, ACL и границами выдачи. Предложение содержит `proposal_id`, `kind` (`suggest_collection|suggest_tags|duplicate_candidate`), `target_ids`, `expected_record_versions`, причину, provenance/evidence и рекомендуемое действие. Идентификаторы и версии сверяются с источником; это **не новый постоянный fact store**.
2. **Предпросмотр.** Вывести заголовки, исходный и целевой раздел, тип/приватность, теги, вложения, авторский комментарий и связанные источники; сравнение «до/после», что изменится для поиска, что останется доступным, последствия для связей/версий и возможность Undo. Не выдавать сходство текста за подтверждённый дубль.
3. **Решение.** `Подтвердить`, `Изменить раздел`, `Не объединять`, `Пропустить`, `Отмена`. Отдельное подтверждение для каждого неоднозначного объединения; для безопасного переноса/тегов разрешено пакетное подтверждение с видимым количеством. Никаких необратимых действий без самостоятельного подтверждения.
4. **Запись.** Использовать **только существующий канонический writer** `local-memory/note-actions.ts` / `repository.ts` с транзакцией, ожидаемой версией, повторной проверкой профиля, collection ACL и статуса непосредственно перед commit. Не обходить `memory_revisions`, индексы или существующий `undoNotes`. При конфликте CAS перечитать и предложить повторный просмотр; никакой частичной тихой записи.
5. **Отмена/проверка.** После записи показать фактический итог и доступную **действительную** отмену; после отмены и восстановления проверить повторный поиск, исходные вложения, отношения и историю. Если текущий writer не может сохранить исходники или undo для данного типа операции, **не подключать действие**, пока не будет безопасного расширения и теста.

**Особенность merge:** существующий `changeNotes('merge')` переводит остальные записи в `superseded`, переносит вложения и записывает `merged_sources`. До подключения его из диалога необходимы тесты сохранности *всех* комментариев/прикреплённых файлов, истории и undo, включая ссылки на старые ID. Для непроверенных случаев допустим **только предпросмотр** либо создание отдельного конспекта по №73 с сохранением оригиналов; не объявлять это фактическим слиянием.

## 3. Границы и безопасность

- Единая память: `memory_entities`, `memory_collections`, ревизии, существующие отношения/источники и производные FTS/векторы. **Никаких** новых таблиц заметок/тегов/дублей, второго writer/RAG или отдельного «интеллектуального сортировщика».
- Теги, если они отсутствуют в существующей схеме, до отдельного технически обоснованного расширения остаются **предложением/совместимыми метаданными**. Не использовать переименование раздела как имитацию тегов и не писать в произвольные поля `payload` без согласованного контракта индекса/backup.
- Модели доступны только для разрешённого содержимого; private/sensitive/secret, закрытые коллекции и «Документы» не передавать внешней LLM. Для таких записей — ручной выбор или разрешённый локальный путь. Вычисленный fingerprint и результаты поиска не утекут при смене профиля/блокировке.
- Не смешивать с №79 (ревизия, архив/корзина/постоянное удаление), №72/73 (истинность временных фактов), №65/66 (политика актуализации), автоматической фоновой чисткой или MSG-6 (входящие и транспорт импорта). Новое событие с той же темой **не** удаляемый дубль.
- Никаких автоматических переносов, удаления, слияния, подтверждения фактов, подписки и платного фонового анализа; пользователь управляет каждым изменением через чат.

## 5. Приёмка

Человек через чат получает предложение раздела и пояснение, может исправить его, отказаться либо подтвердить; после подтверждения запись находят в новом разделе и поиске. Два одинаковых URL с разными пользовательскими комментариями показывают все оригиналы, а разные события не объединяются. Изменение между preview/confirm приводит к отказу без потери. Все фактические изменения обратимы настолько, насколько это подтверждено тестами; отсутствие безопасного Undo блокирует merge. Лок/закрытая коллекция не раскрывается и не записывается обходным путём. Test evidence отдельно: Jest/SQL/Android CI exact SHA; физическая проверка Vivo — только по факту.

**После O3:** идти к утверждённому [MSG-0/1/2/6](MESSENGER_IMPORT_NO_N8N.md). MSG использует те же коллекции, предложения и защитные правила, но сохраняет материал **только по подтверждению**, без нового хранилища.
