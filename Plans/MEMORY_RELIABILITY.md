# Память на годы: исполнительный подплан

26.10.2026 · **план, реализация открыта**. Единственный порядок работ — [PLAN.md, раздел 2](../PLAN.md#2-что-делаем-дальше--единственная-рабочая-очередь), ред. 75. Подпункты используют существующие номера; не создают новые постоянные задачи сверх 1–91.

Основания: [аудит M01–M19](../docs/architecture/MEMORY_RETRIEVAL_AUDIT_2026-10-26.md), [воспроизведения](../docs/architecture/MEMORY_AUDIT_EVIDENCE_2026-10-26.md), [временная модель](TEMPORAL_MEMORY.md), [связи](RELATIONAL_MEMORY.md). Аудит кода выполнен на main `b1a2b3b`; temporal/relational документы — проект, а не результаты внедрения. При продолжении сначала сверить main/PR.

## 1. Результат для пользователя

Сохранённое находится по содержанию, датам, людям и исходникам; агент может прочитать доказательство и показать его место. Повторные события не стирают историю, новые состояния вызывают понятные предложения, родство помогает найти беседу. Приложение показывает неполную обработку, выдерживает рост данных и даёт проверяемый путь переноса/восстановления.

SQLCipher, локальность, существующие IDs/оригиналы/ревизии остаются основой. Индекс, краткое содержание и вывод модели — производные, а не единственная копия знания. UI и внешний агент имеют разные права, но используют согласованный поисковый контракт. Собственный сервер не нужен для этих пакетов.

## 2. Малые пакеты и критерии выхода

### №66.1 — актуальность enrichment (M10)

**Реализовано в технической ветке, не в main.** [Контракт и тесты](../openspec/changes/memory-enrichment-snapshot/proposal.md), [журнал](../docs/architecture/MEMORY_TECHNICAL_PROGRESS_2026-10-26.md). №54а ниже остаётся отдельным пакетом. Исходный сценарий: текст «библиотекарь» изменён на «программист», пока LLM готовит индексные слова. До исправления результат старого текста мог получить новую дату и считаться актуальным.

- Читать входную версию/хеш и релевантные права до обработки; проверять их снова **атомарно при записи** terms/derived relations. Поздний ответ старой версии не коммитится. Изменившийся источник ставится в повторную обработку, а не бесконечно повторяется внутри запроса пользователя.
- Сохранение пользовательского текста не ждёт LLM; lock, смена профиля, удаление/merge и смена sensitivity аннулируют неприменимый результат. Повторный запуск идемпотентен.
- Проверить контракт обрабатываемых полей отдельно: исправление гонки не должно молча включить новые виды данных во внешний запрос. Поддержка `extracted_text` — с разрешением этого источника и его revision.
- №54а: видимый режим/провайдер, пауза/лимит текущего enrichment. Согласие обычных разделов уже было; не просить его повторно, но не расширять автоматически на файлы/secret/новые платные задачи.

**Готово:** поведенческие тесты воспроизводят edit-in-flight, delete/lock/profile/ACL change, повтор и отказ записи; поздний результат не меняет актуальные terms/relations. Исторический probe из аудита не становится тестом, требующим сохранения дефекта.

### №63а.1 — совместимые запись, экспорт и восстановление (M08/M18)

Сейчас создание корпуса не согласовано с ограничением backup 2 GiB и restore 100k entities; проверка размера может происходить уже после создания/копирования. Это задача надёжности, а не просьба владельцу выполнить отложенный restore.

- Определить поддерживаемый путь для уже существующей базы и будущих записей: preflight места/предела, оценка временных копий, проверяемый экспорт, понятный отказ до изменения источника. Не обрезать память и не просто поднять константу.
- Сначала специфицировать минимальное исправление; если большой архив не помещается в текущий формат, не притворяться, что он восстановим. Потоковый/сегментированный формат — отдельный следующий PR по измерениям, с проверкой перехода старого формата.
- Manifest/контроль целостности и версии, неправильный ключ, обрыв, отсутствие места, старые v1–v5, совместимость оригиналов и receipts. Явно описать, что восстановление требует пустых **коллекций**, а не только списка заметок, и дать безопасный путь отдельной тестовой базы без удаления рабочей.
- Производные индексы можно пересоздать; исходные записи/вложения/связи/решения пользователя не теряются. Обновить restore при появлении новых таблиц claims/relations/proposals.

**Готово:** автоматические проверки граничных размеров/количества и round-trip поддерживаемых схем, отказ без повреждения рабочей базы. Граничные mocks/fixtures не выдавать за реальный многогигабайтный SQLCipher benchmark. Ручной тест владельцем по-прежнему отложен.

### №66.2 — полнота и точность поиска (M02/M03/M05)

- Декларировать searchable projection: title/body, разрешённый extracted text, текст observations, типизированные поля шаблона, имена/типы вложений и source metadata. Каждое поле имеет происхождение и права; произвольный JSON целиком не индексировать.
- Убрать потерю смысла после 120 символов и безусловную потерю дат/отрицаний; сохранить точный режим чисел/фраз/имён. Языковые fallback проверять на русском корпусе, не считать английский Porter решением морфологии.
- Единый контракт query/scope/filters и объяснимые отличия UI и агента. Кандидаты → ранжирование → выбор доказательств; не сводить весь документ к первому короткому фрагменту.
- Фильтры коллекции/вида/даты/источника и status, явный поиск по архиву/истории. Удалённое не обнаруживается в обычной выдаче. «Нет подходящего» отличается от «не проиндексировано/обработка не завершена/нет разрешения».

**Готово:** tests на observations/typed fields/название файла, длинный запрос, фразу с добавочными словами, русский exact/semantic/negative, архив/корзину/ACL и обновление после edit. Метрики публикуются по категориям; mock terms не называются настоящим semantic benchmark.

### №45.1/77.1 — поиск, чтение и проверяемый ответ (M07/M05/M17)

- Минимальные операции: `search_memory`, `read_note/read_chunk`, `read_attachment_metadata/segment`, `list_memory`, `count_memory`. Имена уточнить в OpenSpec; добавить инструмент вместо второй логики поиска.
- Прочитать достаточно источника в пределах бюджета; fetch по stable ID + revision + range/location. Повторная проверка версии/ACL при каждом чтении. Слишком длинный результат возвращает cursor/coverage, а не незаметно выдаёт первый кусок за всё содержимое.
- Доказательство: запись/вложение, версия, цитата или диапазон, страница/таймкод только при наличии. Список найденных кандидатов не выдаётся за список действительно использованных источников. Ошибка/неполнота названа.
- «Все» и «сколько» выполняются list/count с фильтрами и пагинацией; top5 недостаточно. Подсчёт уникальных событий/фактов задаёт единицу счёта, не путает chunks с заметками.
- История чата — отдельный scope с ролями/временем, а не автоматическая биография; ответ ассистента не становится фактом пользователя. Нормализация и lazy load истории — №66.3/65, не обязательная индексация всех чатов первым PR.

**Готово:** вопрос требует двух отдалённых частей длинной заметки, ответ опирается на обе; stale/deleted/secret источник недоступен; полный список проходит несколько страниц; count не зависит от top-k. Не нужен предварительный большой A/B-стенд №50.

### №66.3 — рост, источник и возобновляемая обработка (M04/M06/M09/M13/M14/M16/M18/M19)

Разбивать на отдельные PR по результату, не внедрять весь слой одной миграцией:

1. **Sources/extractions/segments:** stable IDs, версия исходника и модели, вид/язык/coverage/ошибка извлечения, страница/таймкод/диапазон, ручной текст отдельно от OCR/ASR/LLM summary. Вначале текст и текущие originals; структура готова для фото №83, полного ASR №75 и PDF.
2. **Очередь dirty IDs:** задания записаны на диск, batch выбирается SQL LIMIT, статусы и счётчики вычисляются без переноса всего корпуса в JS. Lease/version, bounded retry/backoff, отмена, resume после kill, приоритет поиска пользователя; не удерживать глобальную DB-операцию во время LLM/native inference.
3. **Manifest индекса/модели:** fingerprint весов, runtime/tokenizer/preprocessing, dimension/normalization, version пространства; несовместимые векторы не сравнивать. Миграция индекса отменяема, fallback сохраняется; query не ждёт бесконечно background batch.
4. **Стоимость чтения/истории:** metadata-only cards, индексы под реальные WHERE/ORDER BY, cursor pagination, lazy read бесед/ревизий. Для ранжированного поиска — стабильная search session, не подстановка курсора даты. Замерить snapshot/delta варианты до крупной нормализации.
5. **Repair и lifecycle:** проверки orphan/hash/index/schema, переиндексация без изменения originals, disk preflight миграций, приоритет исходных данных. Содержимое диагностических логов — отдельный управляемый срок/защита, metadata по умолчанию; не пересылать личный корпус в CI.

**Готово перед production №83.2:** source revision и валидные locations, manifest, ограниченные batches и возобновляемый rebuild, удаление/ACL/backup согласованы; профиль 1k/10k без повторного полного переноса каждой пачки. Отдельные дорогие улучшения (ANN, delta history, большой экспорт) принимаются по измерению, не блокируют изолированный 83.1 spike.

WorkManager может сохранять задачи через рестарт, но не открывает закрытую SQLCipher и не снимает ограничения батареи. Сначала durable queue при разблокированном приложении; новая работа с персональными данными вне сессии требует отдельной политики. Скачивание общедоступных весов и перенос готового ciphertext — другой класс операций.

### №72.1–72.3 и №66.4 — утверждения, время, идентичность и связи (M12/M15/M10/M13)

**Общая основа до двух веток UX:** stable claim/entity IDs, source evidence/revisions, review decisions и undo. Не создавать независимые очереди подтверждений для №17/20/56/72/73 и связей. Тип утверждения не равен `kind` всей заметки. Версия схемы назначается при реализации, не резервируется в нескольких документах как v6.

- **72.1:** события/эпизоды, состояния с периодами, наблюдения и устойчивые сведения; valid time и recorded time, точность/неизвестность даты, asserted/planned/negative. [Полная модель](TEMPORAL_MEMORY.md).
- **72.2:** новый факт адресно ищет потенциально конфликтующие состояния; предложение показывает что/почему/с какой даты меняется. Сохранение источника не блокируется, пользователь может оставить оба, поправить даты, отложить/отказаться. CAS и обратимый журнал; не закрывать всю заметку или старое событие.
- **72.3:** current/as-of/history/events/list и проверка достаточности доказательств. Последняя замена свечей вычисляется по дате события, не времени импорта; старый чек не становится последним ремонтом. План и неизвестная дата не превращаются в подтверждённое состояние.
- **66.4:** person/role/participant/about/mentioned/source, reverse lookups и несколько источников одной связи. «Моя сестра» — отношение, не глобальный alias. Явное однозначное заявление используемо; тёзки/ASR/сходство — кандидаты с подтверждением, не автоматическая идентичность. Решения confirmed/rejected/deferred/retracted сохраняются. [Полный контракт и R1–R11/C1–C10](RELATIONAL_MEMORY.md).
- Новая родственница или исправленная расшифровка адресно пересматривает ранее неразрешённые упоминания. При поиске разрешён bounded переход по доказанным связям и fallback; не нужен полный граф всех попарных сходств, Neo4j или повтор всех LLM-вызовов.

**Готово:** temporal acceptance из спецификации и relational R1–R11/C1–C10 превращены в регрессии по мере реализации; голосовое редактирование и LLM-правка проходят тот же жизненный цикл. Отдельно: несколько работ/адресов/сестёр, correction vs transition, поздний источник, отказ без повторного навязывания, merge/delete, профиль/ACL, undo/restore решений. Спецификация сама тест не заменяет.

### №60б/75/83/85 — форматы и мультимодальность

Повторно не реализовывать многовложенность №84 и Share №61в. [83.0–83.6](LOCAL_MULTIMODAL_AI.md) сохраняются: сначала изолированный native spike и фото, далее видео/аудио. PDF text/OCR, HTML body, полные ASR-сегменты, повтор извлечения и исправление распознанного текста используют один source/segment слой. Не обещать поддержку PDF/аудио в чат-транспорте лишь потому, что память хранит оригинал.

Контрольные сценарии: автомобиль без caption → похожее фото с различением экземпляра; беседа с сестрой → реальное аудио; точная фраза → настоящий таймкод; статья → основной текст и URL; ошибка одного из нескольких файлов → честное coverage и сохранность остальных. Права на облачную обработку исходника не выводятся из права хранить его локально.

### №63б/65/66/79 — дальнейшая долговечность

- Периодические копии/retention только после выбранного расписания и политики; восстановление всегда проверяемо. Не выдавать backup за live sync двух устройств. Переносимый экспорт нужен, чтобы данные не зависели от единственной версии приложения.
- Merge сохраняет источники/связи/aliases, combined media limits и возможность undo; семантическая похожесть — предложение, точный повтор источника — idempotency. Один и тот же ремонт и два похожих ремонта не одно и то же.
- Раздельные политики истории, чатов, индексов и временных/диагностических файлов. Ограничивать размер/пагинацию и проводить repair, не молча удалять пользовательские оригиналы ради скорости.
- «Удалить сведения о X»: сначала показать места/категории/неполный охват, выбор, мягкое удаление с ограниченным undo; финальное удаление отдельно. Из памяти, индекса и разрешённого контекста удалённое исключается сразу. Старые выгруженные копии и внешние сообщения приложение не может гарантированно стереть. Не обещать одновременно окончательное удаление и бессрочную отмену.

## 4. Что не внедряем заранее

Не менять SQLCipher на серверную базу ради гипотетического миллиона записей. Не вводить одновременно общий графовый движок, новый embedding runtime, live sync и массовую миграцию личных фактов. Не считать число cosine вероятностью личности/истины. Не сканировать все пары фактов LLM после каждого сохранения. Не требовать вручную заполнить технические поля для каждой заметки. Не блокировать сохранение источника ожиданием анализа.

Следующие опции открываются **по доказанной проблеме**: native vector extension/ANN — если текущий поиск не укладывается в измеренный бюджет; отдельное зашифрованное blob-хранилище — если SQLCipher originals мешают проверяемым операциям; дополнительная инфраструктура/sync — при отдельном запросе, контракте конфликтов и модели ключей. Обещание «максимальной точности» заменяется measured recall, precision, полнотой доказательств и честным отказом при неопределённости.

## 5. Проверки и контрольная точка

Синтетические fixtures не содержат личных данных пользователя. Начать с расширения существующего небольшого корпуса: граничные/отрицательные примеры, source revision, dates/relations, privacy. Для больших объёмов — воспроизводимый генератор и 1k → 10k → 100k по отдельным ступеням; последняя ступень не означает уже подтверждённую поддержку.
