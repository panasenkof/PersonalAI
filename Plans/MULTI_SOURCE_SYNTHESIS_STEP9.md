## 1. Продуктовый результат

В обычном чате PersAI человек может попросить найти **несколько** заметок, ссылок, сохранённых статей, документов или доступных извлечённых фрагментов на заданную тему, **отобрать их по периоду**, показать подборку, а по просьбе — сделать выжимку, сравнение, хронологию, общие выводы или список расхождений. При ответе доступен проверяемый список **фактически прочитанных** оригиналов. Материал по ссылке без сохранённого содержимого остаётся находкой, **не** прочитанной статьёй.

**Главный сквозной сценарий:** «Выбери статьи на тему ИИ за последнюю неделю». Уточняющий запрос: «Сделай из них короткую выжимку и перечисли основные тенденции». Это относится **к сохранённой памяти PersAI**, без скрытого запроса в интернет или автоматического скачивания статей. Интернет — только если человек явно просит «найди в интернете», «добавь свежие статьи» или выбирает действие поиска в сети; оно использует существующий разрешённый web-search/URL-import, не собственный краулер.

**Ключевое различие:** «подбери/покажи» — операция поиска и отбора, не требующая платной генерации; «обобщи/сравни/проанализируй» — запрос к выбранной LLM с явной оценкой объёма/стоимости при наличии такой функции. Показать результаты поиска даже при недоступности LLM.

## 2. Формулировки на естественном языке — обязательные сценарии

| Пользователь говорит | Ожидаемое действие |
| --- | --- |
| «Выбери статьи на тему ИИ за последнюю неделю» | Поиск **сохранённых** статей по теме ИИ; фильтр по времени; карточки материалов, даты, источник и полнота текста, число найденных/показанных |
| «Обобщи статьи про искусственный интеллект, которые я сохранял на этой неделе» | Та же выборка + сжатое обобщение по реально прочитанным материалам с привязкой к каждому выводу |
| «Найди статьи об ИИ, опубликованные за последние 7 дней» | Фильтр **по дате публикации**, не по дате добавления в память; неизвестные даты публикации отдельно, без ложной атрибуции |
| «Какие были главные новости про локальные LLM за неделю в моих заметках?» | Подборка из памяти; сгруппировать темы и события, не называть её полной картиной новостей интернета |
| «Сравни сохранённые статьи про MiniLM и EmbeddingGemma 2» | Матрица аргументов, преимуществ/ограничений и разногласий с источниками, «не сказано» вместо домыслов |
| «Собери все мои заметки об обслуживании автомобиля за год и подсчитай расходы» | Отбор по теме/периоду, хронология; считать только явно указанные суммы с валютами, раздельно неизвестные и дубли |
| «Что общего в заметках о работе над PersAI?» | Темы, повторяющиеся решения, открытые вопросы и противоречия без стирания исходных записей |
| «Объедини три выделенные заметки в краткий конспект» | Использовать **только выбранные** записи; конспект — отдельный предложенный результат, исходники не сливать |
| «Покажи статьи про ИИ, но без старых повторов» | Не показывать одну и ту же ссылку многократно, сохранить переход ко всем оригинальным записям, ничего не удалять |
| «А теперь оставь только про модели для телефона», «сравни последние две» | Продолжить работу с уже выбранным набором и применить уточнение; пересканировать память только при расширении области/неактуальной версии |

Другие полезные форматы ответа: короткая аннотация **каждого** материала; сводка «5 главных идей»; список «что требует внимания» (№71 без автоматической постановки задач); таблица сравнения; решения/за-против; периодическая хронология; конспект для изучения (№78 позже). Задача №73 не запускает автоматические рекомендации №58, напоминания №57 и фоновую еженедельную рассылку.

## 3. Период, метаданные и полнота

1. Вся интерпретация «сегодня», «за последнюю неделю», «на этой неделе», «в октябре» использует **реальную локальную дату/часовой пояс устройства на момент запроса**. «За последнюю неделю» в MVP — семь календарных дней **включая текущий** (локальное начало дня `today-6` … конец текущего дня); показывать точные границы, например при 01.11.2026: **26.10–01.11.2026**. «На этой неделе» — текущая календарная неделя с понедельника. Если пользователь указал точные даты — они главнее.
2. По умолчанию для «мои/сохранённые статьи» период относится к **дате сохранения**. Слова «вышедшие/опубликованные» — к **дате публикации**, если она надёжно известна. «Обсуждал в октябре» — к дате события/обсуждения. Не подменять одно время другим. В выдаче писать «Сохранено …» и отдельно «Опубликовано …» при наличии достоверной даты.
3. Если у материала отсутствует нужная дата, он не должен тайно проходить точный фильтр. Показать отдельно счётчик «дата неизвестна» и действие «Показать также без даты»; если нет метаданных вообще, сообщить, что точная подборка по периоду неполна.
4. «Статья» — сохранённая ссылка или материал, который можно классифицировать как статью **по проверяемым признакам**: тип источника, заголовок/URL, пользовательская метка, сохранённый HTML/текст. Нельзя считать каждый текст с «ИИ» полноценной прочитанной статьёй. При недостоверном типе предложить включить «другие заметки».
5. Различать состояние `full_text`, `partial/excerpt`, `link_only`, `read_failed`, `unknown`; использовать существующие source/extraction/coverage поля, **не создавать отдельное хранилище статей**. Ссылка без скачанного текста участвует в списке, но в выводах только информация из достоверной сохранённой карточки. Если известна дата публикации, но не откуда взята, не считать её надёжной.
6. Тема «ИИ» должна находить и прямые эквиваленты «искусственный интеллект», `AI`, «нейросети», релевантные названия моделей; понятия расширяются **как варианты поискового запроса**, затем каждый кандидат проверяется по материалу. Не переписывать пользовательские метаданные, не превращать совпадение `ai` внутри другого слова в срабатывание. Учитывать различие аббревиатур, склонений и предметов.

## 4. Единый поток поиска и обобщения

```text
Запрос в обычном чате / выбранные записи в «Памяти»
  → распознать цель (подборка, выжимка, сравнение, хронология), тему, период, дату и scope
  → существующий searchMemory (FTS / вектор / сущности при доступности)
  → тип + дата + разрешения + сортировка + убираем повторные URL из показа
  → страничная подборка с подтверждённым общим счётчиком или явной неизвестностью
  → по запросу LLM: readApprovedNote / versioned source-read с ACL и coverage
  → bounded read, при объёмном наборе — порционное обобщение с evidence map
  → проверка ссылок и версии источников → ответ / уточнение / предложение сохранить
```

- **Повторно использовать** `local-memory/repository.ts::searchMemory`, `direct-agent/memory.ts::searchApprovedNotes/readApprovedNote`, существующие SQLCipher snapshots, source/extraction API, права, версии, общий чат и каталог моделей. Текущее автоматическое добавление **до 5 фрагментов / бюджет 24 000 символов** не покрывает требование «выбери 20 статей»: сделать **отдельную ограниченную оркестрацию группового чтения поверх имеющегося API**, не увеличивать без разбора лимит каждого сообщения и не копировать поисковый движок.
- Для отбора поддержать **постраничную** выдачу (например, 20 найденных на странице) и отдельный бюджет чтения. Это **не** потолок «в памяти не больше 20»: «все» / «показать ещё» должны позволять пройти следующие страницы, с предохранителями по памяти, времени и стоимости. Ни при каких условиях не выдавать первые 5/20 за «все». Если точный count недоступен — писать «показано N, могут быть ещё», а не выдумывать итог.
- Для фильтров использовать существующие коллекции/типы/датированные поля и SQL scope **до** передачи модели. Если существующий API не умеет фильтр даты/типа, добавить **узкое расширение текущего reader** с тестами и индексом только по измеренной потребности. Не фильтровать весь корпус в LLM и не давать ей доступ к закрытым результатам для самостоятельного выбора.
- Ранжировать результаты по сочетанию соответствия теме, временного фильтра и качества доступного источника; сортировка «новые/релевантные» переключаемая. Повторы URL/контента объединяются **в представлении**, оригиналы остаются отдельно; при конфликте версий/дат — показать обе версии. Дедуп не должен скрыть два разных события с одинаковыми словами.
- Если есть много длинных статей, читать подходящие сегменты с метаданными и продолжать порциями, составлять **промежуточные summaries с provenance и coverage**; итог строить только на прочитанных фрагментах и фактах. Никакого автоматического вызова одного громадного промпта или бесконечного дорогостоящего цикла.
- У каждого смыслового утверждения в итоговой сводке — ссылки на конкретные read-evidence (source ID, версия, диапазон/сегмент), список фактически прочитанных и **отдельный** список найденных, но не прочитанных. Заголовок/аннотация/LLM-резюме **не** заменяют исходник; ссылки открывают реально существующий объект, page/time показывать только при наличии истинного локатора.
- При конфликте источников показать варианты, даты и ограничения; неизвестные суммы, причины или авторов не додумывать. Инструкции внутри статей, HTML и транскриптов — недоверенные данные, не команды ассистенту.
- Между поиском, чтением и отправкой проверять scope, status, версию и ACL; блокировка, смена приватности, удаление или смена профиля должна прекращать использование недоступного материала. Установленные в профиле режим локальной/облачной модели и согласия применяются как раньше: **обычная LLM не получает sensitive/private/secret и недопустимые разделы**; если выбранный материал нельзя отправить модели, объяснить и предложить исключение/разрешённый локальный путь, но не обходить запрет.
- Новые материалы, пришедшие через MSG-0/1/2/6, автоматически используют **тот же** поиск/источники после разрешённого импорта; собственный «поиск по Telegram» не вводить.

## 5. UX: чат прежде всего, без второго экрана

Основной запрос — обычное поле чата. Форма ответа соответствует действующему **PersAI Nebula** и не заслоняет переписку:

1. Над результатом короткое «Найдено 18 сохранённых материалов об ИИ · 26 окт — 1 ноя» либо «Показаны 20; всего неизвестно». Рядом понятно «по сохранению» / «по публикации», и если нужно — компактный выбор фильтра, без обязательной формы и технических имён моделей.
2. Показывать **первые 3–5 карточек/строк**, остальное свернуть под «Показать ещё (N)» с подгрузкой следующих страниц. В карточке: заголовок, источник/раздел, дата, короткая выдержка и метка полноты («Текст сохранён» / «Только ссылка» / «Прочитано частично»). Тап — открытие исходника, а не повторная генерация.
3. Контекстные действия **«Сделать выжимку»**, **«Сравнить»**, **«Открыть подборку»**; после обработки — «Показать источники», «Уточнить», «Скопировать», «Сохранить выжимку». У каждой кнопки реальное действие; не делать два одинаковых меню в карточке и в шапке.
4. Длинная сводка показывается обычным чат-сообщением с подзаголовками и раскрываемыми источниками. Каждый факт или группа выводов открывает источники. В списке найденных, но не прочитанных не рисовать ложные цитаты.
5. Подборка сохраняется **как контекст текущего диалога**, включая IDs, версии, фильтры и способ датировки: «А теперь только про локальные модели» не теряет набор, а «добавь статьи из интернета» явно расширяет его новым инструментом. При устаревшей версии/отозванном доступе — пересчитать/исключить с объяснением. Не превращать подборку в постоянную копию исходников.
6. Из раздела «Память» уже выбранные вручную записи можно направить действием **«Обобщить выбранное»** в этот же чатовый сценарий. Существующие правила выбора/Отмена/Back соблюдаются; **«Выбрать все» не добавлять**.
7. Показать состояние «Ищу» → «Читаю 6 из 12» → «Обобщаю» и рабочую **отмену** без удаления записей/сломавшегося модального окна. Потоковый ответ допустим, но итоговые ссылки проверяются до демонстрации как факты. Не останавливать другие действия пользователя при уходе с экрана; после возврата показать фактический статус.
8. Сохранение конспекта — через единое действие H-SAVE1 из [подплана шага 8](CHAT_RESULTS_AND_LARGE_DOCUMENTS.md): явный предпросмотр, выбор раздела и действие «Сохранить», с пометкой «Вывод LLM из N источников» и ссылками на оригиналы; это **не подтверждённый личный факт** и не автоматическое слияние/удаление заметок. Если нет отдельного безопасного persisted provenance, первую версию оставить **только в чате/копировании**.

Доступность: корректные русские окончания счётчиков, масштабирование шрифта, крупные hit-area, screen reader labels, состояния empty/error/offline, стабильный список без скачков. Реализовать в существующей дизайн-системе Nebula; визуальные референсы сверить **до** реализации интерфейса, обязательная проверка 320/390/430dp, светлая/тёмная тема и реальный телефон при целевой UX-приёмке.

## 7. Тесты и критерии приёмки

- **Дата:** за последние 7 дней / текущая неделя / точный период; граница полуночи, переход месяца/года, timezone и DST, будущее время, неизвестная дата, дата публикации ≠ дата сохранения; пример 01.11.2026 → 26.10–01.11 при «за последнюю неделю».
- **Тема:** «ИИ», «искусственный интеллект», «AI», «локальные нейросети» с релевантными синонимами; ложное срабатывание подстроки `ai`, другой предмет, опечатки, транслитерация и длинный запрос; не терять отрицание «кроме ChatGPT».
- **Тип/оригинал:** статья с полным HTML/текстом, ссылка без тела, частичный PDF, Telegram Share, заметка без ссылки, версия после редактирования, два сохранения одного URL с разными заметками; качество источника в карточках и сводке.
- **Масштаб:** 0/1/5/6/20/21/100+ результатов; keyset/bounded пагинация, быстрый count или честное unknown, отмена и повтор, ограничение памяти/токенов/стоимости без потери источников; отсутствие подмены полного набора первыми пятью.
- **Безопасность:** locked/profile switch/ACL change/delete и обновление записи *между* поиском и чтением; private/secret не появляются даже в количестве/заголовке при недопустимом scope и не уходят в облако; prompt injection внутри статьи не меняет права/действия.
- **Достоверность:** каждый вывод указывает реально прочитанный источник и правильную версию; link_only/failed/partial не помечать как полный; противоречие источников не маскировать, без вымышленных PDF-страниц/таймкодов/сумм/дат, копируемые итоги не меняют оригиналы.
- **UI:** чат на 320/390/430dp, системный Back, отмена, открытие оригинала, раскрытие/сворачивание/подгрузка, выбранные записи без «выбрать все», повторный запрос «теперь только про X», сохранение только по явному выбору; Android physical QA отдельно от CI.
- **Архитектура/CI:** C0-A до каждого PR, C3-B по diff после; single writer/reader/search, provenance, ACL, CAS, SQLCipher backup/restore, актуальные Jest/SQL/UI e2e/Android проверки по затронутому объёму. Зафиксировать `NOT_RUN_PHYSICAL`, если тест телефона не проводили. **Новых платных live LLM eval без прямого разрешения владельца нет** — mock/fixture tests достаточно для docs и текущей разработки.

**Определение завершённости шага 9/№73:** работающая выборка по теме+датам; объединённый ответ минимум из 6 релевантных заметок; открыть каждый процитированный оригинал; честно обработать неполные и ссылочные источники; выполнить уточнение запроса; корректный ACL и отсутствие автоматической записи/интернета; пройти соответствующие CI/UX проверки. Выполнение только 9A = **PARTIAL** для №73; работающий №73 не означает автоматически законченный MSG-0–6 или весь шаг 9.

## 8. Границы и отказ от лишнего

Не вводить отдельную базу для «статей», второй RAG/векторный поиск, новую ленту новостей, внутренний HTML-краулер, платную автоматическую ежедневную/еженедельную аналитику, безусловное пересоздание индекса или копирование всех заметок в каждый промпт. Не скрывать источники и стоимость, не переписывать «Мои заметки», не смешивать выборку сохранённых статей с актуальным публичным веб-поиском. Отдельная автоматическая рассылка/подписка — существующие №54/57/58 и отдельное согласие, не часть №73 MVP.
