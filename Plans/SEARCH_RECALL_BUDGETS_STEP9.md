# Этап 9 — числовые бюджеты поиска и обработки источников

**Актуализация 06.11.2026.** Это контракт качества/ограничений, а не отдельная очередь работ или новая реализация RAG. Источник приоритета — [PLAN.md §2](../PLAN.md), приёмка — [30 сценариев](AGENT_SCENARIO_ACCEPTANCE.md) и A07. Изменения в GitHub — #386–#391 (для каждого кода фактический CI/merge подтверждается отдельно). **Физический Vivo X200 Pro: NOT_RUN** для этих пакетов; без измерений нельзя обещать полный recall или целевые задержки при 50 тыс. записей.

## Для чего разные лимиты

- **Размер одной страницы/вызова:** сохранять ограниченным для CPU, памяти, стоимости LLM и AppLock; показывать пользователю `hasMore`, `nextCursor`, частичный охват. Нельзя превращать одну страницу в утверждение «вся память прочитана».
- **Кандидаты перед ранжированием:** выбирать глубже, чем показываемые первые 5–8; проверять recall на корпусах с известными ID и текстами, а не выбирать магическое число без тестов.
- **Полнота исходника:** 900 символов предварительного фрагмента и 24 тыс. символов общего LLM-контекста не должны блокировать версионированное дочитывание конкретной заметки. Честно сообщать о неполном чтении и об изменениях исходника.
- **Границы безопасности:** стандартные разрешённые разделы для внешней модели, AppLock, одна транзакция с ACL, CAS/version/fingerprint, запрет фонового массового вывода private/secret — **не смягчать** ради recall.

## Оставшиеся проверки, не объявляемые выполненными

1. **A07 relevance/recall:** построить детерминированный корпус `0/1/5/20/100/1000/10k/50k`, известные target IDs, опечатки, неоднозначности, многословный запрос с важной серединой, близкие негативные примеры и устаревшие/секретные версии; измерять recall@5/20, false positives, p50/p95 latency, RAM, время поиска после индексации, холодный/тёплый индекс, результаты при отключённой embedding-модели. Выбирать пороги MiniLM/EmbeddingGemma лишь после замеров.
2. **Много источников:** 100+ статей / извлечённых сегментов и длинная заметка. Пользовательское «все» требует исчерпывающего ACL-фильтра/постраничной обработки, а не только top-100. Модель должна уметь явно назвать количество реально прочитанных и не подменять его общим `count`.
3. **Приёмка на Vivo:** проверить 5001+ фото, 10k–50k записей, длительность/native peak memory и AppLock/cancel; сравнивать качественные метрики до/после на одинаковой модели, источниках, корпусе и версии индекса. UI smoke/эмулятор не равен C2 physical PASS.
4. **Качество вторичной выжимки:** оценивать факты, пропуски, оговорки, числовые значения и противоречия на длинных документах с эталонным ответом. Даже полный обход всех фрагментов и адаптивный бюджет не гарантируют, что summary сохранит каждую деталь.
5. **Разные права:** на каждом новом cursor/странице проверять AppLock, смену профиля, архивирование, удаление и перевод раздела в закрытый; не выдавать устаревшие handles. Не использовать эти read-only возможности для массовых write/delete без отдельного полного scope + user confirmation.

**C0-A/C3-B:** сохраняется один канонический SQLCipher writer/search/extraction path. Эти пакеты меняют бюджет и полноту существующих readers/adapters, не вводят альтернативные индексы, модельный runtime или скрытую внешнюю передачу.
