1. Один пакет = одна ветка = один или несколько маленьких PR; каждый PR — один проверяемый пользовательский результат.
2. Новая возможность помощника = новый инструмент в `mobile/src/direct-agent/tools/` (после ARCH-2) с полем `guidance` (после ARCH-3). Отдельных ответов в обход модели не делать.
3. Любое изменение данных = предложение → подтверждение пользователя → существующий writer → квитанция → отмена. Новый вид предложения добавляется по правилу из ARCH-4 (обработчик в `proposals.ts`).

5. Фоновых платных вызовов модели нет, пока не выполнен пакет 10-1.

## Этап 9 — остаток (после приёмки)

### S9-1 — разбор «Входящих» через чат (№18, №56; сценарий S07)

- **Цель:** фраза «разбери входящие» даёт пачку предложений «заметка → раздел + теги», пользователь подтверждает всё, часть или отклоняет.
- **Зависимости:** ARCH-4 (общий механизм предложений). По решению 12.11.2026 (TG-6) новый импорт из Telegram может сразу идти в обычный раздел; S9-1 нужен для того, что уже лежит во «Входящих» и для «Поделиться».
- **Решение владельца:** «Входящие» закрыты от помощника. Для разбора текст заметок уходит выбранной модели. Нужно явное согласие: разовое на каждую пачку (рекомендуется) или постоянная настройка.
- **Шаг 0:** `direct-agent/tools/proposal-tools.ts` (`propose_import_metadata`, `propose_move_local_note`), `media/import-llm-classifier.ts` (как устроено согласие на передачу текста при импорте, #418), `local-memory/note-actions.ts` (`changeNotes('move')`, `undoNotes`), `direct-agent/move-proposal.ts` (почему перенос ограничен обычными разделами), `local-memory/note-tags.ts`.
- **Контракт:**
  - Инструмент чтения `list_inbox_for_triage(limit ≤ 10, cursor?)` доступен модели **только** в ходе, перед которым пользователь нажал «Разрешить разбор N записей» на карточке согласия в чате. Возвращает идентификатор, версию, заголовок, первые 600 символов текста, существующие теги.
  - Инструмент предложения `propose_inbox_triage(items: [{noteId, expectedVersion, targetSectionSlug, tags ≤ 5, reason}])`, до 10 элементов. Идентификаторы принимаются только из результата чтения этого же хода.
  - Новый вид предложения `inbox_triage`: карточка со списком строк «заголовок → раздел · теги», у каждой строки переключатель; кнопки «Применить выбранные» и «Отклонить».
  - Исполнение: одна транзакция через `changeNotes('move')` для выбранных строк плюс запись тегов через существующий путь правки (`reviseEntity` с проверкой версии). Перенос из «Входящих» в обычный раздел меняет уровень записи на `standard` — это отдельно написано на карточке: «После переноса запись станет доступна помощнику».
  - Квитанция: число перенесённых, кнопка «Отменить» через `undoNotes`.
- **Не делать:** автоматический разбор без подтверждения; создание новых разделов в этой же карточке (для этого есть `propose_create_memory_section`); разбор закрытых разделов кроме «Входящих».
- **Тесты:** согласие не дано — инструмент недоступен; выдуманный идентификатор отклонён; версия изменилась между предложением и подтверждением — строка пропущена с пояснением, остальные применены; частичный выбор; отмена возвращает раздел, уровень и теги; блокировка приложения в середине — ничего не применено.
- **Готово, когда:** сценарий «10 записей из Telegram во „Входящих“ → разбор → 8 подтверждено → помощник находит их» проходит в тесте на настоящей SQLite и записан в долг приёмки.

### S9-2 — дубли и объединение через чат (№20)

- **Цель:** «найди дубли» показывает группы кандидатов и предлагает объединение с предпросмотром.
- **Зависимости:** ARCH-4.
- **Шаг 0:** как сделаны кандидаты точного дубля по адресу (#376; `local-memory/agent-catalog.ts`, поиск по `source_url`), объединение и его отмена (#432; `note-actions.ts` `changeNotes('merge')`), ограничение 12 тегов при объединении.
- **Контракт:**
  - Инструмент чтения `find_duplicate_candidates(kind: "same_url" | "same_text", limit ≤ 10)`: группы по 2–5 записей. `same_url` — существующая выборка; `same_text` — совпадение SHA-256 нормализованного текста (пробелы и регистр), считается на устройстве по обычным разделам, без модели.
  - Инструмент предложения `propose_merge_notes(noteIds, expectedVersions, keepNoteId, reason)` — одна группа за вызов.
  - Вид предложения `merge_notes`: карточка показывает, какая запись остаётся, какие вливаются, сколько вложений и тегов переносится, и фразу «Исходные записи можно вернуть отменой».
  - Исполнение и отмена — только существующие `changeNotes('merge')` и `undoNotes`.
- **Не делать:** объединение «похожих по смыслу»; автоматическое объединение; объединение записей из разных уровней доступа.
- **Тесты:** группа из трёх с вложениями; блокирующий случай «тегов больше 12» показан как причина отказа; отмена восстанавливает все записи; запись изменилась — отказ.

### 10-2 — паспорт возможностей модели и назначение по операциям (№55а)

- **Цель:** для каждого подключения видно, что модель умеет, и можно назначить разные модели на чат и на фоновые операции.
- **Шаг 0:** `direct-agent/settings.ts` (типы подключений, хранение), `check.ts` (`checkConnection`), `attachment-capabilities.ts` (`imageCapability` — образец состояния «не проверено / поддерживается / нет»), `helper-model.ts` (`indexTermsModel` — как сейчас выбирается вспомогательная модель), экран `DirectAgentSettingsScreen.tsx`.
- **Контракт:**
  - Тип `ModelPassport = { tools: Cap; images: Cap; streaming: Cap; checkedAt?: string }`, где `Cap = "supported" | "unsupported" | "unverified"`. Хранится внутри записи подключения (там же, где остальные его настройки; попадает в резервную копию вместе с подключением — проверить по `backup-settings.ts`).
  - Кнопка «Проверить возможности» рядом с существующей «Проверить подключение»: три коротких запроса (вызов одного тестового инструмента; потоковый ответ; изображение 8×8 пикселей — только если пользователь отметил «проверить изображения»). Каждый запрос учитывается в 10-1 с назначением `other`.
  - Назначения: «Основная модель чата», «Модель фоновой обработки» (обогащение, переформулировка, классификация импорта). Второе по умолчанию «как сейчас» — поведение `indexTermsModel` сохраняется, пока пользователь не выбрал явно.
  - Если у модели чата `tools = "unsupported"` — в чате предупреждение «Эта модель не умеет вызывать инструменты; память и действия недоступны», а не молчаливая деградация.
- **Не делать:** автоматический выбор модели (№55б); изменение формата запросов к провайдерам.
- **Тесты:** проверка для каждого из трёх протоколов (`openai`, `openai-compatible`, `anthropic`) на подменённом транспорте; сохранение и восстановление паспорта; назначение фоновой модели влияет на `askHelperModel`; предупреждение в чате.

### 10-3 — журнал действий (№76) · нужно решение владельца

- **Цель:** у каждого действия, меняющего что-то вне чата, есть запись: что предложено, что подтверждено, что реально произошло.
- **Решение владельца (хранилище):** (а) таблица `agent_actions` в SQLCipher — миграция схемы v20 и новая версия манифеста резервной копии; журнал переносится на новый телефон; (б) журнал только для внешних действий в защищённом хранилище устройства, последние 200 записей, без миграции и без переноса. Для этапа 10 достаточно (б); (а) понадобится, когда появятся расписания с внешней записью.
- **Шаг 0:** `direct-agent/task-state.ts` (`ToolOutcome`, `TaskEvidence`), `direct-agent/proposals.ts` (после ARCH-4), `local-memory/note-actions.ts` (журнал отмены — что уже записывается для внутренних действий).
- **Контракт:**
  ```ts
  type ActionRecord = {
    id: string;                       // идентификатор операции, создаётся при предложении
    kind: string;                     // "calendar_read" | "mail_draft" | ...
    effect: "read" | "internal_write" | "external_action";
    summary: string;                  // что именно: адресат, объект, объём — до 300 символов, без секретов
    status: "proposed" | "confirmed" | "running" | "succeeded" | "failed" | "unknown" | "cancelled";
    createdAt: string; finishedAt?: string;
    verification?: string;            // чем подтверждён результат
  };
  ```
  - В `ToolSpec.effect` добавляется значение `"external_action"`; инструмент с таким эффектом не исполняется циклом модели — он только создаёт предложение. Исполняет приложение после подтверждения.
  - Статус `unknown` (сеть оборвалась после отправки) никогда не повторяется автоматически: сначала проверка результата, затем решение пользователя.
  - Экран: Настройки → «Журнал действий» (список, фильтр по статусу, очистка).
- **Не делать:** сами внешние действия (они в 10-6); запись в журнал текстов заметок и содержимого писем.
- **Тесты:** полный жизненный цикл записи; `unknown` не приводит к повтору; предел 200 записей; журнал не содержит секретов (проверка на подстроки ключей из тестовой конфигурации).

### 10-4 — локальные напоминания (№57а) 

- **Цель:** «напомни завтра в 9 позвонить врачу» создаёт уведомление телефона, которое срабатывает без открытия приложения и без модели.
- **Зависимости:** ARCH-10 (решение по механизму уведомлений); ARCH-4.
- **Шаг 0:** документ ARCH-10; `direct-agent/fact-tool.ts` (`validDate`, виды записей, раздел событий); как текущая дата и часовой пояс попадают в контекст модели (№28; `direct-agent/context.ts`).
- **Контракт:**
  - Новая зависимость `expo-notifications` (единственное добавление зависимости в этапе; требует решения ARCH-10 и пересборки APK).
  - Инструмент предложения `propose_reminder(title ≤ 120, fireAtLocal: "YYYY-MM-DDTHH:mm", noteId?)`. Время в прошлом и дальше 2 лет отклоняется.
  - Вид предложения `reminder`: карточка «Напомнить: {текст} · {день недели, дата, время} · часовой пояс телефона».
  - Хранение: запись памяти вида «событие» в обычном разделе с полями `remind_at` и `reminder_state: "scheduled" | "fired" | "cancelled"` в `payload_json` (новой таблицы нет). Идентификатор системного уведомления — в защищённом хранилище устройства как производные данные: карта «запись → уведомление».
  - Текст уведомления на экране блокировки: по умолчанию «PersAI: напоминание» без содержания; настройка «Показывать текст напоминания на экране блокировки» выключена по умолчанию.
  - Сверка при каждом запуске после разблокировки: для записей `scheduled` с будущим временем без системного уведомления — создать заново (после перезагрузки телефона, восстановления из копии); для прошедших — пометить `fired`.
  - Инструменты `list_reminders(from?, to?)` (чтение) и `propose_cancel_reminder(noteId, expectedVersion)`.
- **Не делать:** повторяющиеся напоминания (отдельный PR после приёмки разовых); вызовы модели при срабатывании; фоновые задачи.
- **Тесты:** разбор и проверка времени; переход на летнее время и смена часового пояса (время хранится как локальное «настенное» плюс пояс создания; правило пересчёта записать в PR); отмена; сверка после потери системных уведомлений; восстановление из резервной копии создаёт уведомления заново.
- **Готово, когда:** на телефоне уведомление приходит при закрытом приложении; строка в долге приёмки.

### 10-6 — первый внешний сервис (№64) · нужно решение владельца

- **Решение владельца:** какой сервис первым. Рекомендация — без серверов и сторонних ключей: (1) календарь телефона **только на чтение** через системное разрешение; (2) **черновик письма** через системное окно «Поделиться»/почтовое приложение с текстом и выбранными вложениями. Отправку выполняет человек в почтовом приложении; PersAI честно пишет «черновик открыт», а не «отправлено».
- **Зависимости:** 10-3.
- **Шаг 0:** `media/share-destination.ts` и использование `expo-sharing`/`expo-intent-launcher` (уже в зависимостях); сценарии S16, S22, A01, A06 в [AGENT_TOOLS_SCENARIOS.md](AGENT_TOOLS_SCENARIOS.md).
- **Контракт (календарь):** зависимость `expo-calendar`; разрешение запрашивается при первом вызове инструмента, с объяснением; инструмент чтения `list_calendar_events(fromLocal, toLocal, limit ≤ 50)` возвращает название, начало, конец, календарь; запись в журнал действий с эффектом `read`. Создание и удаление событий — отдельный пакет после приёмки чтения.
- **Контракт (письмо):** инструмент предложения `propose_mail_draft(to?, subject ≤ 200, body ≤ 20000, attachmentNoteIds ≤ 5)`; карточка показывает адресата, тему, начало текста, список файлов с размерами; подтверждение открывает системное окно; запись журнала получает статус `succeeded` с пометкой проверки «открыто системное окно; отправку выполняет пользователь».
- **Не делать:** собственную отправку почты по SMTP/API; доступ к файлам телефона вне уже сохранённых вложений.
- **Тесты:** отказ в разрешении; пустой календарь; границы суток; вложение из закрытого раздела отклоняется; карточка письма соответствует аргументам.

### 10-7 — задания по расписанию с моделью (№57б) · после приёмки 10-1…10-6

- **Цель:** еженедельная сводка по подписке (S20).
- **Решение владельца:** на Android без фоновой работы честный вариант — уведомление по расписанию «Сводка за неделю готова к составлению», а сама сводка составляется при открытии приложения одним нажатием. Полностью фоновое составление требует открытой базы при заблокированном приложении и не рекомендуется.
- **Контракт:** задание = запись «расписание» (период, тема, предел вызовов модели на запуск) в настройках профиля; уведомление через механизм 10-4; при нажатии — обычный ход чата с подготовленным запросом; расход учитывается в 10-1 с назначением `summary`; №54б (резерв на запуск) реализуется здесь: задание не стартует, если дневной предел исчерпан.
- **Не делать:** запуск модели без действия пользователя.

### 11-1 — «что требует внимания» по запросу (№71)

- **Зависимости:** ARCH-5 желателен (выборка по датам), 10-4 (напоминания) желателен.
- **Шаг 0:** `local-memory/temporal-store.ts` (`listTemporalKnowledgeHistory`, запрос на дату), `agent-catalog.ts`, инструменты `list_local_notes`, `count_local_notes`.
- **Контракт:** инструмент чтения `list_dated_items(fromLocal, toLocal, limit ≤ 30)`: события и записи с явной датой в интервале из обычных разделов, плюс напоминания из 10-4; каждая строка с идентификатором и версией. В `guidance`: не выдумывать сроки, не заявлять полноту; строка без источника запрещена. Ответ в чате — список со ссылками на записи.
- **Не делать:** фоновый запуск; чтение календаря (он подключается через 10-6 отдельным инструментом).
- **Тесты:** пустой интервал; граница суток; запись без даты не попадает; 30+ записей — честное «показаны первые 30».

### 11-2 — короткий профиль «обо мне» (№15, №16)

- **Шаг 0:** `openspec/changes/about-me-profile/` (уже есть предложение и задачи), `local-memory/self-identity.ts`, раздел профиля в `fact-tool.ts` (`DEFAULT_SECTIONS`).
- **Контракт:** выполнить по существующему OpenSpec. Дополнительные границы: профиль — обычная запись в обычном разделе, правится пользователем; в системный промпт попадает не более 600 символов (обрезка по предложениям) через отдельную часть `buildSystemPrompt`; знакомство при первом запуске — один пропускаемый экран-подсказка в чате, без анкеты.
- **Тесты:** профиль пуст — промпт без блока; длинный профиль обрезан; правка профиля меняет следующий запрос; профиль из закрытого раздела не используется.

### 11-3 — предпочтения из поправок (№17, №19)

- **Шаг 0:** `fact-tool.ts` (`draft_memory_fact`, вид «предпочтение»), `direct-agent/agent-preferences.ts`.
- **Контракт:** когда пользователь поправляет помощника («отвечай короче», «не предлагай X»), модель вызывает существующий `draft_memory_fact` с видом «предпочтение»; после подтверждения запись сохраняется в раздел профиля. Действующие предпочтения (до 10 последних, до 800 символов суммарно) добавляются в промпт отдельным блоком с пометкой «правила пользователя». У записи есть переключатель «применять» (поле в `payload_json`).
- **Не делать:** сохранять предпочтение без подтверждения; выводить предпочтения из поведения без явной фразы пользователя.
- **Тесты:** отказ ничего не меняет; выключенное правило не попадает в промпт; предел объёма.

### 11-4 — манера общения (№82)

- **Контракт:** настройка профиля: тон (`нейтральный` | `дружелюбный` | `деловой`), длина ответа (`короче` | `обычная` | `подробнее`), обращение (`ты` | `вы`). Хранение рядом с `agent-preferences.ts`; включить в `backup-settings.ts` по образцу лимита вызовов. В промпт добавляется одна фраза из закрытой таблицы 3×3×2; свободный текст не принимается. Экран: одна сворачиваемая группа в существующих настройках помощника.
- **Тесты:** каждая комбинация даёт ожидаемую фразу; сброс; сохранение после перезапуска и восстановления из копии; правила честности и источников в промпте не меняются (сравнение остальной части промпта).

### 11-5 — черновик в своём стиле (№74)

- **Зависимости:** ARCH-5 (выборка образцов).
- **Контракт:** пользователь выбирает 1–5 заметок как образцы стиля («пиши как в этих заметках») — это выборка текущего диалога; модель читает их существующими инструментами чтения выборки и пишет черновик. `guidance`: факты брать из задания и памяти, из образцов — только стиль. Результат — обычный ответ с кнопками «Сохранить в заметку» (существующая `prepareAssistantReplyNote`) и «Скопировать». Отправки нет.
- **Тесты (скриптовые):** образцы читаются с проверкой прав; черновик не содержит фактов, присутствующих только в образце (проверка на контрольную строку).

### 11-6 — наставник по своим материалам (№78)

- **Зависимости:** ARCH-5.
- **Контракт:** режим «проверь меня по этим материалам»: выборка 1–10 записей; модель задаёт вопрос, пользователь отвечает, модель сверяет ответ с прочитанным фрагментом и приводит ссылку на место. Состояние занятия (номер вопроса, счёт, пройденные записи) — в существующем рабочем черновике задачи (`workspace_put`), не в памяти. По завершении — предложение сохранить итог как заметку.
- **Не делать:** отдельный экран; хранение истории занятий в новой таблице; аудио и видео.
- **Тесты:** вопрос основан на реально прочитанном диапазоне (есть запись покрытия); ответ «не знаю» обрабатывается; итог сохраняется только после подтверждения.

### 11-7 — сводка памяти и рекомендации по подписке (№21, №58)

- **Зависимости:** 10-7, 11-1.
- **Контракт:** два готовых задания для механизма 10-7: «Сводка памяти за неделю» (что добавлено, по разделам, с числами из `count_local_notes`) и «Что почитать из сохранённого» (несохранённое в интернете не искать без включённого поиска). Оба выключены по умолчанию.

### 11-8 — напоминание по месту (№81) · поздний, по решению владельца

- **Контракт первого этапа:** только при открытом приложении, разрешение на геопозицию по запросу; проверка «я рядом с местом» при открытии; фоновых геозон нет. Требования — [ASSISTANT_FEATURES.md §4](ASSISTANT_FEATURES.md). Перед началом — отдельный документ о приватности.

## Этап 12 — экспорт, история, восстановление, ревизия

### 12-1 — переносимый экспорт (№63б)

- **Цель:** выгрузка памяти в читаемом виде, не привязанном к PersAI.
- **Шаг 0:** `local-memory/backup.ts` (только чтение: как перечисляются записи и вложения), `expo-sharing`, экран `MemoryBackupScreen.tsx`.
- **Контракт:** архив ZIP: `notes/<раздел>/<дата>-<заголовок>.md` (заголовок, теги, источник, текст), `attachments/<id>/<имя>`, `index.json` (идентификаторы, версии, даты, связи). По умолчанию только обычные разделы; закрытые — отдельным флажком с предупреждением «файл не зашифрован». Создаётся во временном каталоге, передаётся через системное окно, затем удаляется. Предел: предупреждение о нехватке места до начала.
- **Не делать:** импорт из этого формата; изменение формата зашифрованной копии.
- **Тесты:** имена файлов безопасны (кириллица, длинные, одинаковые); закрытые записи не попадают без флажка; отмена удаляет временные файлы; блокировка приложения прерывает экспорт.

### 12-2 — контроль роста истории диалогов (№65)

- **Шаг 0:** `direct-agent/conversations.ts` (`ConversationRepository`), `chat-store.ts` (`remove`), где считается объём.
- **Контракт:** в настройках строка «Диалоги: N штук, X МБ»; действие «Удалить диалоги старше…» (3 / 6 / 12 месяцев) с предпросмотром числа и объёма и подтверждением; заметки, сохранённые из диалогов, не затрагиваются — это написано на карточке. Автоматического удаления нет.
- **Тесты:** граница даты; активный диалог не удаляется; после удаления поиск по истории не находит удалённое.

### 12-3 — восстановление и напоминание о копии (№66, №63)

- **Зависимости:** 10-4.
- **Контракт:** (1) напоминание «Давно не было резервной копии» — локальное уведомление, если последней копии больше N дней (настройка: выключено / 7 / 30); нажатие открывает экран копии; фоновой копии нет, так как база закрыта при заблокированном приложении. (2) Учебная проверка копии: кнопка «Проверить копию» расшифровывает выбранный файл во временную базу, сверяет манифест и счётчики и показывает отчёт, не трогая рабочую базу.
- **Шаг 0:** `backup.ts` — есть ли уже отдельная от восстановления проверка манифеста; если да, переиспользовать. Этот пакет читает `backup.ts`, но менять его можно только с отдельным разрешением владельца.
- **Тесты:** повреждённый, усечённый файл, неверный код — отчёт об ошибке, рабочая база не изменена; временная база удаляется.

### 12-4 — групповая ревизия памяти через чат (№79)

- **Зависимости:** ARCH-4.
- **Шаг 0:** `local-memory/hygiene.ts` (`discoverHygieneGroups`, `MemoryHygieneService`, типы предпросмотра и влияния), [MEMORY_HYGIENE.md](MEMORY_HYGIENE.md), сценарий A05.
- **Контракт:** инструмент чтения `suggest_review_groups()` поверх `discoverHygieneGroups`; инструмент предложения `propose_review_batch(targets: [{id, recordVersion}], action: "archive" | "trash", reason)`; вид предложения `review_batch`: карточка показывает точное число, первые 10 заголовков, ссылку «показать все», влияние из `MemoryReviewImpact`, и что именно произойдёт («в архив» / «в корзину; из корзины можно вернуть»). Исполнение — существующий `MemoryHygieneService`. Окончательное удаление из корзины через чат не делается.
- **Тесты:** состав изменился между предложением и подтверждением — отказ с новым числом; закреплённые и помеченные «не предлагать» записи не входят; отмена возвращает всё.
