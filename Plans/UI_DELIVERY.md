## Аудит и устранение дублирования функций — U1–U5

**Когда:** проверять внутри каждого пакета U1–U4 при изменении экрана или навигации; повторить сквозной аудит на U5 (№87–90). Не ждать финала, чтобы устранить обнаруженные дубли, и не открывать самостоятельный редизайн только ради этой задачи.

**Что проверять:**

1. **Карта действий и точек входа:** Главная/история, Память/запись, импорт из файла/камеры/Share/URL, настройки моделей/голоса/поиска/лимитов/копий и системная навигация. Для каждого действия указать все кнопки/маршруты, обработчик, источник состояния и ожидаемый результат; проверить, нет ли двух экранов или разных кнопок с одинаковым назначением без ясной причины.
2. **Дублирование настроек и логики:** две формы изменения одной опции, разные сохранённые значения на разных экранах, раздельные обработчики, которые расходятся по поведению; скрытые/устаревшие пункты, которые повторяют актуальную функцию. Отдельно проверить прежние и новые точки входа после миграции UI.
3. **Отличить дубль от полезной альтернативы:** например, файл из чата и файл из памяти могут начинать разные пользовательские сценарии. Такие точки входа сохранять, если у них разные цели; общую операцию выносить в один сервис/состояние, без повторной реализации и противоречивых настроек. Не удалять функцию из-за похожей подписи или повторного использования компонента.
4. **Исправление:** определить канонический экран/действие, убрать лишний элемент либо сделать его явной ссылкой на основной путь, сохранить обратную совместимость навигации и существующие записи/настройки. Не менять AppLock, SQLCipher, разрешения, B+C сферу и действие агента без самостоятельного основания и проверок.
5. **Регрессии:** автоматический сценарий для каждого устранённого дубля: обе прежние точки входа корректно приводят к ожидаемому результату либо безопасно перенаправляют; данные и выбранные настройки сохраняются после возврата/перезапуска; нет двух конкурирующих обработчиков, двойного запуска действий или повторных платежных LLM-запросов. Проверить accessibility labels, Back, Gboard, переходы вкладок и состояние во время работы.

**Артефакт:** пополняемая таблица аудита в спецификации соответствующего экранного пакета: `функция / места вызова / решение (один путь | обоснованный альтернативный вход | устранённый дубль) / тест / статус`. Отмечать факты, а не удалять функции по предположению. Для U5 — сводная таблица по всем трём вкладкам и вложенным экранам.

**Критерий завершения U5:** отсутствуют необоснованные дубли пользовательских функций и конкурирующие настройки; оставшиеся альтернативные входы документированы и используют согласованное состояние; устранение дублей покрыто регрессиями. Подтверждение — browser/native CI для соответствующего SHA плюс краткая Android-проверка изменённых маршрутов. Недоказанное оставить открытым, а не объявлять завершённым.

Пакет — законченный пользовательский сценарий, обычно один PR. Отдельный PR оправдан самостоятельной ошибкой сборки/безопасности или изменением данных, а не одной декоративной настройкой. Не обещать жёсткий срок до проверки зависимостей.

**Разработка U1–U4 не ждёт замеров батареи или лимита Figma.** Согласованный B+C и существующие референсы действуют. Для конкретного экрана до кода фиксируем компоновку и состояния в его спецификации, используем интерактивное превью/снимки реального UI; неполную Figma не называем завершённой. Новую художественную концепцию без согласования не вводим. Приёмка конкретного экрана на Android остаётся обязательной.

## Как должен выглядеть целостный интерфейс

- Три вкладки: Главная, Память, Настройки. Космический фон и стеклянные поверхности с общей иерархией. Читаемый текст — на спокойной подложке. Для рабочих списков не нужна ещё одна большая анимированная сфера.
- Главная: компактная шапка, история занимает пространство, ввод закреплён снизу. Микрофон/нормализация/Send доступны при клавиатуре. Статус операции словами; цвет и B+C дополняют смысл. Вложения в чат внедряются с работающим транспортом, не декоративной кнопкой.
- Память: поиск и содержимое впереди административных действий. Добавление/импорт, просмотр, редактирование — чётко различимые шаги. Массовые действия появляются только после выбора.
- Импорт: пользователь видит исходник, извлечённый текст, куда сохраняет и что произойдёт при отмене. «Отправить модели» и «Сохранить в память» — отдельные действия.
- Настройки: краткий итог под категорией, настройки внутри; ошибки рядом с полем. Диагностика/лаборатория в разработческом разделе. Новые инструменты и задания позже входят в эту архитектуру без разрастания нижней панели.

## Правила завершения работы

1. До реализации: проблема, затронутые сценарии, что увидит пользователь, критерии приёмки. Короткая спецификация в существующем change; не плодить дубликаты.
2. Во время реализации: исправить причину; на гонки и переходы состояния — поведенческие тесты. Строковые guards оставлять для запретов/инвариантов, не принимать их за UX-тест.
3. До передачи владельцу: агент запускает typecheck, применимые tests, браузерные сценарии и проверяет CI/native. При ограничении среды указывает его, не передаёт пользователю отладку CI.
4. Для каждого кандидата фиксировать PR + commit SHA + CI/native URL + APK/tag + устройства/проверенные сценарии. Любое изменение SHA требует новых применимых проверок; прежнее зелёное состояние не переносится.
5. Пользователю — один контрольный APK и короткий перечень изменённых сценариев, а не полная повторная приёмка после каждого tweak. Данные не удалять, экран «Защищено» не менять и не включать в новый ручной чек-лист; восстановление остаётся отложенным.
6. При P0/P1 — исправление текущего кандидата. При P2 — запись в реестр с приоритетом; не задерживать независимую работу над другим экраном. Художественное качество B+C не упрощать ради формального PASS.
7. В конце PR обновить действующий статус и только затем историю. Один актуальный порядок в PLAN; у подпланов — детализация и ссылки, а не собственная очередь.

## Ревизия кода Home в этом изменении

Состояние чтения и очередь requestAnimationFrame ранее переживали смену диалога и уход с вкладки. Теперь очередь отменяется на blur/unmount/смене ID; фоновые обновления не прокручивают скрытый Home; другой диалог получает собственный FlatList и открывается у последних сообщений, тот же диалог при возврате с вкладки сохраняет чтение выше. LLM продолжает работу независимо от UI. Приёмка: четыре поведенческих теста hook + общие UI-регрессии + Android-переходы U0.

## Проверки ревизии

- PASS: TypeScript; 460 Jest assertions / 64 suites (включая 4 новых поведенческих теста); 22 release tests; сохранность 91 номера; SHA-256 оригиналов Nebula; diff check.
- Локальный browser run NOT RUN: загрузка Chromium в среде вернула повреждённый архив. Проверка остаётся обязательной в GitHub Actions; не заменять её синтаксической проверкой скрипта.
- Native build и browser CI нового SHA: проверяются в PR. Android Gboard, TalkBack, FPS/battery и визуальная приёмка NOT RUN.
- CI теперь сохраняет снимки production browser fixtures и экран при сбое как artifact `browser-ui-<sha>` на 7 дней. Данные fixtures синтетические.
