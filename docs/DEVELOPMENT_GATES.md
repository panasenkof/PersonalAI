# PersAI — правило обязательного цикла разработки

**Статус:** правило проекта, утверждено владельцем 26.10.2026. Применяется к каждой задаче, промежуточному этапу и PR. Входит в [AGENTS.md](../AGENTS.md) и правило Cursor. **PLAN.md §2 — единственная актуальная очередь**, подпланы и OpenSpec раскрывают требования, не становятся вторым roadmap.

## Идентификаторы и защита от раздробленного roadmap

- Единственный порядок — PLAN.md §2; постоянные номера только №1–91. Термины ENG-M0…M6 обозначают стадии **архитектуры**, AUD-M01…M19 — **аудитные находки**, не новые задачи. Исторические обозначения M0/M01 в ссылках продолжают работать.
- Формы 63а.1, №79а, MSG-2, U5 и 83.2 — **подпакеты** уже существующего номера. Добавлять новые «а/б/1/2» уровни в PLAN только по действительной независимой приёмке, а не автоматически для каждого PR. Ярлык ветки/PR вида 63а.1б не резервирует новую строку 1–91.
- В описании PR: **один** главный №, шаг очереди, затронутые AUD-M/ENG-M, зависимости (если stacked), C1/C2 и родительские остатки. Разделять «DONE конкретного среза» и «DONE всей задачи»; непроверенное оставлять NOT VERIFIED. При двух № для одного сценария не отражать это двумя разными «готово».
- Актуальный статус **только** ROADMAP_STATUS.md, очередь **только** PLAN.md §2; технические доказательства/проекты — в релевантном подплане, PR и аудите. Не заводить новый TODO-файл/таблицу статусов, дублирующую эти источники. Мигрировать готовый PR по факту, не по старому чату.

## Проверка фактического target merge

После любого merge PR со статусом `merged=true` ОБЯЗАТЕЛЬНО проверить `base.ref` и реальные файлы/sha в целевом `main`. Слияние в уже слитую feature-ветку не переносит её новых коммитов автоматически в main. При staged PR выбирать main как конечный target (или после parent merge менять base), проверять сравнение git-дерева и CI фактического нового SHA. Это не вторая очередь: это обязательная защита от потери реализованного кода, воспроизведённой PR #135/#137–140 27.10.2026.

## Контроль A — до изменения кода

1. **Актуализировать факты:** проверить свежую `main`, открытые PR и изменения зависимых файлов; не строить решения только на выводах старого диалога, ревизии плана или непроверенном статусе CI.
2. **Сверить планы:** найти номер/пакет и очередь в [PLAN.md](../PLAN.md), фактический статус в [ROADMAP_STATUS.md](../Plans/ROADMAP_STATUS.md), открыть *релевантные* подпланы, действующие OpenSpec/дизайн-контракты, связанные аудиты, код и тесты. Зафиксировать достигнутое, ещё не сделанное, конфликты, пробелы, дублирование и зависимости.
3. **Обновить решения, если нужно:** сопоставить планы с текущей реализацией и последними явно утверждёнными владельцем требованиями; упрощать ненужные шаги, добавлять отсутствующие критические проверки и устранять противоречия. **Не делать вид, что изменение плана автоматически реализовало функцию.**
4. **Проверить референсы и лучшие практики:** изучить уже сохранённые в репозитории референсы по *той же задаче*, оценить их актуальность/качество; при существенном редизайне, новой архитектуре, смене API/SDK либо пробеле в данных искать свежие проверяемые официальные источники и примеры. Записать дату и ссылку, что **принято / адаптировано / отвергнуто** и почему. Для значимых UI-переделок применять [mobile-ui-ux](../skills/mobile-ui-ux/SKILL.md): 2–4 подходящих аналога, Apple HIG как качественный референс, Android/Material, Back, TalkBack, WindowInsets как контракт. Для безопасности/БД/SDK отдавать приоритет официальной документации и реальным ограничениям. Не копировать чужой интерфейс/код вслепую.
5. **Сформировать маленький контракт текущего этапа:** точный пользовательский сценарий и инварианты, изменяемые файлы/API, проверяемые результаты, применимые регрессии, ограничения, **что отложено на следующие этапы**. Сравнение должно быть со стадией разработки, а не со всем будущим продуктом.

Для рутинного bugfix, копирайта, рефакторинга без нового поведения или уже утверждённого точного UI-паттерна не проводить новый конкурентный анализ ради галочки: отметить `References: existing / N/A (reason)`. **Но актуальность плана и границ всё равно проверить.** Не тратить недели на исследования вместо небольших рабочих PR.

## Контроль B — в ходе реализации

- Работать небольшими законченными проверяемыми вертикалями, сохранять защиту данных/локальный SQLCipher, профиль и исходники; не переписывать утверждённый UI или готовые модули «для красоты».
- Если новые факты/референсы/проверки показали, что план устарел, корректировать конкретный пункт PLAN + профильный подплан/OpenSpec **в том же PR или отдельным связанным документным PR**. Не создавать вторую очередь.
- Промежуточная реализация может содержать только backend/API без UI; нельзя называть невыпущенные экраны рабочими функциями.

## Контроль C — **после каждого промежуточного шага**, перед закрытием PR

**Ключевое решение владельца:** повторная приёмка касается **именно того, что уже реализовано, и реальных регрессий затронутых зависимостей**. НЕ нужно заново проверять весь будущий план, незавершённые страницы, модели или внешние интеграции.

**Обязательны два независимых итога:**

**C1. Проверка созданной функциональности.**
- Реально подключённый сценарий / API / schema/UX против мини-контракта, положительный кейс, negative/error/cancel, CAS/ACL/lock/undo, когда применимо.
- Регрессии затронутых существующих сценариев (например, для SQLCipher — прежние данные, миграция/backup/restore, оригиналы и индекс; для UI — Back/IME/selection/accessibility). Не запускать нерелевантный общий UI benchmark и тяжёлый native pipeline вручную без причины, но следовать *обязательным* CI.
- Конкретная версия кода/commit SHA, реальные запущенные тесты и результаты. `PASS` только после выполнения; `FAIL`, `NOT RUN`, `NOT IMPLEMENTED`, `BLOCKED`, `N/A (reason)` не маскировать. Нативная сборка, публикация APK и физическая Android-приёмка — разные факты.

**C2. Обязательная итоговая сверка с общим планом И подпланами.**
- Сопоставить **построчно относящиеся к текущему этапу требования/acceptance criteria** из `PLAN.md`, `Plans/ROADMAP_STATUS.md`, профильных подпланов, OpenSpec и утверждённых решений с фактическим diff, вызовами API и тестами.
- Отчёт по каждому применимому пункту: `MATCH` / `PARTIAL` / `DEVIATION` / `NOT IMPLEMENTED (next stage)` / `NOT VERIFIED`. Не подменять «внесено в код» результатом теста.
- Любое отклонение от **обязательной** части текущего контракта: либо **исправить код** до объявления этапа выполненным, либо обосновать изменение и **обновить общий план + подплан + спецификацию**, если решение действительно стало лучше и не нарушает предыдущие обязательства. Пользовательские запреты, безопасность и необратимые действия не отменяются автором PR «для удобства».
- Если найден неустранённый блокер или отклонение: назвать его и оставить этап `PARTIAL/BLOCKED`. Следующий этап не должен опираться на необоснованное `DONE`.
- Обновить статус в одном реестре `Plans/ROADMAP_STATUS.md` и одном основном плане `PLAN.md` по факту. Ссылки на PR/SHA и незапущенные Android-тесты фиксировать, не переписывать историю и не плодить новые «актуальные» дорожные карты.

## C3 — обязательная архитектурная консолидация для каждого PR (27.10.2026)

После реализации каждого небольшого шага, **до закрытия PR**, просмотреть только изменённую область и её необходимые зависимости:
1. Нет ли второго способа выполнять ту же операцию, второго источника истины, повторяющихся бизнес-правил, новых лишних состояний, обходных условий, временных адаптеров или ненужной абстракции?
2. Можно ли удалить/объединить устаревший код и тесты, переиспользовать действующий механизм либо сделать поток данных короче **без** потери функциональности, безопасности, приватности, производительности и обратной совместимости?
3. Не затруднит ли упрощение текущие миграции, откат, диагностику, релиз или соседние незавершённые PR? **Не объединять без необходимости изменение поведения, схемы данных и масштабный рефакторинг в одном PR.**
4. Если небольшое локальное упрощение безопасно и проверяемо — выполнить его в текущем PR и проверить затронутые регрессии. Если не требуется — зафиксировать NO CHANGE NEEDED с одной причиной. Если рискованно/широко — зафиксировать DEFERRED, конкретную возможность, причину и **условие возврата**, без обязательства рефакторить прямо сейчас.
5. При завершении отдельного архитектурного этапа выполнить более широкую ревизию затронутых реализаций: подтвердить один источник истины и удалить временные механизмы после миграции. Указывать фактическую экономию сложности (какие реализации/ветви/зависимости удалены), а не требовать искусственного уменьшения строк.

**Особый режим PersAI при пересоздании памяти:** пока ENG-M1–M4 и соответствующие native/SQLCipher/backup/restore/поиск/UX регрессии не завершены, **никакого параллельного большого переписывания** репозиториев, поиска, слоёв хранения или миграций только ради консолидации. Небольшие улучшения внутри предметного PR допускаются лишь при минимальном риске и своей C1-проверке. **Отдельная серия architecture-consolidation PR назначена в PLAN.md §2 после стабилизации базового нового Memory Engine (M1–M4)**; мультимодальные эксперименты M5 и необязательная автоматизация M6 не должны искусственно блокировать эту контрольную точку.

Отчёт C3 для **каждого PR**: SIMPLIFIED (что было устранено, тест) / NO CHANGE NEEDED (причина) / DEFERRED (что, риск, триггер и ссылка на пункт PLAN/аудит). Не заводить четвёртую дорожную карту, не принуждать микрофиксы к большому рефакторингу. C3 дополняет, но **не заменяет C1/C2**.

## Шаблон итогового отчёта в каждом PR

```
Пункт PLAN.md / версия: ...
Связанные подпланы / OpenSpec: ...
Референсы: существующие ...; новые ... (или N/A с причиной)
Объём текущего этапа: ...; следующие этапы НЕ включены: ...
C1 — реализация и тесты:
  Выполнено: ...  PASS: ...  FAIL: ...  NOT RUN: ...  N/A: ...
  Затронутые регрессии / безопасность / restore: ...
C2 — сверка с планом:
  MATCH: ...  PARTIAL: ...  DEVIATION: ...  NOT IMPLEMENTED (next stage): ...
  Необоснованные отклонения исправлены?: да/нет; при изменении решений: ссылки на обновлённые PLAN/подплан/OpenSpec
C3 — архитектурная консолидация: SIMPLIFIED / NO CHANGE NEEDED / DEFERRED; доказательство/причина/условие возврата: ...
Результат этапа: DONE / PARTIAL / BLOCKED; следующий конкретный шаг: ...
```

## Применение к №79 «Ревизия памяти»

- **№79а**: схема хранения pin/never_suggest/defer и read-only `dryRun`; тестировать их и смежные SQLCipher миграцию/backup, **не требовать сейчас** UI массового выбора, ИИ-группировки и физического удаления.
- **№79б**: локальные группы с объяснениями и охраняемыми исключениями; проверка кандидатов и отсутствия модификаций до подтверждения.
- **№79в / M4-UX**: экран групп, исключения, preview, подтверждение архив/корзина, откат и Android доступность.
- **№79г**: позднее — семантический анализ и возможный opt-in периодический обзор. Ни одна стадия не авторизует автоматическое безвозвратное удаление.

Подробности: [MEMORY_HYGIENE.md](../Plans/MEMORY_HYGIENE.md). Последующие шаги имеют собственную проверку и отдельную **C2-сверку** с планом, которая не может быть заменена зелёным CI.
