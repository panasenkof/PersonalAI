# Выпуск и эксплуатация PIA Agent

## Что должен заполнить оператор

До публичного запуска нужны реальные: домен/сервер, OPERATOR_NAME, SUPPORT_EMAIL, опубликованные HTTPS PRIVACY_URL/TERMS_URL, SMTP с TLS, оплаченный DEFAULT_LLM_API_KEY и проверенные модели. Не храните эти секреты в GitHub или в диагностике. Политика оператора должна описывать хранимые аккаунты/диалоги/файлы, обработчиков (хостинг, почта, LLM и выбранные мессенджеры), сроки и процедуру удаления, резервные копии, контакты и применимые правила. Техническая справка не заменяет эту политику.

1. Скопировать `.env.example` в `.env`, установить APP_ENV=production, случайные JWT_SECRET, POSTGRES_PASSWORD и PIA_AGENT_SECRET. Настроить публичные поля выше, REQUIRE_VERIFIED_EMAIL=true и положительные RATE_LIMIT_AUTH_PER_MINUTE/RATE_LIMIT_LLM_PER_MINUTE. CORS_ORIGINS должен совпадать с доменом. PUBLIC_BASE_URL=https://<домен>, PIA_DOMAIN=<домен без схемы>.
2. Настроить отдельный BACKUP_ENCRYPTION_KEY. Ключи приложения и копий хранить в менеджере секретов отдельно от копий. Docker Compose монтирует журнал удалений в отдельный volume `deletions`.
3. Установить PUBLIC_LAUNCH=true. Запуск откажет при незаполненной обязательной конфигурации. Это проверка конфигурации, а не доступности SMTP/LLM/политики.
4. Направить DNS на сервер, разрешить 80/443, выполнить `docker compose --profile public up -d --build --wait`. Caddy получает HTTPS-сертификат. Прямой порт nginx привязан только к loopback; внешние подключения идут через HTTPS. Не публиковать app:8000 напрямую.
5. Проверить `/ready` снаружи, новую регистрацию/доставку письма/подтверждение, первый чат, «Проверить модель и поиск», загрузку файла, восстановление пароля, экспорт и удаление двух тестовых аккаунтов с проверкой изоляции. Установить ограничения бюджета/оповещения в кабинете LLM-провайдера: частотный лимит PIA не является денежным потолком.
6. Настроить независимый внешний мониторинг HTTPS `/ready`, истечения сертификата, очереди, ошибок SMTP, заполнения диска и возраста последней резервной копии. Не подключать содержимое чатов к мониторингу.

PUBLIC_LAUNCH по умолчанию выключен для обновления существующих частных установок. С включением REQUIRE_VERIFIED_EMAIL прежним аккаунтам понадобится подтверждение: заранее уведомите пользователей, они могут запросить письмо на экране восстановления без входа.

## Резервные копии и восстановление

`deploy/backup.sh /absolute/dedicated/backup-dir` выполняется из корня репозитория с экспортированным BACKUP_ENCRYPTION_KEY и работающей Compose-установкой. Backup-контейнер выполняет только CLI от root для чтения закрытых volume; архивы имеют права 0600. Запускайте scheduler с правами чтения этих архивов и доступа к Docker. Скрипт останавливает API и worker, снимает pg_dump + blob-снимок, шифрует архив, сохраняет актуальный журнал удалений отдельно и возобновляет сервисы даже при ошибке. На время копии сервис недоступен. Поддерживаются архивы до 1 GiB; для большей установки нужны потоковые средства резервирования. Redis не копируется: долговечные задания восстановятся из БД, доставка внешним каналам должна быть проверена после аварии.

Настройте ежедневный запуск через системный scheduler, например cron (пути и права определить на сервере):

```cron
0 3 * * * cd /srv/PersonalAI && /srv/pia-ops/backup-with-secrets.sh >> /var/log/pia-backup.log 2>&1
```

Обёртка должна безопасно получать BACKUP_ENCRYPTION_KEY, вызывать `deploy/backup.sh /srv/pia-backups` и отправлять оператору сигнал при ошибке. BACKUP_RETENTION_DAYS по умолчанию 30; скрипт удаляет только собственные датированные архивы старше этого срока. Зеркалируйте зашифрованные архивы и **текущий** журнал удалений на независимое хранилище после каждого удаления или с минимальной задержкой. Ежедневная копия журнала одна не гарантирует сохранение удалений при потере сервера между копиями; перед широким запуском настройте непрерывную репликацию volume `deletions`. Не включайте журнал в старые снимки и не удаляйте его при восстановлении.

Проверяйте восстановление ежемесячно и перед каждым значительным обновлением в изолированной установке без реальной почты, мессенджеров и публичного трафика:

1. `BACKUP_ENCRYPTION_KEY=... python -m app.operations.backup restore --archive /path/pia-....fernet --destination /new/restore-dir` (команды Python выполняются из `backend`). Каталог должен отсутствовать; архив проверяет аутентичность, контрольные суммы, лимит размера и пути. Он содержит database.dump и blobs.
2. Создать **новую** Postgres БД с расширением vector, импортировать `pg_restore --no-owner --dbname=<новая БД> /new/restore-dir/database.dump`. Не восстанавливать поверх работающей БД. Для SQLite database.dump уже является файлом БД; создавать копию в новой установке.
3. Подключить восстановленные blobs и исходные PIA_AGENT_SECRET; выполнить миграции. Отдельно подключить **самый актуальный** внешний журнал удалений. При остановленных API/worker выполнить `DATABASE_URL=<новая БД> BLOB_STORAGE_DIR=<восстановленные blobs> python -m app.operations.restore_deletions --journal /path/current-deletions.log --writers-stopped`. Утилита повторно удаляет аккаунты/файлы и отменяет их старые задания. Если журнал отсутствует или повреждён, трафик не открывать.
4. Проверить `/ready`, чтение старого диалога и файла с исходным ключом, факт/поиск, изоляцию, отсутствие удалённого аккаунта, задачи. Замерить длительность, сохранить дату, результат и ответственного. Только затем менять публичную установку.

Цели до измерения на реальном сервере: RPO ≤24 часа при ежедневной копии данных, RTO ≤2 часа. Это **целевые**, а не подтверждённые показатели. Журнал удалений должен иметь более строгий RPO. Автоматический тест в репозитории подтверждает SQLite snapshot → encrypted archive → восстановление данных и файлов, отказ при неверном ключе/опасном пути/неверной контрольной сумме. Производственный Postgres + Docker сценарий требует отдельной приёмки.

## Нативный выпуск

Expo последовательно обновлён с SDK 51 до 52, 53 и 54; React Native 0.81 и Navigation 7. Выполнить `npm ci`, typecheck, Jest, expo-doctor. SDK 54 здесь — выбранная база, не заявление о последней версии SDK. На подписанной сборке проверить Android/iPhone/планшет, крупный шрифт, screen reader, клавиатуру, safe area, камеру, экспорт через системное меню, фон/возврат и смену сети.

Владелец предоставляет Expo project ID, owned bundle/package ID, HTTPS endpoint и аккаунты/подписи Apple/Google. Настроить EAS и переменные удалённой сборки; `eas build --profile preview --platform android` для APK, production для AAB/IPA и TestFlight. Expo Go и успешный Metro export не заменяют установку подписанного приложения. Ссылки на магазины добавлять только после появления реальных доступных сборок.

## Приёмка первого пользователя

Открыть `/app/start.html`, установить PWA по справке, создать аккаунт и подтвердить почту, получить ответ без ручной настройки модели. Проверить понятность расходов, поддержку и правила данных. Напоминания сейчас через Telegram; push не обещать. Испытатель должен пройти сценарий без подсказок автора. До завершения инфраструктурных и аппаратных проверок приглашать только в согласованный закрытый пилот.
