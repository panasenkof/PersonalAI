# Безопасность

## Fail-closed в production (`APP_ENV=production`)
Приложение **не стартует**, если (`app.config.production_problems`):
* `JWT_SECRET` дефолтный или короче 32 символов;
* нет валидного `PIA_AGENT_SECRET` (Fernet);
* задан токен канала, но нет его секрета: `TELEGRAM_WEBHOOK_SECRET`; `SLACK_SIGNING_SECRET`;
  `WHATSAPP_APP_SECRET` + `WHATSAPP_VERIFY_TOKEN`; `DISCORD_PUBLIC_KEY`;
* `QUEUE_BACKEND=redis` без `REDIS_URL`; `CORS_ORIGINS=*`.

Вебхук канала без настроенного секрета в production отвечает 503 (а не принимает запросы «по умолчанию»); неверный секрет/подпись — 401. Сравнение секретов — constant-time.
Slack — HMAC-подпись + окно replay; WhatsApp — `X-Hub-Signature-256`; Discord — Ed25519 подпись interaction.

## Аутентификация
* **2FA (TOTP, RFC 6238)**: `POST /v1/auth/2fa/setup` → секрет + `otpauth://` URI; `/2fa/enable` (подтверждение кодом) → 8
  одноразовых recovery-кодов по 64 бита энтропии (в БД — только SHA-256 хеши); `/2fa/disable` (пароль + код). Логин: `POST /v1/auth/token` с полем `otp`;
  без него → 401 `otp_required`. Каждый TOTP-код принимается **один раз** (запоминается time-step, RFC 6238 §5.2) — перехваченный
  код нельзя переиспользовать. Есть в веб-UI и мобильном приложении (Настройки).
* **Роли**: `user` | `admin`. Администратор создаётся из серверной консоли (`python -m app.security.admin email`),
  либо назначается другим администратором
  (`PATCH /v1/admin/users/{id}`); `GET /v1/admin/users|stats`. Нельзя понизить/отключить самого себя.
* **Отзыв токенов**: `users.token_version` зашит в JWT; смена пароля, `POST /v1/auth/logout-all`, блокировка пользователя
  мгновенно инвалидируют все выданные access/refresh токены. Access и refresh — разные типы токенов.
* **Ротация JWT-секрета** без разлогина: новый — в `JWT_SECRET`, старый(е) — в `JWT_SECRET_PREVIOUS` (через запятую);
  подписывает первый, проверяются все.
* Защита от перебора: rate limit на регистрацию/логин по IP (`RATE_LIMIT_AUTH_PER_MINUTE`), блокировка логина по e-mail после
  `LOGIN_MAX_FAILURES` неудач на `LOGIN_LOCKOUT_SECONDS`, блокировка привязки каналов (5 неверных link-кодов за 15 минут на
  внешний аккаунт). Счётчики общие между репликами при `REDIS_URL`. Время ответа логина не зависит от того, существует ли e-mail.
* **За reverse proxy** включите `TRUST_PROXY_HEADERS=true` (тогда IP берётся из *последнего* значения `X-Forwarded-For`, которое
  дописал ваш прокси). По умолчанию заголовок игнорируется — иначе клиент мог бы подделать IP и обойти лимит.
* SSE в вебе и мобайле авторизуется заголовком `Authorization` (токен не попадает в URL и логи); `?access_token=` оставлен только
  для сторонних EventSource-клиентов — не используйте его за прокси, который логирует URL.
* `/ready` не раскрывает тексты ошибок БД/Redis (только `ok`/`error`; подробности — в логах).

## Шифрование at rest (прикладной уровень)
С `PIA_AGENT_SECRET` (MultiFernet; несколько ключей через запятую — ротация) шифруются:
* API-ключи LLM пользователей;
* история чатов (`chat_turns.content`);
* TOTP-секреты;
* тела джоб и результаты (`ingestion_jobs.envelope/result`) и черновики фактов (`extracted_facts.payload`);
* загруженные файлы (`BLOB_STORAGE_DIR`, магическая сигнатура + Fernet; `ENCRYPT_BLOBS=true`).

Старые незашифрованные данные читаются и перешифровываются командой `python -m app.security.rekey`
(то же после ротации ключа: новый ключ первым, старый — следом, затем `rekey`, затем убрать старый).

### Что шифрованием приложения **не** закрыто
Поисковые копии базы знаний — `chunks.text` и JSON-`payload` сущностей/наблюдений — хранятся открыто, потому что по ним
работают полнотекстовый/векторный поиск и SQL-фильтры. Полное шифрование «всей БД» делается на уровне хранилища, и это
нужно включить в вашей инфраструктуре:
* управляемый Postgres (RDS/Cloud SQL/Azure и т.д.) — encryption at rest (KMS) включено флагом;
* self-hosted — шифрованный том (LUKS/dm-crypt, шифрованный EBS/PD) для `pgdata`, `redisdata` и `blobs`;
* бэкапы шифруйте отдельно.
Это сознательное разделение: ключи, переписка и файлы защищены приложением независимо от диска, а индексы для поиска —
инфраструктурным шифрованием.

## Прочее
* Изоляция по `user_id` на каждом запросе, владение blob'ами, защита от path traversal, лимит загрузки.
* Ключи и токены не попадают в логи; ошибки внешних API логируются без тел запросов.
* Подтверждение фактов (`CONFIRM_EXTRACTED_FACTS`): данные, извлечённые из фото/PDF, попадают в базу знаний только после
  явного «Подтвердить» пользователя (кнопки Telegram/Slack/Web/Mobile).

## LLM endpoints и публичная регистрация

В production пользователь выбирает только URL из `LLM_ALLOWED_BASE_URLS` (точное совпадение после нормализации).
Для Ollama добавьте доверенный адрес, например `http://ollama:11434/v1`; это применяется и к ранее сохранённым настройкам.
Администратор отвечает за доверенность этих серверов и DNS. В development локальные URL разрешены.
`ADMIN_EMAILS` больше не назначает права. Для существующего аккаунта команда требует `--promote-existing`:
сначала проверьте владельца. При обновлении проверьте ранее выданные роли — автоматически они не отзываются.
Ротация `rekey` при недоступном старом ключе прерывает транзакцию, сохраняя исходный шифротекст.
