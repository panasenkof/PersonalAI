# UX/UI Redesign PersAI — проектное направление (2026-10-21)

> **Статус:** визуальное направление **Nebula v0.3 одобрено** (21.10.2026). 21.10 отдельно утверждены REF-ICON-A и REF-ORB-B (иконка и живой объект); нормативная спецификация — [NEBULA_VISUAL_CONTRACT.md](design/NEBULA_VISUAL_CONTRACT.md). Финальный интерактивный Figma-дизайн и APK ещё не приняты; код UI не менялся. Этот документ — детализация задач **86–90** из [PLAN.md](../PLAN.md), а не самостоятельная очередь. Согласование макета **до UX-аудита** — обязательное требование владельца проекта.

**Связанные файлы:** [предварительный UX-аудит исходников](UX_AUDIT_PRELIMINARY_2026-10-21.md) (не заменяет Android QA), [манифест оригинальных изображений](design/references/README.md) (пока ожидает фактической загрузки бинарных файлов).

## 1. Концепт и порядок

- **Утверждённый пользователем визуальный контракт:** [Nebula v1.0](design/NEBULA_VISUAL_CONTRACT.md) — тёмная футуристичная тема, живые многослойные объёмные сферы по двум конкретным пользовательским изображениям, анимируемые мембраны, космическая глубина и ограниченный star-flight. Минималистичные/плоские замены явно запрещены. Согласовано художественное направление, но не финальная Figma-реализация.
- **Текущая Figma:** [проект PersAI](https://www.figma.com/design/FO1xr1tsaHOnfzJC8O9mqK), сохранены версии v0.1 и v0.2; создана отдельная страница `APPROVED STYLE · Nebula v0.3` с палитрой/типографикой и базовым сферическим компонентом. **Полный перенос экранов v0.3 в Figma пока не закончен из-за ограничения числа MCP-вызовов тарифа Starter; нельзя говорить, что финальный макет уже есть в Figma.**
- **Демонстрационный интерактивный HTML-прототип v0.3:** подготовлен в разговоре 21.10.2026, включает локальное прикрепление фото/PDF/файлов, демо-чат, переключение анимации голоса, прототипы памяти и настроек, шесть SVG-иконок; не связан с настоящим LLM или памятью. При продолжении работы перенести концепт в нативные Figma-компоненты, сохранив семантические editable layers, а не импортировать большой screenshot.
- **Отложенное утверждение:** проверить обновлённый интерактивный макет, активные и пустые состояния, доли экрана для диалога и ввода, доступность и пределы анимации. До этого не считать завершённой детальную UI-спецификацию и аудит.
- Стек: React Native / Expo 57; React Navigation Bottom Tabs + Native Stack, `react-native-safe-area-context`, уже существующие Jest и браузерный Playwright. Нативная приёмка APK обязательна отдельно.
- **Последовательность:** (A) Figma-концепт → утверждение общей композиции → (B) аудит текущих экранов/сценариев → (C) дизайн-система → (D) постепенный перенос экранов → (E) регрессионная защита каждого PR. Исправление блокирующего разрешения микрофона выполняется параллельно, без ожидания редизайна.

### Эстетическое направление

Направление Nebula: тёмный космический фон, умеренное цианово-сиреневое свечение, читаемая типографика, компактные иконки, стеклянные поверхности и карточки **только для структурирования информации**; основной чат максимально свободен от второстепенных блоков. Первая страница не должна начинаться с «Чем помочь сегодня?», навязанных идей и подсказок. Светлая тема сохраняется как доступный будущий вариант, но не первичный референс. Убрать декоративные инструкции и технические подробности с основных экранов; не заменять плотную форму россыпью гигантских карточек. На Android использовать привычные паттерны Material 3, не имитировать навигацию другой платформы. Все будущие категории и экраны должны соответствовать тем же правилам.

### Уточнение дизайна главной: настоящий чат + вложения (21.10.2026)

- Максимальная видимая область принадлежит **потоку сообщений**. На обычной главной **нет** больших приветствий «Чем помочь сегодня?», шаблонных подсказок и постоянно видимых блоков будущих задач. При пустом чате достаточно спокойного нейтрального состояния или анимируемой сферы, без информационного шума.
- Закреплённый **composer**: поле ввода, кнопка «+», отдельная заметная кнопка голоса, отправка; у длинного текста поле может расти лишь до установленного ограничения, затем прокручивается внутри. Системная клавиатура не перекрывает действия и историю.
- По «+» выбрать изображение, несколько файлов, PDF, аудио, камеру; показывать чипы/миниатюры до отправки, возможность удалить одно вложение, прогресс обработки и ошибки конкретных файлов.
- **Файлы внутри сообщения (мультимодальный чат)**, не обязательно запись в долгосрочной памяти. Модель через безопасный мультимодальный адаптер получает разрешённые пользователем вложения и при необходимости отвечает текстом, цитатами, картинками, файлами/результатами. Приватные «Документы» нельзя автоматически передавать LLM без явного согласия; должны соблюдаться текущие правила доступа/стоимости. Не объявлять обработку изображений и PDF готовой по факту наличия UI.
- Отдельное подтверждённое действие «Сохранить в память» или контекстная политика сохранения, с просмотром происхождения, статуса обработки и возможностью отказа. Это отличается от п. 84 «несколько медиафайлов в **одной заметке**» и требует самостоятельного функционального контракта с агентом.
- Дизайн состояний: отправка, загрузка, мультимодальная обработка, отказ провайдера, превышение бюджета, частично неуспешное вложение, завершение распознавания, просмотр вложения в диалоге и повторная попытка.
- Микроанимации: мягкое движение/дыхание сферы в idle, «слушает» вокруг микрофона, индикация работы модели и появления ответа. Реализация экономна к батарее, отключается по `prefers-reduced-motion`/Android Reduce animations, не мешает скроллу и набору.
- Иконка: **утверждён REF-ICON-A**, первая из двух присланных пользователем 21.10.2026 сложных космических сфер. Шесть ранее предложенных простых SVG/PNG **отклонены**. Внутри приложения для `NebulaCore` выбран **REF-ORB-B**, вторая присланная плазменная сфера. Геометрия, SHA-256 и запреты — [визуальный контракт](design/NEBULA_VISUAL_CONTRACT.md). Адаптивную Android-иконку требуется отдельно изготовить и принять по качеству и safe area; наличие выбранного референса не делает задачу реализованной.
- Новое функциональное направление (в дополнение к пп. 60, 61, 75, 83–85): **мультимодальный агентный чат**. Перед реализацией отдельная OpenSpec: входящие файлы/контент, capabilities моделей, согласие и границы приватности, OCR/зрение/извлечение PDF, выходные сообщения, журнал/ошибки, лимиты и кеш/удаление вложений.

## 2. Архитектура навигации: текущие и планируемые функции

Рекомендуемая отправная точка: три нижние вкладки **Главная / Память / Настройки**. Новые самостоятельные вкладки добавлять лишь по результатам пользовательских сценариев, не «по одному пункту плана». Для компактных сценариев использовать контекстное меню, bottom sheet, вложенный экран, поиск и ненавязчивые статусы; частые операции — в 1–2 шага.

| Область / экран | Текущие функции | Запланированные функции и пункты PLAN | Требуемые UX-паттерны |
| --- | --- | --- | --- |
| Главная/чат | диалог, история, смена модели, голос, фото/файл, «Улучшить/Исходный», просмотр памяти и источников | сводка дня (71), рекомендации (58), черновики в своём стиле (74), объяснимость ответов (77), наставник (78), персона/характер (82) | компактный закреплённый composer; меню вложений по «+»; история/модель компактно в шапке; источники и ход работы сворачиваемые; предложения не должны вытеснять чат |
| Память/поиск | заметки, разделы, статусы, поиск, вложения, корзина, правки, объединение, резервирование | CLIP + OCR (83), несколько медиа в одной записи (84), очищенный импорт URL и MP3 (85), полные транскрипты (75), новые шаблоны/связи (56, 66), даты фактов (72–73), право на забвение (79) | один общий поиск и фильтры; визуально различимые типы вложений; галерея/просмотр файлов внутри записи; доступность оригинала и извлечённого текста; подтверждение и undo разрушительных действий |
| Проактивные задачи / действие из чата | пока ограничено запросами пользователя | automations (57), календарь/события/почта (64), сводка дня (71), геонапоминания (81), каталог инструментов (62), уровни автономии/журнал (76) | единый каталог активностей по контекстному входу (не четвёртая обязательная вкладка); экраны создания/приостановки задания; журнал выполнения; подтверждение действий; разрешения по месту только при реальном использовании |

| Системные состояния | вход, ошибки, загрузка, экспорт, Share и камера | несколько файлов в Share (84), автоматический импорт (85), фоновые операции (57), дополнительные права (81) | единые skeleton/empty/error/success/permission; сценарий возврата из системного окна; сохранение черновиков; запрет на неожиданный сброс биометрии и навигации |

**Важно:** изображённые в концепте карточка «Сегодня», несколько вложений и настройка характера — **зарезервированные UI-точки для будущего**, а не объявление готовой функциональности. Не показывать их как рабочие кнопки в APK, пока реализация не появилась.

### 87 — UX-аудит и карта сценариев (P0, ПОСЛЕ утверждения 86)

- Инвентаризация существующих экранов и переходов, вертикальной прокрутки, дублирующихся настроек, слишком сложного первого экрана, слабых/необнаружимых действий.
- Скриншоты актуального APK и браузерной имитации с размерами 320/360/390/430 dp; отдельно long text, большие шрифты, клавиатура, bottom insets, жестовая и трёхкнопочная навигация, светлая/тёмная темы.
- Проверка сценариев: первый запуск → подключение; спросить; диктовка; фото/Share/URL → память; найти оригинал; изменить/перенести/удалить запись; резервная копия; контроль расходов и доверенного действия.
- Запротоколировать обнаруженные проблемы P0/P1/P2 **со скриншотом, шагом воспроизведения и проверяемым критерием устранения**; подготовить карту экранов текущих и будущих функций.
- Не выполнять бессистемную косметику по результатам аудита.

### 88 — Единая дизайн-система и UI-скилл (P1)

- Версионируемые semantic tokens: light/dark + high contrast; palette, typography, 4/8-pt spacing, radii, elevations, iconography, focus/pressed/disabled/loading/error/success, touch targets и motion.
- Компоненты: AppShell, SafeAreaScreen, Header, BottomTabBar, Composer, IconAction, Button, SearchField, Chips, ListRow, SectionHeader, EmptyState, BottomSheet, AttachmentGallery, MediaPreview, AgentActionConfirmation, Status/CostIndicator, SettingsRow, FormField.
- Разделить вариант/состояние компонентов от контента и бизнес-логики; повторно использовать компоненты. Зафиксировать Figma-источник и соответствие React Native компонентам, доступным для Code Connect позднее.
- Создать `docs/UI_GUIDELINES.md` и версионируемый `skills/mobile-ui-ux/SKILL.md` либо эквивалентные инструкции, которые агент реально читает до UI-изменений. `AGENTS.md` (п. 70) должен **ссылаться** на UI-правила, а не переписывать их.
- Правила плотности, визуальной иерархии, прогрессивного раскрытия; запрет на «экран настроек внутри карточки на главном экране» без UX-обоснования.

### 89 — Переход на новую навигацию и экраны без потери функциональности (P1)

**Отдельными небольшими PR:** AppShell/навигация → Главная/ввод → Память и редактор → импорт/медиа → Настройки/подключения → состояния и полировка. Не перекладывать в тот же PR изменение RAG, SQLCipher, разрешений камеры/микрофона или миграции базы, если это не необходимо для UI. Все существующие сценарии, доступность памяти, безопасность и сохранение настроек должны оставаться рабочими.

Проверять сохранение истории, состояния ongoing-запроса при переходе вкладок, черновиков и данных после обновления APK.

### 90 — UI regression gates и QA-принцип для всех будущих PR (P1; начать вместе с 88, соблюдать с 89)

- Переиспользовать `mobile/scripts/verify-mobile-ui.cjs`, расширить сценарии; пиксельные скриншоты на размер/тему/плотность отдельно от native Android.
- Нативные Maestro / инструментальные проверки только после оценки поддержки React Native/Expo и стоимости CI. Не считать веб-рендер доказательством отсутствия перекрытия Android клавиатурой.
- Критерии: **нет горизонтального overflow и обрезания кнопок**, все основные действия доступны при поднятой клавиатуре, нет перекрытий status/navigation bars, выдерживаются русский длинный текст и масштабирование >=1.3/1.5, touch targets Android обычно >=48dp, контраст, VoiceOver/TalkBack labels, reduced motion.
- Каждый UI PR: Figma/скриншоты до-после, объяснение сценария, какие будущие функции затронуты, визуальные регрессии, smoke на APK и обновление плана. **Не ухудшать дизайн ради ускорения фичи.**
- Защитить скриншоты от случайной замены «эталона» без ревью; CI зелёный не заменяет пользователя.

## 4. Сначала макет — затем аудит: правила изменения решения

1. Визуальная концепция Nebula v0.3 согласована как направление; провести ревью полного интерактивного v0.3 в Figma после снятия лимита доступа, используя HTML-демонстрацию как временный способ проверки.
2. Уточнить сценарии 3 экранов и точки роста: «Сегодня», диалог с действиями, поиск по объекту/тексту картинки, несколько файлов, расписания и расходы.
3. После согласования зафиксировать список `must-have`, `future slot`, `not in initial redesign`; не объявлять будущие элементы существующими.
4. Только после этого приступить к исследованию реального APK и заполнить аудит, прототипы вторичных экранов, dark mode и состояния.
5. При конфликте эстетики и доступности или функциональности сначала исправлять usability, сохраняя лёгкость оформления.

## 5. Внешние первоисточники и методы

- [Material Design 3 / Android UI](https://m3.material.io/) — структура, навигация, компоненты, адаптивность.
- [NN/g: 10 usability heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/) — критерии аудита.
- [NN/g: progressive disclosure](https://www.nngroup.com/articles/progressive-disclosure/) — редкие функции на второй уровень.
- [Expo keyboard handling](https://docs.expo.dev/guides/keyboard-handling/) — реальная клавиатура.
- [Expo safe areas](https://docs.expo.dev/develop/user-interface/safe-areas/) — status/navigation bars.
- [Maestro for React Native](https://docs.maestro.dev/get-started/supported-platform/react-native) — нативные пользовательские сценарии.
- [Storybook for React Native](https://storybook.js.org/docs/get-started/frameworks/react-native-vite) — изучить актуальную совместимость до выбора инструмента.

**Решение об инструментах:** не менять React Native / Expo и не внедрять новую UI-библиотеку без прототипа и проверки совместимости. Figma — источник утверждённого визуального направления; проектные токены и компоненты — источник правил выполнения в коде.
