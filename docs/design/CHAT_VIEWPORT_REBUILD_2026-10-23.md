# U0: восстановление устойчивого диалога

## Основание и область

Запись владельца `1000038817.mp4`, 19.6 с, 720×1600. Около 1–2 с при IME
история исчезает; около 6–8 и 15–18 с ответ меняет положение относительно
поля ввода. Контрольный main: `8f178ed` (после #100). Номер APK из записи
не установлен; соответствие записи этому SHA не утверждается.
Затронуты список сообщений, Send, потоковый ответ, чтение истории, клавиатура,
переходы между диалогами/вкладками и кнопка возврата. Данные, transport,
микрофон, AppLock и художественная B+C не меняются.

## Сравнение со старой реализацией по просьбе владельца

| Ревизия | Управление | Вывод |
| --- | --- | --- |
| `ed981c0` до редизайна, `58fbce5` первая композиция | KAV Android height; список сверху вниз; один unconditional animated scrollToEnd на content-size | Простая предсказуемая геометрия. Но непрерывная анимация и отсутствие ручного reading mode опасны для streaming |
| `f6de0da`, `a1341b9`, `a552f73` | RAF, near-bottom, Send latch, IME hide, lifecycle | Исправляли реальные частные проблемы, постепенно увеличили число владельцев состояния |
| `82a8698`, `52aa50f` | gesture flags, отдельный anchor по высоте streaming footer | Решение зависит от порядка content-size и footer-layout; queued follow не знает об anchor напрямую |
| `507d957` в #100 | flex-end для content container, дополнительные anchor/override flags | Нижнее выравнивание двигает все строки при росте короткого ответа; с виртуализацией/IME меняет координаты |

Возвращаем обычную геометрию старого списка. Безусловный animated scroll не
возвращается: он игнорировал читателя. Footer→row существовал и до редизайна,
поэтому это старый дефект, а не приписанная #100 новая ошибка.

## Подтверждённые исходниками причины и гипотеза Android

1. `chat-store.send` публикует saved assistant, а затем отдельным `finally`
снимает busy/streamText. Home одновременно мог отображать saved row и stream
footer. Даже при React batching ответ менял место/React identity.
2. Пять refs изменялись независимо в Send, IME, scroll и footer-layout.
Отложенная команда могла пережить смену намерения. 70%/позже 45% высоты
ответа — не координата начала ответа, особенно при крупном первом фрагменте.
3. `justifyContent:flex-end` перемещает короткие строки при каждом росте.
4. viewport `onLayout` обслуживал только pending Send: обычное открытие IME
не поддерживало видимость последней реплики.
5. Android clipping при виртуализации/resize — вероятный усилитель исчезновения
строк, не доказанная единственная причина. `removeClippedSubviews=false`
сохраняет virtualization, но запрещает отсечение видимых native children.

## Единый контракт (заменяет прежние scroll-правила #96–100)

- Header и composer остаются вне списка, B+C и нейтральные статусы сохранены.
- Геометрия обычная сверху вниз; короткий диалог не плавает от composer вверх
на каждом токене. Это возврат к старой основе в существующем дизайне Nebula.
- `presentChatRows` выдаёт один viewKey для live/final assistant, не меняя
постоянные UUID в базе. Saved answer имеет приоритет уже при busy=true.
- Единственный контроллер команд: latest / turn / reading. События IME не
выбирают режим. Новый user ID переводит в turn только после принятия Send
store: отклонённый запрос не ломает позицию чтения.
- latest следует концу; turn следует до вопроса и останавливается у его
начала (у очень длинного вопроса оставляет нижние 30% viewport над ответом).
Это измеренная координата клетки списка, не высота streaming footer.
- Ручной жест отменяет queued command; чтение не переопределяется токенами,
completion, IME или возвращением на вкладку. Только явное возвращение к концу
или кнопка включает latest. Новый диалог имеет независимые метрики.
- Кнопка «К последнему» находится внутри области списка, над composer,
с токенами Nebula и touch target 48dp; нет bottom=182.
- Старая история остаётся виртуализированной. Если вопрос ещё вне окна рендера,
одна команда по геометрии ДО Send раскрывает прежний хвост для измерения.

## CI #432: Clear/focus

Browser обнаружил потерю фокуса после Clear. В установленном RN Web 0.21.0
`ScrollView._handleScroll` при keyboardDismissMode=on-drag вызывает dismissKeyboard
даже для программного scroll. Контроллер также не исключал artwork пустого чата.
Исправлено: пустой список не прокручивается; keyboardDismissMode=none, явное
закрытие IME только в настоящем onScrollBeginDrag и Send. Регрессия empty/IME
добавлена, browser assert сохранён без ослабления. Новый SHA требует повторного CI.
