# U3.3 · Несколько вложений и выбор способа распознавания

Дата: 23.10.2026. Продолжение U3.1 / U3.2. Вся подборка сохраняется как **одна заметка**, а не отдельные заметки на каждый файл.

## Сценарий

1. Пользователь выбирает от 1 до 10 файлов через системный picker (изображения, аудио, видео и текст). Ограничение — 80 МБ суммарно. Можно также импортировать один файл с камеры/HTTPS/Android Share, как прежде.
2. На экране показаны имена всех выбранных файлов. Есть **два режима** при числе файлов больше одного:
   - **По очереди (по умолчанию)**: каждый оригинал распознаётся отдельно; результаты записываются в общий редактируемый текст заметки с указанием `Файл N: имя`. Одновременно выполняется не более одного вызова распознавания. Ошибка одного не удаляет другие результаты.
   - **Вместе**: сначала используется тот же последовательный этап получения текста/описаний, затем один дополнительный явный LLM-запрос **сопоставляет** успешно распознанные источники с общим контекстом. Сводный раздел добавляется после источников. Это **не** одновременная передача всех разноформатных бинарных файлов одним запросом: текущее API провайдеров не универсально для смешанного видео/аудио/фото.
3. Перед включением «Вместе» предупреждаем о дополнительных затратах, времени и передаче распознанного текста выбранной модели. Для «Личные — только на телефоне» совместный анализ запрещён; локальное чтение текстов и Whisper остаётся доступным в последовательном режиме. Смена записи на «Личные» возвращает последовательный режим.
4. В конце пользователь проверяет результат и один раз сохраняет **одну** заметку со всеми оригиналами. Распознанный текст сохраняется независимо от пользовательской подписи. Сохранение вызывает `saveMediaNote` один раз. SQLCipher-транзакция атомарно записывает все вложения, части, receipt и запись; при ошибке последнего файла откатывается всё. Никаких незавершённых оригиналов.
5. При ошибке отдельного файла остальные продолжают распознаваться; сообщение об ошибке только в UI, не в индексе знаний как факт. При ошибке дополнительного совместного анализа независимый распознанный текст остаётся, и пользователь может его сохранить. Отмена прерывает очередь и дальнейшие запросы.
6. Старое `file` API и однофайловый fingerprint остаются обратно совместимыми. В существующей таблице `memory_attachments` уже разрешено несколько оригиналов на `entity_id`, поэтому миграция схемы не нужна. Старый viewer U3.2 показывает несколько карточек одной заметки.

## Границы и защита

- Каждый файл сохраняется только по явному подтверждению; шифрование, ограничение сессии и проверка SHA-256 по частям остаются прежними. Выбор файлов не отправляет их в LLM самостоятельно.
- Доступ к обработке провайдером и общий LLM-анализ требуют пользователя и выбранных настроек. Сводный запрос передаёт **только извлечённый текст**, не исходные бинарные файлы, с явными маркерами источника.
- Совместный анализ ограничен 40 000 символов входа; весь индексируемый текст заметки ограничен 60 000 символов. Сокращение или отбрасывание частей **без сообщения пользователю запрещено**.
- Существующие Android Share payload-ы обрабатываются последовательно, как ранее, чтобы случайно не объединять чужие материалы без запроса.
- Не входит: добавление новых вложений к уже сохранённой записи, удаление отдельного вложения, объединённый прямой мультимодальный API-запрос нескольких фотографий за один проход, облачная очередь/возобновление после перезапуска, фоновое распознавание.

## Контракт тестирования

- Jest: три исходника/одна заметка, receipt-совместимость, хеши и транзакционный rollback при ошибке второго файла, лимиты и отказ заблокированной сессии.
- Jest/UI: multi-picker, последовательный порядок, два режима, выбор конфиденциальности, ошибки одного/совместного анализа и сохранение одного результата.
- Jest: опциональный синтез — ровно один дополнительный провайдерный запрос, проверка частичных и слишком длинных результатов, запрет для конфиденциальной записи, отмена.
- TypeScript, Jest, браузерные UI и Android CI необходимы **на финальном SHA PR**. Реальный Android multi-select и связанные кодеки требуют отдельного Maestro-проверочного сценария и ручной приёмки — нельзя объявлять пройденными до появления свидетельств.
