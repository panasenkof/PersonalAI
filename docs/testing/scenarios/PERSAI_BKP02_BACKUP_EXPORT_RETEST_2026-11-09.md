# PersAI — BKP-02: повторная проверка шифрованного экспорта после исправления

**Основание:** отчёты `docs/testing/reports/PERSAI_MEMORY_AI_2026-11-09_f16f9298.md` и `docs/testing/reports/PERSAI_PR444_DEFECT_RETEST_2026-11-09_5f1a6893.md` (DEF-1/P1).
**Изменённый код:** `mobile/src/local-memory/backup.ts` — предварительный расчёт объёма из исходного SQLCipher-файла и WAL с проверкой свободного места; при недоступности штатного пути — проверяемый fallback на PRAGMA.
**Запрет:** не очищать, не удалять и не перезаписывать рабочую память владельца для теста. Не прикладывать в GitHub коды восстановления, пути, DB/WAL, дампы памяти, личные скриншоты или содержимое архива.

## A. Автоматическая проверка (зафиксировать SHA и полный вывод)

1. Сверить SHA проверяемого коммита и предшествующие PR #444–#446, архитектурную карту C0-A/C3-B; новых хранилищ и форматов копии быть не должно.
2. В `mobile/`: `npx tsc --noEmit`, `npx jest --runInBand src/local-memory/__tests__/backup.test.ts`, затем штатные `npm test` и `npm run test:ui`. При FAIL — не объявлять зелёный CI.
3. Проверить тестами: нативный путь SQLCipher + WAL, случай отказавших PRAGMA, fallback без нативного пути, нехватка места, неверный код, повреждённый архив, rollback, очистка временного файла и отказ от выдачи ложного подтверждения сохранения.
4. Проверить CI `Mobile (typecheck + regression tests)`, `CI required`, native SQLCipher, подпись release APK. Записать commit SHA APK и SHA256.

## B. Android 16 / vivo X200 Pro — физическая проверка

1. Установить новый APK **поверх** `com.persai.app` без удаления данных. Записать исходное количество разделов/записей, наличие диалога и состояние AppLock, затем снова сверить после теста.
2. На рабочем профиле открыть Настройки → Резервные копии; создать код восстановления, сохранить его **вне приложения и вне отчёта**, отметить подтверждение, нажать «3 · Сохранить файл копии».
3. Проверить, что появился системный выбор получателя. Сохранить зашифрованный файл в доступном пользователю месте. Нельзя считать закрытие системного меню доказательством сохранения.
4. Подтвердить, что получатель действительно создал **ненулевой** файл; зафиксировать размер и SHA-256 **файла** (без публикации самого файла). Выполнить второй экспорт с другим кодом и проверить второй файл отдельно.
5. При отказе сообщить только безопасный код: `BKP-02A` (чтение записей), `BKP-02B` (число страниц), `BKP-02C` (размер страницы), прочие `BKP-02` (место/оценка), `BKP-03…07`. Не пересылать raw native stacktrace с SQL/ключом. Падение экспорта = **FAIL**, блокирующий релиз, даже при зелёных Jest.
6. Убедиться, что после 2 экспортов исходная память (заметки, вложения, разделы, темы/история диалогов) сохранилась; AppLock и поиск продолжают работать.

## C. Восстановление — только отдельный пустой QA-профиль / второе устройство

1. Создать отдельный пустой QA-профиль, проверить что нет пользовательских данных и что владелец согласен с восстановлением именно в него. Рабочий профиль не трогать.
2. Сохранённый файл №1 восстановить с правильным кодом. Сверить число записей, разделов, вложений, таблицы пользовательских данных и историю диалогов. Проверить выборку по тексту и одному вложению после реиндексации.
3. Повторить на **другом пустом** QA-профиле с файлом №2 и вторым кодом.
4. На отдельном пустом профиле проверить неверный код, обрезанный/повреждённый файл, старые зашифрованные версии (по доступным QA-фикстурам), запрет перезаписи непустой памяти.
5. Проверить, что при ошибке/отмене не происходит частичного переноса, безвозвратного удаления, утечки исходных данных или ложного сообщения «сохранено».
