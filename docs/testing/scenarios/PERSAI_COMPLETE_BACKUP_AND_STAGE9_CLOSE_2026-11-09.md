# PersAI — полная зашифрованная копия, настройки подключений, завершение этапа 9

**Runbook для независимого ИИ-агента / Android 16.** Основание: PR #444–#449 (физический экспорт и восстановление памяти), PR #450 (параметры подключения и ключи), PR #451 (вложенные счётчики), PR #452 (browser/Jest test harness). Не путать успешное выполнение Jest с физической проверкой на телефоне.

## 0. Безопасность и идентификация

1. Зафиксируй `main` SHA, SHА APK и версию установленной сборки, CI status каждой merge-головы. Только официально подписанный APK (один `applicationId` и тот же ключ подписи); устанавливать `adb install -r` без очистки.
2. Исходная память, профиль и коды восстановления считаются личными. Не публикуй лог, raw SQL, API-ключ, номер устройства, полные пути, дампы SecureStore или ciphertext. В отчёт поместить только обезличенный факт присутствия конкретного тестового подключения/ключа.
3. Если для восстановления необходимо очистить единственный профиль, **не запускать `pm clear`** без отдельного явного разрешения владельца и **двух** уже проверенных независимых файлов копии с кодами вне телефона. Предпочтительно использовать запасной тестовый телефон / изолированный профиль.
4. Не передавать несанкционированные ключи сторонним сервисам в качестве «проверки»: достаточно проверить внутри UI, что ключ и конфигурация восстановлены, и выполнить разрешённый тестовый запрос к тестовому провайдеру.

## 1. Данные перед копированием

Создать две синтетические записи в `ИИ / Обучение / QA-BACKUP-CHILD`, одну в родителе; еще одну в защищённом тестовом разделе и одну архивную, где разрешено. Добавить фото или текстовый вложенный файл; зафиксировать SHA-256 **тестового** содержимого, количество файлов, записей и цепочку разделов. Сохранить тестовый диалог с темой, историей и одной черновой заметкой.

Установить не менее двух подключений моделей, например `DeepSeek-QA` и `OpenAI-QA`, с **разными тестовыми ключами**, несовпадающими URL и моделями, отдельно настроить ключ поиска, активное подключение, лимит шагов LLM (не по умолчанию), выбор моделей для медиа, число результатов поиска фото (не по умолчанию), голосовой движок, индексирование поисковых слов (вкл/выкл). Не публиковать значения ключей даже тестовых.

## 2. Кодовая/CI приёмка

1. `cd mobile; npx tsc --noEmit`
2. `npx jest --runInBand src/local-memory/__tests__/backup.test.ts src/local-memory/__tests__/backup-settings.test.ts src/local-memory/__tests__/agent-catalog.test.ts`
3. `npx jest --runInBand` (зафиксировать **код завершения**, не только счётчики pass; `Jest did not exit` = FAIL).
4. `node scripts/verify-mobile-ui.cjs` на поддерживаемом Node 22 и повтор на Node 24; зафиксировать `PASS`/`FAIL` отдельно, не полагаться на CI, если локальное воспроизведение падает.
5. CI `Mobile`, `native-sqlcipher`, `CI required`, `Signed standalone APK`, Android smoke: все `success` на SHA проверяемой сборки.
6. Тест на восстановление старой v19 копии с манифестом 8 без блока настроек: данные восстанавливаются, не подставляются чужие/придуманные API-ключи; UI чётко объясняет, что ключи в старом архиве отсутствуют.

## 3. Два независимых полных экспорта

1. Выполнить `store.checkpoint`, на экране «Резервные копии» проверить явное предупреждение: файл + код дают доступ к **всем** данным и API-ключам, а модельные бинарники/системные разрешения не переносятся.
2. Сгенерировать код 1, отдельно сохранить, экспортировать файл 1. Подтвердить наличие ненулевого файла у получателя и SHA-256. Повторить с новым кодом 2 → файл 2 с другим SHA-256.
3. Проверить, что ни в одном случае файл не считается сохранённым лишь из-за закрытия Android share-sheet. Провал в любом BKP-01…07 не должен оставлять частичный ciphertext или ложный receipt.
4. Проверить, что файл **не** plaintext SQLite и никакие ключи не появляются в имени файла, notification/logcat/UI (кроме намеренного поля кода восстановления).
5. Сверить до/после количество записей, фото и вложений, разделы/пути, историю диалогов и исходные настройки подключений. Исходная база не должна модифицироваться экспортом.

## 4. Восстановление из каждого файла (только безопасное пустое назначение)

1. Подготовить пустой тестовый профиль или второе устройство; если профиль один, выполнить отдельно согласованный безопасный цикл с предварительной перепроверкой копий и кодов. НЕ использовать рабочий профиль без согласования.
2. Восстановить файл 1 с кодом 1, затем файл 2 с кодом 2 в **другом** пустом назначении. Проверить одинаковые ID/версии пользовательских данных, число записей, вложения, хеши тестового файла, иерархию, FTS по русскому, контекст/тему 8+ диалогов.
3. Открыть «Настройки → Модели и подключения»: исходные две модели/провайдеры, разные API-ключи, поисковые ключи, активная модель, URL и остальные параметры должны восстановиться **без ручного ввода**. Проверить не раскрывая ключи в отчёте. Сравнить выбранные медиа-подключения, лимит, результаты фото, голос, флаг индексации.
4. Проверить приложение после force-stop и повторного разблокирования: подключения и данные остаются, AppLock всё ещё требует защиту, не авторизует автоматом отправку личных оригиналов/голоса без явного согласия.
5. Модели на устройстве/ОCR/EmbeddingGemma — бинарники могут потребовать новой загрузки и проверки checksum; **не** переносить старые device-specific пути как рабочие.

## 5. Негативные сценарии без утечек

- Неправильный recovery code, повреждённый/усечённый encrypted file: не меняют существующий профиль, объясняют «код или повреждённый файл» вместо общей ошибки.
- Изменённый `settings_json` или SHA-256 внутри специально подготовленного **тестового** ciphertext (с корректным test-key): отклоняется **до** основной транзакции; секреты не попадают в UI/log.
- Restore в непустую память, конфликт диалогов, старый несовместимый формат: отказ с понятной причиной и без частичного переноса.
- Не читается SecureStore во время экспорта: экспорт не создаёт неполную копию и сообщает о сбое чтения настроек.
- Ошибка записи настроек после восстановленной SQLCipher БД: память сохраняется, UI предупреждает о неполном восстановлении настроек. Не писать «полностью восстановлено».
- Отмена Android file-picker/share-sheet: не происходит подмены профиля/пропажи записей.
- Проверить закрытый раздел и запись: LLM-инструменты не раскрывают содержимое или недоступное количество даже если UI владельца их показывает.

## 6. DEF-4a, DEF-5, Jest

- `count_local_notes`: для вложенного тестового раздела (1 запись у родителя, 2 у детей): direct=1, subtree=3, ACL исключает защищённые записи. Для недоступного/неизвестного ID не выдавать «0», ожидать `catalog_scope_unavailable`.
- Playwright UI: весь сценарий и начальная загрузка composer на Node22 + Node24; если локальная среда падает, записать причину, не подменять `readonly` на `false` и не считать DEF-5 закрытым.
- Jest: проверить полный код выхода, убедиться, что нет late `ExpoModulesCoreJSLogger` и открытых хендлов; если остались — отдельный дефект, не объявлять исправленным по одному зелёному CI.

## 7. Итоговый отчёт и решение об этапе

Положить датированный документ в `docs/testing/reports/` с точным SHA, ссылками на каждый CI/релиз, отдельными `PASS_AUTOMATED`, `PASS_PHYSICAL`, `FAIL`, `NOT_RUN`; сгруппировать результаты по сценарию и дефекту. Ни реальные API-ключи, ни ciphertext не коммитить.

Этап 9 можно отметить закрытым **только при всех критичных PASS**, включая полную копию/восстановление ключей, целостность памяти, отсутствие незакрытых P0/P1 и выполнение согласованного набора сценариев. Незавершённые / отложенные задачи явно перевести в будущий этап с объяснением; не скрывать `NOT_RUN` или `PARTIAL` под «этап завершён».
