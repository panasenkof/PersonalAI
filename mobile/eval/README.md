# Проверочный набор поиска по памяти

Меряет, насколько гибко помощник находит сведения о пользователе (п. 8 плана).

- `memory-fixture.ts` — память вымышленного пользователя Ивана (25 записей по разделам, включая личные «Документы») и 39 вопросов с ожидаемыми записями. Категории: другая форма слова, синоним, через человека, по смыслу, «нет в памяти», личные записи.
- `evaluate.ts` — прогоняет вопросы через тот же код, что и приложение (`searchApprovedNotes`, `prepareDirectContext`), на настоящей SQLite FTS5 (`node:sqlite`). Считает, попала ли нужная запись в пятёрку найденных, ушёл ли помощник в интернет и не попали ли модели личные записи.
- `__tests__/memory-eval.test.ts` — запускается вместе с `npm test`, печатает таблицу и падает, если какая-то категория опустилась ниже нынешнего уровня (`FLOORS`). Когда поиск улучшится, уровень поднимают.

Добавить вопрос: допишите `{ q, category, expect: [id записи] }` в `EVAL_QUESTIONS`, при необходимости запись в `EVAL_NOTES`.

## Расширенная автоматическая приёмка предметной памяти (29.10.2026)

- `domain-fixtures.ts` — **54 полностью вымышленные записи**, по автомобилю (договор, СТС, полис, заказ-наряды, гарантия, стоимость ремонта, ТО), рецептам, сохранённым статьям про ИИ и другие темы, домашним вещам и медицине трёх разных людей.
- `__tests__/domain-battery.test.ts` — реальные `SCHEMA_SQL`, `SqliteMemoryRepository`, FTS, версионное чтение источника, ACL, исправления, фотоприложения, хэши оригиналов, PDF extraction, истинные/неизвестные координаты, принадлежность лабораторных результатов и изоляция личных данных. **Не** заменяет реальный PDF parser, ASR, vision embeddings и LLM.
- `__tests__/live-memory-model.test.ts` — до 77 слепых бытовых диалогов (79 реплик) к реальной OpenAI-compatible LLM **только на синтетических данных**. Условно включается при наличии `PERSAI_EVAL_LLM_API_KEY`, `PERSAI_EVAL_LLM_BASE_URL`, `PERSAI_EVAL_LLM_MODEL`. Тест проверяет ответ, ограничение числа модельных вызовов, отсутствие веб-поиска и утечки секретного маркера; результаты оцениваются независимо от scripted-LLM тестов.
- `../src/direct-agent/__tests__/memory-dialogue-simulation.test.ts` — шесть последовательных агентных сценариев с подменой **только** провайдера и нативного SQLite bridge, но с реальным агентом/каталогом/FTS/записью.
- `.github/workflows/memory-acceptance.yml` — **только ручной запуск** через `workflow_dispatch`, без `schedule`, `push` или автоматических LLM-вызовов. По явной команде пользователя запускаются Jest/TypeScript/SQL **без native-сборки и эмулятора**; Android проверяется отдельно в обязательном основном `.github/workflows/ci.yml`. Платная реальная LLM проверяется только при ручном запуске с галочкой `live_llm=true` и наличии секретов провайдера. Текстовое подтверждение больше не требуется. Наличие ключа само по себе ничего не запускает. В live-тесте установлены лимиты по размеру набора (60/270/395 обращений), **512 выходных токенов на запрос** и **24 000 символов входного запроса**. Превышение останавливает проверку до отправки лишнего запроса. Результаты сохраняются как JSON artifact и summary; неполные/проваленные проверки не считаются PASS.

**Важно о границах:** наличие 54 вопросов и проходящих SQL-тестов не означает, что живой ИИ понимает все их перефразировки. `phrase` — контролируемый термин поиска, `q` — слепой вопрос для будущего масштабирования live-LLM-eval; этот уровень пока не градуируется автоматически для всех 54. Поиск по содержимому **неподписанной** фотографии, отсутствие/качество распознавания реальных документов и медицинская интерпретация без врача также не считаются проверенными. Физический C2 остаётся отложенным до приёмки владельцем после инвентаризации.

### Конфигурация GitHub Actions без передачи ключа в чат

В **Settings → Secrets and variables → Actions** нужного репозитория:

- **Repository secret**: `PERSAI_EVAL_LLM_API_KEY` — ключ тестового провайдера, желательно с минимальным бюджетом и отдельной ротацией.
- **Repository variables**: `PERSAI_EVAL_LLM_BASE_URL` — публичный HTTPS API URL до префикса `/v1`, `PERSAI_EVAL_LLM_MODEL` — имя модели.

Запускать **только по запросу владельца**: Actions → Memory acceptance (real algorithms + optional live LLM) → Run workflow. По умолчанию `live_llm=false`: выполняются только бесплатные по отношению к LLM детерминированные проверки (расходуются минуты GitHub Actions). Для платной проверки достаточно поставить галочку `live_llm=true` и запустить workflow вручную. Без галочки обращения к внешней модели не выполняются. Отдельные секреты хранятся исключительно в GitHub. Не сохранять токены в git, CI artifacts, тикетах или чате. Запросы через API ограничены выбранным набором (60/270/395 за диалоги, плюс один предварительный вызов проверки подключения), но окончательная стоимость зависит от тарифа модели, количества токенов и настроек провайдера; абсолютный денежный лимит дополнительно задаётся на стороне провайдера.

Проверяющий код отдельно знает ожидаемые ID источников и значения. `phrase` из синтетических записей никогда не подставляется как поисковый запрос. Частичная проверка моделью состоялась в [ручном запуске 40927056710](https://github.com/panasenkof/PersonalAI/actions/runs/40927056710): 10 из 12 реплик PASS, 2 FAIL без ошибок API. Полная приёмка не подтверждена.
- `__tests__/natural-dialogues.test.ts` — бесплатная проверка покрытия и структуры 77 сценариев, выполняется в обычном CI. Результаты платного запуска включают статус, поисковые запросы самой модели, использованные источники, ответ, причины ошибки и число запросов к API в отдельном JSON.
- Медицинские анализы, скрытые автомобильные документы и место хранения ключей не доступны облачной модели. Для них проверяется непередача данных и отказ от выдумывания значений. Это не приёмка медицинских консультаций по закрытым файлам.

### Ручной выбор платного набора

При ручном запуске с `live_llm=true` (галочка разрешает платные запросы):

- `suite=smoke` (по умолчанию): 10 диалогов, 12 реплик, максимум **60** запросов;
- `suite=core`: 54 исходных сценария, максимум **270** запроса;
- `suite=full`: 77 сценариев / 79 реплик, максимум **395** запросов.

В ручной платной проверке допускается максимум **5 последовательных вызовов модели на одну реплику**, в том числе вызовы инструментов поиска. Это совпадает с новым значением по умолчанию в приложении (пользовательские настройки лимита сохраняются). Каждый запрос ограничен 512 выходными токенами и 24 000 символов входного тела. Реальные расходы зависят от тарифа и числа токенов: лимит денежных средств устанавливается у API-провайдера. Ничего не запускается по расписанию, пушу или наличию API-ключа.

### Быстрая проверка LLM до Android и npm (29.10.2026)

- `.github/workflows/llm-connectivity.yml` — отдельный ручной workflow **LLM connectivity (quick)**. Делает **ровно один реальный платный API-запрос** с коротким вымышленным сообщением, без npm, Gradle, Android и базы памяти. Проверяет HTTPS, ключ/доступ, имя модели и наличие ответа. Сообщает только безопасный класс ошибки HTTP/DNS/TLS; не печатает секрет, тело запроса и ответ модели.
- Запустить: Actions → **LLM connectivity (quick, one paid request, no Android)** → Run workflow → `live_llm=true` (без текстового подтверждения). Проверка не запускается от CI, push, расписания или одного наличия ключа.
- В обычной ручной `Memory acceptance` тест LLM запускается **параллельно с** SQL, но **без Android и APK**. Native SQLCipher, APK и emulator UI остаются в основном CI и учитываются обязательной проверкой `CI required`. Первая проверка реального подключения LLM выполняется **до установки npm**. Если она не проходит, живые диалоги не отправляются. Пределы диалогового теста не меняются; отдельный preflight добавляет максимум **один** платный вызов.
- Этот preflight проверяет только доступность модели. Он **не подтверждает качество ответов, поиск по памяти или приватность**. Для этого нужны отдельные диалоговые сценарии. После исправления двух ошибок повторный ручной запуск [40935350212](https://github.com/panasenkof/PersonalAI/actions/runs/40935350212) дал **12/12 PASS** с `deepseek-flash` (24 вызова, 0 ошибок), а SQL-сценарии — 347/347 тестов. Это только smoke, не полная приёмка 77 LLM-диалогов или физических C2-сценариев.

### Ручной full на пяти вызовах: диагностика 30.10.2026

В [запуске 41007686856](https://github.com/panasenkof/PersonalAI/actions/runs/41007686856) реальная модель обработала все 80 реплик: 77 PASS, 3 FAIL, 0 ERROR, 162 API-вызова, private leakage=false. После аудита полных ответов два FAIL были ложными: оценщик не распознавал естественные отрицания «точной даты техосмотра нет» и «рецепта кваса в памяти нет». Регрессии этих фраз и контрпримеров исправляются здесь; **новый платный full не запускался**, поэтому фактический результат нового кода не заявляется как 79/80 или PASS.

В JSON-артефакте ручного прогона теперь сохраняется ответ целиком до 12 000 символов вместо 400; поля `answerChars` и `answerTruncated` явно показывают редкое усечение. В консоль CI по-прежнему выводятся только статусы, коды ошибок и количество запросов, не сами ответы; тестовые записи вымышлены. Это меняет только диагностику и оценщик, не лимиты расходов и не алгоритмы поиска.

Третий FAIL — `EXTRA-WEB-TOPICS`: модель не нашла `web-security` (статью про prompt injection) по обобщённому вопросу. Проверка использует реальный SQLite/FTS, но **без on-device эмбеддингов** (`searchApprovedNotes` с переданным тестовым репозиторием отключает `embed`); поэтому она не показывает качество векторного поиска. Не добавляем вторую систему синонимов или индекс до C2-сравнения на устройстве с проверенно построенными векторами (поиск ID `web-security` и ACL, а также baseline без векторов). Если vector retrieval справится, задача дополнительного лексического расширения закрывается без нового кода.


### Анализ повторного прогона #41007686856 (attempt 2, 30.10.2026)

Повторение старого workflow_dispatch закреплено за SHA `c5b0fb6` (а не за новой `main`): 76/80 PASS, 4 FAIL, 0 API ERROR, 168 платных вызовов, утечек закрытых записей не зафиксировано. **Ни одно исправление после этого SHA повторный запуск не проверил.**

- `NATURAL-med-me-us`: корректное «описания УЗИ там нет» ошибочно оценивалось как отсутствие отказа. В текущем едином oracle добавлена эта форма и отрицательная регрессия против выдуманного результата УЗИ.
- `EXTRA-CAR-NOT-DONE`: корректное «не подтверждение того, что ремонт сделан» не соответствовало слишком узкому regex. В едином сценарии добавлена естественная форма и отрицательная регрессия против утверждения «ремонт сделан». Закрытый акт по-прежнему не разрешён модели.
- `NATURAL-web-rag`: тестовый агент искал исходной длинной фразой и немедленно ответил «ничего нет»; при этом production `ChatStore` вызывает `runDirectAgent` с `rewrite:true`, а eval этого параметра не передавал. Eval теперь использует **ту же штатную переформулировку вопроса**, без нового индекса, таблицы или hardcoded словаря синонимов. Это меняет поведение **только будущих ручных live-прогонов** и может увеличить число платных helper-обращений; общий бюджет 400 API calls/полный набор, ограничение выходных токенов и явный opt-in остаются.
- `EXTRA-WEB-TOPICS`: по-прежнему отдельный lexical-only пропуск `web-security`; никаких дополнительных retrieval-путей не добавлено. Нужен native C2 прогон на устройстве с корректным индексом эмбеддингов перед решением о совершенствовании поиска.

Этот PR исправляет проверку (№8), а не качество векторной модели (№13). Сначала бесплатный CI. Повторная платная full-приёмка только по явному запросу владельца, **не** через Re-run jobs старого SHA.


### Выведенный из live-пула ручной сценарий про prompt injection (30.10.2026)

По решению владельца `EXTRA-WEB-TOPICS` **исключён из автоматически оцениваемых наборов smoke/core/full**, а не просто отмечен `skip`. Теперь полный набор — **77 диалогов / 79 реплик**; smoke (10/12) и core (54/54) без изменений. Исключение одного неоднозначного перефразирования не означает, что весь поиск по смыслу прошёл приёмку. Базовый `NATURAL-web-security` с прямым вопросом об инструкции внутри веб-страницы сохранён для контроля обычного поиска.

**Для проверки на устройстве:** сохранить в обычный доступный модели раздел «Заметки» запись с названием «Prompt injection» и текстом «В статье о prompt injection описаны недоверенные документы и разграничение системных инструкций и данных.» Убедиться, что локальные эмбеддинги настроены и индексирование записи завершилось, затем спросить **«Что я себе откладывал про безопасность ИИ, кроме архитектуры агентов?»**. Результат должен найти именно эту заметку и передать смысл без выдуманной информации. Повторить с отключёнными векторами как контроль FTS, проверить, что закрытые записи не выдаются. Это **C2/ручное наблюдение**, не результат CI и не доказанный уровень качества до фактической проверки.
