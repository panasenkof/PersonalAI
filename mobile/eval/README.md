# Проверочный набор поиска по памяти

Меряет, насколько гибко помощник находит сведения о пользователе (п. 8 плана).

- `memory-fixture.ts` — память вымышленного пользователя Ивана (25 записей по разделам, включая личные «Документы») и 39 вопросов с ожидаемыми записями. Категории: другая форма слова, синоним, через человека, по смыслу, «нет в памяти», личные записи.
- `evaluate.ts` — прогоняет вопросы через тот же код, что и приложение (`searchApprovedNotes`, `prepareDirectContext`), на настоящей SQLite FTS5 (`node:sqlite`). Считает, попала ли нужная запись в пятёрку найденных, ушёл ли помощник в интернет и не попали ли модели личные записи.
- `__tests__/memory-eval.test.ts` — запускается вместе с `npm test`, печатает таблицу и падает, если какая-то категория опустилась ниже нынешнего уровня (`FLOORS`). Когда поиск улучшится, уровень поднимают.

Добавить вопрос: допишите `{ q, category, expect: [id записи] }` в `EVAL_QUESTIONS`, при необходимости запись в `EVAL_NOTES`.

## Расширенная автоматическая приёмка предметной памяти (29.10.2026)

- `domain-fixtures.ts` — **54 полностью вымышленные записи**, по автомобилю (договор, СТС, полис, заказ-наряды, гарантия, стоимость ремонта, ТО), рецептам, сохранённым статьям про ИИ и другие темы, домашним вещам и медицине трёх разных людей.
- `__tests__/domain-battery.test.ts` — реальные `SCHEMA_SQL`, `SqliteMemoryRepository`, FTS, версионное чтение источника, ACL, исправления, фотоприложения, хэши оригиналов, PDF extraction, истинные/неизвестные координаты, принадлежность лабораторных результатов и изоляция личных данных. **Не** заменяет реальный PDF parser, ASR, vision embeddings и LLM.
- `__tests__/live-memory-model.test.ts` — до 78 слепых бытовых диалогов (80 реплик) к реальной OpenAI-compatible LLM **только на синтетических данных**. Условно включается при наличии `PERSAI_EVAL_LLM_API_KEY`, `PERSAI_EVAL_LLM_BASE_URL`, `PERSAI_EVAL_LLM_MODEL`. Тест проверяет ответ, ограничение числа модельных вызовов, отсутствие веб-поиска и утечки секретного маркера; результаты оцениваются независимо от scripted-LLM тестов.
- `../src/direct-agent/__tests__/memory-dialogue-simulation.test.ts` — шесть последовательных агентных сценариев с подменой **только** провайдера и нативного SQLite bridge, но с реальным агентом/каталогом/FTS/записью.
- `.github/workflows/memory-acceptance.yml` — **только ручной запуск** через `workflow_dispatch`, без `schedule`, `push` или автоматических LLM-вызовов. По явной команде пользователя запускаются Jest/TypeScript/SQL **без native-сборки и эмулятора**; Android проверяется отдельно в обязательном основном `.github/workflows/ci.yml`. Платная реальная LLM проверяется только при ручном запуске с галочкой `live_llm=true` и наличии секретов провайдера. Текстовое подтверждение больше не требуется. Наличие ключа само по себе ничего не запускает. В live-тесте установлены лимиты по размеру набора (36/162/240 обращений), **512 выходных токенов на запрос** и **24 000 символов входного запроса**. Превышение останавливает проверку до отправки лишнего запроса. Результаты сохраняются как JSON artifact и summary; неполные/проваленные проверки не считаются PASS.

**Важно о границах:** наличие 54 вопросов и проходящих SQL-тестов не означает, что живой ИИ понимает все их перефразировки. `phrase` — контролируемый термин поиска, `q` — слепой вопрос для будущего масштабирования live-LLM-eval; этот уровень пока не градуируется автоматически для всех 54. Поиск по содержимому **неподписанной** фотографии, отсутствие/качество распознавания реальных документов и медицинская интерпретация без врача также не считаются проверенными. Физический C2 остаётся отложенным до приёмки владельцем после инвентаризации.

### Конфигурация GitHub Actions без передачи ключа в чат

В **Settings → Secrets and variables → Actions** нужного репозитория:

- **Repository secret**: `PERSAI_EVAL_LLM_API_KEY` — ключ тестового провайдера, желательно с минимальным бюджетом и отдельной ротацией.
- **Repository variables**: `PERSAI_EVAL_LLM_BASE_URL` — публичный HTTPS API URL до префикса `/v1`, `PERSAI_EVAL_LLM_MODEL` — имя модели.

Запускать **только по запросу владельца**: Actions → Memory acceptance (real algorithms + optional live LLM) → Run workflow. По умолчанию `live_llm=false`: выполняются только бесплатные по отношению к LLM детерминированные проверки (расходуются минуты GitHub Actions). Для платной проверки достаточно поставить галочку `live_llm=true` и запустить workflow вручную. Без галочки обращения к внешней модели не выполняются. Отдельные секреты хранятся исключительно в GitHub. Не сохранять токены в git, CI artifacts, тикетах или чате. Запросы через API ограничены выбранным набором (36/162/240 за диалоги, плюс один предварительный вызов проверки подключения), но окончательная стоимость зависит от тарифа модели, количества токенов и настроек провайдера; абсолютный денежный лимит дополнительно задаётся на стороне провайдера.


## 78 естественных диалогов для реальной LLM (только по запросу)

- `natural-dialogues.ts` — 54 исходных случая плюс 24 дополнительных бытовых сценария: 78 диалогов, 80 пользовательских реплик. Включены сравнения ТО, уточнение второго рецепта, вопросы без ответа, поиск вещей, сохранённые статьи об ИИ и безопасность анализов родственников.
- `__tests__/live-memory-model.test.ts` — действующий агент и настоящий SQLite/FTS; **модель сама** формулирует поисковые запросы, вызывает инструменты и пишет ответ. Проверяющий код отдельно знает ожидаемые ID источников и значения. `phrase` из синтетических записей никогда не подставляется как поисковый запрос. Частичная проверка моделью состоялась в [ручном запуске 40927056710](https://github.com/panasenkof/PersonalAI/actions/runs/40927056710): 10 из 12 реплик PASS, 2 FAIL без ошибок API. Полная приёмка не подтверждена.
- `__tests__/natural-dialogues.test.ts` — бесплатная проверка покрытия и структуры 78 сценариев, выполняется в обычном CI. Результаты платного запуска включают статус, поисковые запросы самой модели, использованные источники, ответ, причины ошибки и число запросов к API в отдельном JSON.
- Медицинские анализы, скрытые автомобильные документы и место хранения ключей не доступны облачной модели. Для них проверяется непередача данных и отказ от выдумывания значений. Это не приёмка медицинских консультаций по закрытым файлам.

### Ручной выбор платного набора

При ручном запуске с `live_llm=true` (галочка разрешает платные запросы):

- `suite=smoke` (по умолчанию): 10 диалогов, 12 реплик, максимум **36** запросов;
- `suite=core`: 54 исходных сценария, максимум **162** запроса;
- `suite=full`: все 78 сценариев / 80 реплик, максимум **240** запросов.

Каждый запрос ограничен 512 выходными токенами и 24 000 символов входного тела. Реальные расходы зависят от тарифа и числа токенов: лимит денежных средств устанавливается у API-провайдера. Ничего не запускается по расписанию, пушу или наличию API-ключа.

### Быстрая проверка LLM до Android и npm (29.10.2026)

- `.github/workflows/llm-connectivity.yml` — отдельный ручной workflow **LLM connectivity (quick)**. Делает **ровно один реальный платный API-запрос** с коротким вымышленным сообщением, без npm, Gradle, Android и базы памяти. Проверяет HTTPS, ключ/доступ, имя модели и наличие ответа. Сообщает только безопасный класс ошибки HTTP/DNS/TLS; не печатает секрет, тело запроса и ответ модели.
- Запустить: Actions → **LLM connectivity (quick, one paid request, no Android)** → Run workflow → `live_llm=true` (без текстового подтверждения). Проверка не запускается от CI, push, расписания или одного наличия ключа.
- В обычной ручной `Memory acceptance` тест LLM запускается **параллельно с** SQL, но **без Android и APK**. Native SQLCipher, APK и emulator UI остаются в основном CI и учитываются обязательной проверкой `CI required`. Первая проверка реального подключения LLM выполняется **до установки npm**. Если она не проходит, живые диалоги не отправляются. Пределы диалогового теста не меняются; отдельный preflight добавляет максимум **один** платный вызов.
- Этот preflight проверяет только доступность модели. Он **не подтверждает качество ответов, поиск по памяти или приватность**. Для этого нужны отдельные диалоговые сценарии. После исправления двух ошибок повторный ручной запуск [40935350212](https://github.com/panasenkof/PersonalAI/actions/runs/40935350212) дал **12/12 PASS** с `deepseek-flash` (24 вызова, 0 ошибок), а SQL-сценарии — 347/347 тестов. Это только smoke, не полная приёмка 78 LLM-диалогов или физических C2-сценариев.
