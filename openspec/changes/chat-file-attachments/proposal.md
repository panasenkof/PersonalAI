# №84: файлы в сообщении чата

26.10.2026. Самостоятельный пакет после #125, не новая версия импорта заметок.

## Сценарий

Скрепка в composer → системный выбор → имя и миниатюра в черновике → убрать любой файл или нажать обычную отправку. Выбор не вызывает LLM. Без текстового вопроса используется явный нейтральный запрос «Посмотри приложенные файлы». Отправленные файлы видны в сообщении и входят в последние 8 реплик для уточняющих вопросов. Модель без vision может отказать: ошибка провайдера показывается, вложение остаётся в истории.

Вместо прежнего плюса «В память» в composer теперь скрепка для сообщения. Канонический импорт в заметку остаётся в Память → Добавить; камера по-прежнему явно ведёт в импорт памяти. Кнопки и сфера не размножаются. Выбранные файлы не создают заметку; сохранение предложений агента в память — отдельное явное действие.

## Данные и границы

JPEG, PNG, WebP; текст UTF-8 (TXT/MD/CSV/JSON и подобные); с H1 — PDF только как извлечённый локально текстовый слой (Android 15+ либо 12–14 с S Extension 13+). До 3 файлов на сообщение, текущий runtime-лимит подготовленного изображения до 6 МБ (не 2 МБ; точное значение задаёт MAX_CHAT_FILE_BYTES), защищённый черновик вмещает до 240 000 символов текста суммарно. При объёме свыше 24 000 для совместного пересказа включается согласованная обработка по частям (H-DOC1, #315–317). [Актуальный подплан](../../../Plans/CHAT_RESULTS_AND_LARGE_DOCUMENTS.md). PNG/JPEG/WebP проверяются по сигнатуре; внешние URI и бинарные/неподдерживаемые форматы отвергаются. На диалог до 24 МБ вложений (для текста консервативная оценка размера), затем новый диалог. Оригинальные PDF-байты, аудио и видео через этот путь пока не отправляются. PDF до 6 МБ проверяется по сигнатуре и системным парсером, превращается в текстовый блок с честным покрытием страниц и отметкой «оригинал не отправляется». Для скана без текстового слоя нет скрытого OCR/облачного fallback; предложено сохранить в память. При превышении текста или ошибке чтения отправка не происходит и содержимое не усекается незаметно.

Используется существующий SQLCipher snapshot диалога, без plaintext-файлов для постоянного хранения и без миграции таблиц. Picker cache удаляется в finally. Повторная проверка при чтении snapshot; повреждённые вложения оставляют исходную запись нетронутой и делают её нечитаемой с существующим сообщением восстановления истории. Отмена/блокировка/смена диалога не применяют поздний результат. Ошибка до транспортного запроса восстанавливает черновик и файлы; при ошибке провайдера отправленная реплика с файлами остаётся в истории.

В запросе реально передаются image content blocks и текстовые блоки с обозначением недоверенных данных. Протоколы Responses, Chat Completions, Anthropic Messages. Нет отдельной загрузки в Files API, автоматического OCR, поиска изображения или отправки вложений вспомогательным моделям. Поддержку vision произвольного совместимого сервера нельзя вывести из его названия; ответственность за выбор модели остаётся видимой в composer.

## Референсы и решение

Документальное сравнение 26.10.2026, не испытание чужих приложений:
- [ChatGPT: работа с файлами](https://openai.com/academy/working-with-files/) — вход у поля сообщения и вопрос к прикреплённому материалу; адаптируем в одну скрепку и локальный черновик.
- [Claude: загрузка файлов](https://support.claude.com/en/articles/8241126-upload-files-to-claude) — вход из composer, различие файла чата и постоянных материалов проекта; сохраняем различие чат/память. Их набор форматов и серверные лимиты не переносим.
- Android-перевод: системный DocumentPicker, Back отменяет выбор; доступные подписи и явное удаление чипа. Web drag/drop и платформенные Apple-контролы не копируем. Существующие Nebula tokens/клавиатура/нижняя панель сохранены.

Транспорт: [OpenAI images](https://developers.openai.com/api/docs/guides/images-vision), [Anthropic vision](https://platform.claude.com/docs/en/build-with-claude/vision). Форматы сверены по официальной документации; runtime-проверки запросов покрыты тестами трёх протоколов.

## Проверки

TypeScript; реальная сериализация запросов трёх протоколов с текущими и историческими вложениями; парсинг сохранённого диалога; отсутствие вызова модели при выборе; восстановление черновика при отказе до отправки; лимиты/повреждённые файлы; блокировка/отмена picker и очистка cache; browser с сохранением и отправкой настоящего текстового блока. Android picker, настоящий vision endpoint, TalkBack, большой шрифт и память на реальном устройстве NOT RUN локально. Required minimal Maestro не расширяется.

### H1 — реализуемый срез 02.11.2026

Picker PDF → проверка сигнатуры `%PDF-` и системный `extractPdfPages` → безопасный текстовый `ChatAttachment` с явным названием «Текст PDF: …» и покрытием → обычная ручная отправка через существующие OpenAI/Anthropic/chat-completions text blocks. Никаких исходных PDF-байтов в LLM запросе/истории и новой памяти. Проверка файла, 3-файлового бюджета и 24k текста, отмены/lock/очистки кеша — соответствующими тестами. Дополнительные аудиоформаты, ошибка одного вложения без потери других, индивидуальный retry/готовность и физический Vivo до I — остаток H; не считать H полным DONE по H1.

### H2 — отдельные ошибки выбора файла (02.11.2026)

В системном picker каждый из до трёх выбранных файлов проходит существующую проверку MIME/сигнатуры, `readChatAttachments` и общий `checkedChatAttachments` отдельно. Ошибка одного файла не стирает корректные вложения и ранее прикреплённые файлы текущего черновика; диагностическое сообщение сообщает имя и безопасную причину. Нет скрытого отправления, сохранения в память, фоново сохранённых оригиналов или автоматической попытки OCR/LLM. Повтор — пользователь вновь выбирает неудавшийся файл. Глобальная отмена, блокировка профиля и уход с экрана запрещают частичный commit. Совокупный лимит учитывает ранее принятые файлы. Source picker очищается в существующем `finally`.

**Ограничения H2:** изолированный режим пока только при выборе файлов из чата; Android Share сохраняет строгую atomic preflight до отдельной UI обработки в H3. Для неудачных файлов нет постоянных карточек или автоматического retry; предупреждение в действующей строке чата и повтор через ту же кнопку файла. Аудио и неподдерживаемые бинарные форматы не объявляются прочитанными. Реальный Android/Vivo, смена модели/транспорт и CI требуют отдельной проверки.

### H3a — Android Share, готовность по каждому файлу (02.11.2026)

Новый короткий вертикальный срез №84. Имеющийся `inspectSharedMaterial` по-прежнему описывает допустимость исходников для памяти и глобальные лимиты чата (не более 3 файлов / 24k текста). В `prepareSharedMaterial` файлы Share готовятся по отдельности в прежнем `persai-incoming` кеше через **тот же** `readChatAttachments`/ `checkedChatAttachments`, который используется в picker. Старая глобальная ошибка одного неподдерживаемого файла больше не обнуляет весь готовый набор. Индивидуальный результат: `chatStatuses[]` со статусом `ready/error` и фиксированным сообщением без исходного provider URI; только `ready` имеют `ChatAttachment`. В конце приватные копии всегда удаляются, external content:// оригиналы не затрагиваются. Lock/abort проверяются между стадиями и предотвращают возврат частично готового пакета.

`ShareDestinationScreen` показывает список доступных/непрочитанных материалов, доступную долю и ручную кнопку повторной проверки. В чат добавляются исключительно готовые вложения и явно переданный текст; отправка выбранной модели происходит только потом из чата. Сохранение в память использует прежний `MemoryImport` с **исходными Share payloads**, без побочного сохранения при проверке/повторе. Нет нового writer/SQLCipher-таблиц, сети, OCR fallback, транспорта и нового состояния в постоянном хранилище.

Не закрывает H полностью: отдельные карточки/ready-error-retry в самом чате, аудиовложения как транскрипт, изменение модели и физическое тестирование Vivo. Отказ одного файла не означает отправку этого файла; обязательные CI / emulator и реальный Android различаются. Benchmarks: existing step-8 UI section/Android Share native patterns (предварительно утверждены); никакого существенного редизайна.


### H3b — локальный Whisper для аудиофайлов в чате (02.11.2026)

Один узкий вертикальный срез №84: пользователь **явно выбирает аудиофайл через кнопку «Файл» в чате**. Файл до 20 МБ, MP3/M4A/WAV/OGG/FLAC/AAC, преобразуется существующим `transcribeAudioFile` **только локально** после проверки установленной модели `initWhisper/getWhisperStatus`; длительность ограничена штатным ASR максимумом 20 минут. Устройства с отсутствующим Whisper получают безопасную ошибку и не выполняют облачный fallback. Длинная расшифровка свыше 24 000 символов отклоняется без усечения; общая сумма с другими вложениями проверяется прежним `checkedChatAttachments`. Непустой transcript сохраняется в существующий ChatAttachment c `kind=text, mime=text/plain`, маркировкой «Транскрипт аудио: …», явным предупреждением о возможных ошибках и отсутствии исходных аудиобайтов. Только ручная отправка из чата передаёт этот текст выбранному LLM через тот же `chatContent`. Аудиооригинал не хранится в SQLCipher-снимке чата и удаляется из временного picker cache; оригинал при желании сохраняют отдельно в память.

Во время ASR показывается индикатор и кнопка отмены; `AbortSignal` отменяет native транскрипцию и не принимает поздний callback при lock/unfocus. Каждый элемент по-прежнему готовится изолированно; ошибки не стирают принятые вложения. **Android Share намеренно не запускает распознавание при открытии экрана выбора назначения:** запись можно вручную выбрать в чате; существующий путь «В память» сохраняет оригинал. Отдельное явное подтверждение Share-ASR, расширение поддерживаемых кодеков, модельные benchmarks, реальная точность/скорость на Vivo и полноценный статус по каждому файлу в основном чате — остаток H, не объявлены готовыми.

C0/C3: один авторитетный direct-chat writer, прежний file decoder и Whisper engine, прежняя SQLCipher память/поиск/ACL и backup, ноль новых моделей, таблиц, ASR транспортов, сетевых запросов. Проверки: offline-only, байты аудио не попали ни в один LLM protocol, empty/overlong/no-model, abort/lock, Share opt-in gate, карточка transcript. Тесты fixtures и CI отличаются от физического Android: точный SHA/результат выставлять после запуска required CI.
