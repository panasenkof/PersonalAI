# Memory Engine vNext — temporal knowledge graph

## Why
Схема SQLCipher v5 рассчитана прежде всего на заметки. В ней есть relations/observations/vectors, но отсутствует надёжная идентификация объектов, атомарное связывание факта с конкретным источником, полноценная история значений и общий поиск по наблюдениям, разговорам и медиа. Архитектура не может гарантировать сценарии «разговор с моей сестрой», «где работал тогда», «свечи поменял два раза» без догадок LLM.

Владелец согласовал проектирование новой долговременной памяти агента без сохранения текущих **тестовых** данных. Для установленных APK это **не** разрешение на незаметное удаление пользовательской базы.

## What changes (proposed, M0 only)
- Стабильные objects, typed claims/state/event, два времени valid/known, evidence→точный сегмент источника, mentions отдельно от подтверждённых отношений.
- Независимые оригиналы: sources/segments/messages/blobs, со ссылками на файлы и таймкоды. Одни и те же байты могут использоваться несколькими источниками.
- Подтверждаемые предложения и журнал операций; идемпотентный импорт, дедупликация, конфликты, безопасное объединение/забывание.
- Унифицированный локальный lexical/graph/time/vector search с политикой доступа по всему пути, проверяемыми доказательствами и fallback при отсутствии модели.
- Отдельный этап UX после стабильных API: визуальные карточки объектов, история, источники, связи/конфликты, не редизайн Home/Nebula.
- Точный контракт: Plans/MEMORY_ENGINE_ARCHITECTURE.md; UX: Plans/MEMORY_ENGINE_UI.md; реализация пойдёт отдельными небольшими PR M1–M6.

## Scope now / not now
M0 **только документация и согласование планов**. Этот PR не меняет схему SQLCipher, данные, графику или настройки. Не внедряем чужой фреймворк, графовую СУБД, сервер, фоновую геолокацию и дополнительные платные LLM-вызовы.
В M1 никакой silent-drop старой БД. Предусмотреть явное сбрасывание тестовой базы/отказ, ключи и внешний аккаунт не трогать.
